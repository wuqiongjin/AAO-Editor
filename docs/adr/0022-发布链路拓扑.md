# ADR-0022: 发布链路拓扑（CNB 工作台 + GitHub 公开面孔）

- **状态**：Accepted（2026-10-19 与用户拍板；替代起稿时的 Proposed。2026-10-20 增补 §9「GitHub 侧门禁」——用户诉求「对外公开的主仓库是 GitHub，门禁也得配」引出；具体规则值待用户在 GitHub 侧应用时确认。2026-10-20 修订 §5：增补 PR 段桩驱动例外——release-pipeline/10，用户确认。2026-10-25 修订 §7：CNB 副本同时作为可选下载源，须提供匿名 generic feed——grilling 定案，见 release-pipeline/16）
- **背景**：代码主仓在 CNB（`cnb.cool/AsterPicker/AAO-Editor`，public——开发工作流、门禁都在 CNB 侧），发布目标在 GitHub（`github.com/wuqiongjin/AAO-Editor`，public——electron-builder `publish.owner/repo`、ADR-0021 默认下载源、README 下载入口三处都已指向它）。仓库此前无任何 CI（无 `.github/`、无 `.cnb.yml`）；双 README 的「本地开发」指引从 GitHub clone、下载与反馈入口也都指向 GitHub，但该仓当前只有 24 commit 的 Vite 脚手架（无 release）——名实不符，镜像要解决的正是这件事。CNB 构建节点默认仅 Linux（mac/win 需组织自建机，当前没有）；素材按 release-pipeline/01 口径「CI 构建期注入、仓库不含二进制」，由外部素材源仓提供。
- **结论**：两侧分工——**CNB = 工作台**（质量门禁 + 向 GitHub 的代码镜像 + 国内 release 副本），**GitHub = 公开面孔**（代码镜像 + 三平台发版 + Releases）。发版由 `v*` tag 触发 GitHub Actions 矩阵构建，electron-builder 直接产出**正式 Release**。GitHub 对日常使用保持可写（罕见 PR 走人节奏回流），但常态下由 CNB 单向推送。
- **变更触发**：改镜像方向、把 GitHub 改成可写主仓、改下载源（含 CNB 是否作为应用内 feed）、引入代码签名 / 公证、改素材取件方式、动 assets 仓可见性、改 GitHub 侧门禁配置（分支 / tag 规则、必过检查、PAT bypass 名单），须先改本文件并经用户确认。
- **关联**：[ADR-0021](./0021-应用更新.md)（发版原址 GitHub；关于里可选下载源 GitHub / CNB）；[ADR-0011](./0011-Bestdori集成与本地客户端网络素材边界.md) §4（分发边界）；`.scratch/release-pipeline/issues/01`（素材注入与镜像原则）、`07`（本决策的 grilling 全记录）、`16`（下载源双源 + CNB feed）。

## 1. 职责划分

- **CNB 侧**：`main` push / MR → 质量门禁（`npm test` + `npm run build` + `npm run assets:check`；`pull_request` 段为桩驱动例外，见 §5）；`v*` tag push → 门禁 + 镜像 job（`main` + tag 推送 GitHub）；每天 22:00 定时 + `web_trigger` 手动触发 → 轮询 GitHub latest release 并转载到 CNB release（国内下载副本）。
- **GitHub 侧**：`v*` tag push / `workflow_dispatch` → **ubuntu 单平台门禁三件套（`ci-gate.sh`）** → windows / macOS / linux 三平台矩阵构建 → electron-builder `--publish always` 发布正式 Release（`latest*.yml` 随包，发布即可被默认下载源 GitHub 的 updater 发现）；`pull_request → main` → PR 门禁（§9，与 CNB 同款 `ci-gate.sh`，必过检查名 `gate`）；分支 / tag 规则保护公开 main 与发版 tag（§9）。
- CNB **不**构建安装包：无 mac/win 节点；单一构建真相放 GitHub Actions，避免两边产物不一致。

## 2. 代码通道：CNB → GitHub 单向镜像（非 force）

- **镜像 job**：每次 `main` push、每次 `v*` tag push 时执行；推送范围 = `main` + tags；**只允许 fast-forward**（不加 `--force`）。
- **安全语义**：没人往 GitHub 写时，快进推送与 force 无差别；一旦 GitHub 侧出现未回流的提交（如已合并的 PR），镜像 push 被拒绝 → job **响亮失败**，绝不静默覆盖。纪律：**GitHub 侧的任何合并，先 `git pull github main` 回流到 CNB，再下一次 CNB push**。
- **GitHub PR 回流路径**（罕见但有门）：他人在 GitHub 提 PR → 在 GitHub merge → 本地 `git pull github main` → push CNB → 镜像自然快进。人的节奏，不搞自动双向同步。
- **一次性例外**：GitHub 现有 24 commit 脚手架与 CNB 历史无关，首次同步由用户手动 `git push github main --force` 抹掉；此后永远快进。
- **只推不删**：tag 不删不覆盖；CNB 侧重打 tag 会撞非快进失败——那种情况本就该失败。
- CNB 侧 secret 走平台 secret 仓库 imports（见 §3）：`GITHUB_TOKEN`（fine-grained PAT，contents **+ workflow** 均写、仅授权代码仓——镜像推全仓含 `.github/workflows/`，GitHub 拒绝无 `workflow` scope 的 PAT 更新 workflow 文件）。

## 3. 素材注入：GitHub Actions 直连 CNB

- GitHub Actions 以 GitHub secret `ASSETS_SOURCE`（完整带只读 CNB 令牌的素材源 git 地址，一个 secret 到位）取件；CNB 门禁 job 同型——`ASSETS_SOURCE` 由 secret 仓库 `env.yml` 经同一 `imports:` 通道注入（`ci-assets.sh` 优先读它）。流水线内置 `CNB_TOKEN` 作用域仅限当前仓、读不了外部素材源，两侧统一为显式带令牌的 `ASSETS_SOURCE`；本地开发 export 有素材源读权限的访问令牌或 `ASSETS_SOURCE` 同理。**素材源地址与凭据一律走 secret / 脚本内置，不写入公开文档**（与 `assets-sync.mjs` 的编码存储约定一致）。
- CNB 侧两个 secret（`GITHUB_TOKEN` 镜像推送用、`ASSETS_SOURCE` 取素材用）走**平台 secret 仓库**：独立 private 仓存 `env.yml`，`.cnb.yml` 各流水线 `imports:` 引用注入。CNB 没有 GitHub 式仓库级 secret，这是平台既定机制。
- **不建 GitHub assets 镜像仓**：少一个仓、少一条推送流水线、素材少一份公网副本、token 过期是构建可见失败。代价是发版构建依赖 CNB 在线——可接受（自有 infra，且失败可见）。
- **不 pin ref**（YAGNI，单人项目）：clone main tip。接受「同一代码 tag 重建可能换到不同素材」——仅发生在故意更新素材时，不是缺陷。
- 素材源仓设为 **private**（第三方版权素材，不随代码仓分发）。private 是**可见性姿态而非 containment**：按 Q1，安装包公开分发，素材随之公开；真正的边界是 LICENSE 与 release notes 的版权声明（MIT 仅覆盖代码）。

## 4. 触发与版本

- `v*` tag push 触发发版 + `workflow_dispatch` 手动补发；`npm version` 手动管理；CI 校验 tag 与 `package.json` version 一致（不一致即失败）。
- 不上 conventional-commits 自动发版：内部工具要「人按一下才发」，避免半成品变成 updater 可收的新版。

## 5. 门禁与存量债

- 门禁 = `npm test` + `npm run build` + `npm run assets:check`——定义了就永远绿。
- **PR 段例外——桩驱动（2026-10-20 用户确认，release-pipeline/10）**：CNB `pull_request` 事件按「不可信事件不注入密钥仓库」口径（§3）拿不到素材快照，`ci-assets.sh` 取件必然失败（表现为门禁红在 clone 素材源仓）。该段改传 `ci-gate.sh --stub-assets`：`scripts/ci/ci-stub-gen.mjs` 写入「API 同真产物、数据取最小合法集」的占位 `*.gen.ts` 顶替取件（逐注册表判别：真快照则不动，缺 / 是桩才写），跳过 `assets:check` 与取件复核——PR 段门禁 = `npm test` + `npm run build`。仅对真实快照数据有效的守约套件（注册表坐标钉子、真实采样结构、精灵源格比）由 `tests/support/assetSnapshot.ts` 判别后 `skipIf` 跳过，行为类测试照常全量。**零遗漏仅限合入前**：合入后 main 的 push 门禁有真快照，三件套全量复跑兜底；桩契约漂移（注册表 API 变更、判别失效）由 PR CI 红暴露，不静默。push / MR / tag_push / crontab / web_trigger 五段不动，维持三件套。
- **三侧同一脚本**：CNB 门禁 job、GitHub PR 门禁（`ci.yml`）、GitHub 发版门禁（release.yml `gate` job）都调 `scripts/ci/ci-gate.sh`（口径一处定义，不复制）。触发面：CNB 跑常态路径（push / MR / tag_push）；GitHub PR 门禁只跑罕见回流 PR（§9）；镜像 push 不触发 GitHub 侧任何 workflow。**例外（用户 2026-10-20 拍板）**：tag 发版路径门禁跑两次——CNB 一次 + GitHub `gate` job 一次；tag 规则保留管理员直推灵活性（§9），发布物必须过门禁，双跑是换灵活性的对价，非疏漏。
- `npm run lint` / `npm run test:types` 存量错（HANDOFF 记录在案）不进门禁，另排 chore 票逐项清理。

## 6. 发版语义与签名

- 首个 Release 即**正式 Release**（非 draft / 非 prerelease）：draft 对 updater 不可见，内部验收绕不开「发出去才能被更新发现」。
- 本期**不做**代码签名 / 公证：mac Gatekeeper / win SmartScreen 的代价**双落地**——README 下载节 + 发版 workflow 的 `notes` job（三平台发布完成后用 `gh release edit` 把未签名告知与发行说明写进 release notes 头部）。
- **版本描述的单一来源 = 仓库根 `RELEASE_NOTES.md`**（`build.releaseInfo.releaseNotesFile` 指定；放根目录是 issue 04 锁测禁根 `build/` 夹之故）：electron-builder 读它写进 `latest.yml` 的 `releaseNotes`（产品内更新弹窗，ADR-0021 §2「有发行说明则附上」）；GitHub release 正文由 workflow `notes` job 从同一文件拼装（发布器 payload 只有 `tag_name/name/draft/prerelease`，**不写 body**——2026-10-19 源码实证）。发版 = 更新此文件 → 提交 → 打 `v*` tag。

## 7. 国内副本

- 每天 22:00 定时（Asia/Shanghai，平台固定）轮询 GitHub latest release → 有新版本下载安装包 → CNB release（`cnbcool/attachments` 插件 / Release API，内置 `CNB_TOKEN`）；幂等跳过已镜像版本。频率口径：发版是手动低频事件，轮询只为「免看管」——**不加密频率换时效**；要即时补镜像走 `web_trigger` 手动触发（页面「构建 → 手动触发构建」或分支详情页「镜像国内副本」按钮，见 `.cnb/web_trigger.yml`），与 cron 同一脚本。
- **手点下载 + 可选应用内下载源**：网页下手装仍走 CNB release 页；应用内把 CNB 选为下载源时，updater 必须能匿名 GET 到与 GitHub 同一 tag 的 generic feed（`latest.yml` / `latest-mac.yml` / `latest-linux.yml` + 安装包 + blockmap，sha512 与 GitHub 构建产物一致）。镜像脚本在转载附件之外，还要产出/改写这份 feed（GitHub 的 yml 里是相对文件名，不能原样当 CNB generic 根用）。**CNB 仍不构建安装包**；没有可匿名 feed 就不合关于里的 CNB 选项（ADR-0021 §3）。cron 频率不加密——人不赶着更新；停在 CNB 且副本未跟上 = 检查显示已是最新。

## 8. 否决

- 双向自动同步（CNB ↔ GitHub）：冲突治理 + 双边 CI，单人项目纯负担；PR 回流靠人（§2）。（口径边界：「双边 CI」指常态路径两边重复跑；GitHub 侧只监听 PR 的门禁不在此列——见 §5 / §9。**唯一例外**：tag 发版路径的双跑——用户 2026-10-20 拍板保留管理员直推 tag 的灵活性，GitHub 侧必须有自己的门禁兜底，见 §5 / §9。）
- CNB 重建 mac/win 安装包：无节点；且破坏单一构建真相。
- GitHub 作为开发主仓：开发工作流（云开发环境、门禁、素材邻近性）全在 CNB。
- GitHub assets 镜像仓：直连 CNB（§3）更轻——少一仓一 job、失败可见。
- assets pin ref：YAGNI（见 §3）。
- 自动打 tag 自动发版：不可控（见 §4）。

## 9. GitHub 侧门禁（2026-10-20 增补）

GitHub 是对外公开的主仓库（README 下载 / 默认下载源 / clone 入口三处都指向它），仅靠 CNB 侧门禁 + 镜像非 force 失败只是**事后响亮失败**——坏代码已经公开过一轮；罕见回流 PR（§2）更是零检查直达公开 main。故 GitHub 侧自设门禁，四件 + 一项清理：

- **分支规则（`main`，建议 ruleset「protect-main」）**：禁 force push、禁删除；**必须走 PR 才能合并**（required approvals = 0——单人仓，自己合自己的 PR，不摆第二双眼睛）；**必过检查 `gate`** 且要求分支最新；**不对管理员放开绕过**，bypass 名单只放**镜像 PAT**（fine-grained PAT 身份）——CNB 镜像 job 因此照常快进推送，其余一切直推被拒。纪律不变：GitHub 侧写入仍只走 PR 回流（§2），规则只是把纪律从「约定」变成「机制」。选 ruleset 而非经典分支保护：bypass 名单显式支持 PAT 身份，且规则对仓库管理员同样生效。
- **tag 规则（`v*`，ruleset「protect-release-tags」）**：授权身份 = **镜像 PAT + 仓库管理员**（用户 2026-10-20 拍板 B：直推灵活性要保留——应急场景人能直接推 tag）；禁更新、禁删除——对齐 §2「tag 只推不删不覆盖」，防 tag 被改指向后重放发版 workflow。镜像推 tag 的正是同一个 PAT，不受影响。**直推灵活性的对价 = 发版 workflow 自带门禁兜底**（§1 / release.yml `gate` job）：直推的 tag 没过 CNB 门禁，由 GitHub 侧三件套把关后才进构建矩阵——跑不过门禁的 tag 发不出正式 Release；代价是常态发版门禁跑两次（CNB + GitHub 各一次），用户拍板接受。
- **PR 门禁 workflow（`.github/workflows/ci.yml`）**：`pull_request → main` → 单 job `gate`（job id 即必过检查名，分支规则 required check 填 `gate`）→ 调 `scripts/ci/ci-gate.sh`（与 CNB 同一脚本，§5）。素材快照仓 private：`ASSETS_SOURCE` 只在本仓分支的 PR 里注入，**fork PR 拿不到 secret → 明确失败并指路**（维护者把分支推入本仓后重跑，或改走 CNB MR）——不静默跳过，红着比绿着安全；同仓分支 PR 正常全量跑。（与 CNB 侧 PR 段「桩驱动转绿」有意不一致：GitHub 侧 fork PR 是凭据缺失、须响亮失败；CNB 侧不可信事件本就不注入密钥，以最小合法桩维持门禁可执行——见 §5。）必过检查为红时合并被挡，这正是门的语义。
- **Actions 权限收紧**（repo Settings → Actions → General）：workflow 权限保持默认 read-only（release.yml 在 workflow 级自行提升 `contents: write`，现状不动）；关闭「允许 GitHub Actions 创建 / 批准 PR」；保留「首次参与的贡献者需批准后才运行 workflow」（public 仓默认，本身即一道门）。
- **存量清理**：删除 GitHub 侧残留的 `master`（24 commit 旧脚手架；默认分支早已是 `main`，镜像也只推 `main` + tags）——公开仓不该挂着一条名实不符的旧分支。
