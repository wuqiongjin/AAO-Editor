# ADR-0022: 发布链路拓扑（CNB 工作台 + GitHub 公开面孔）

- **状态**：Accepted（2026-10-19 与用户拍板；替代起稿时的 Proposed）
- **背景**：代码主仓在 CNB（`cnb.cool/AsterPicker/AAO-Editor`，public——开发工作流、门禁都在 CNB 侧），发布目标在 GitHub（`github.com/wuqiongjin/AAO-Editor`，public——electron-builder `publish.owner/repo`、ADR-0021 更新源、README 下载入口三处都已指向它）。仓库此前无任何 CI（无 `.github/`、无 `.cnb.yml`）；双 README 的「本地开发」指引从 GitHub clone、下载与反馈入口也都指向 GitHub，但该仓当前只有 24 commit 的 Vite 脚手架（无 release）——名实不符，镜像要解决的正是这件事。CNB 构建节点默认仅 Linux（mac/win 需组织自建机，当前没有）；素材按 release-pipeline/01 口径「CI 构建期注入、仓库不含二进制」，由外部快照仓提供。
- **结论**：两侧分工——**CNB = 工作台**（质量门禁 + 向 GitHub 的代码镜像 + 国内 release 副本），**GitHub = 公开面孔**（代码镜像 + 三平台发版 + Releases）。发版由 `v*` tag 触发 GitHub Actions 矩阵构建，electron-builder 直接产出**正式 Release**。GitHub 对日常使用保持可写（罕见 PR 走人节奏回流），但常态下由 CNB 单向推送。
- **变更触发**：改镜像方向、把 GitHub 改成可写主仓、改更新源、引入代码签名 / 公证、改素材取件方式、动 assets 仓可见性，须先改本文件并经用户确认。
- **关联**：[ADR-0021](./0021-应用更新.md)（更新源只认 GitHub 正式 Release）；[ADR-0011](./0011-Bestdori集成与本地客户端网络素材边界.md) §4（分发边界）；`.scratch/release-pipeline/issues/01`（素材注入与镜像原则）、`07`（本决策的 grilling 全记录）。

---

## 1. 职责划分

- **CNB 侧**：`main` push / MR → 质量门禁（`npm test` + `npm run build` + `npm run assets:check`）；`v*` tag push → 门禁 + 镜像 job（`main` + tag 推送 GitHub）；每天 22:00 定时 + `web_trigger` 手动触发 → 轮询 GitHub latest release 并转载到 CNB release（国内下载副本）。
- **GitHub 侧**：`v*` tag push / `workflow_dispatch` → windows / macOS / linux 三平台矩阵构建 → electron-builder `--publish always` 发布正式 Release（`latest*.yml` 随包，发布即可被 ADR-0021 的 updater 发现）。
- CNB **不**构建安装包：无 mac/win 节点；单一构建真相放 GitHub Actions，避免两边产物不一致。

## 2. 代码通道：CNB → GitHub 单向镜像（非 force）

- **镜像 job**：每次 `main` push、每次 `v*` tag push 时执行；推送范围 = `main` + tags；**只允许 fast-forward**（不加 `--force`）。
- **安全语义**：没人往 GitHub 写时，快进推送与 force 无差别；一旦 GitHub 侧出现未回流的提交（如已合并的 PR），镜像 push 被拒绝 → job **响亮失败**，绝不静默覆盖。纪律：**GitHub 侧的任何合并，先 `git pull github main` 回流到 CNB，再下一次 CNB push**。
- **GitHub PR 回流路径**（罕见但有门）：他人在 GitHub 提 PR → 在 GitHub merge → 本地 `git pull github main` → push CNB → 镜像自然快进。人的节奏，不搞自动双向同步。
- **一次性例外**：GitHub 现有 24 commit 脚手架与 CNB 历史无关，首次同步由用户手动 `git push github main --force` 抹掉；此后永远快进。
- **只推不删**：tag 不删不覆盖；CNB 侧重打 tag 会撞非快进失败——那种情况本就该失败。
- CNB 侧 secret 走密钥仓库 imports（见 §3）：`GITHUB_TOKEN`（fine-grained PAT，contents **+ workflow** 均写、仅授权代码仓——镜像推全仓含 `.github/workflows/`，GitHub 拒绝无 `workflow` scope 的 PAT 更新 workflow 文件，2026-10-19 镜像首跑实证）。

## 3. 素材注入：GitHub Actions 直连 CNB

- GitHub Actions 以 GitHub secret `ASSETS_SOURCE`（完整带只读 CNB 令牌的素材源 git 地址，一个 secret 到位）取件；CNB 门禁 job 同型——`ASSETS_SOURCE` 由密钥仓库 `env.yml` 经同一 `imports:` 通道注入（`ci-assets.sh` 优先读它）。流水线内置 `CNB_TOKEN` 作用域仅限当前仓、读不了私有快照仓（2026-10-19 门禁首跑实测证伪初版「门禁零 secret」设计，两侧统一为显式带令牌的 `ASSETS_SOURCE`）；本地开发 export 个人访问令牌（需有快照仓读权限）或 `ASSETS_SOURCE` 同理。**快照仓地址与凭据一律走 secret / 脚本内置，不写入公开文档**（与 `assets-sync.mjs` 的编码存储约定一致）。
- CNB 侧两个 secret（`GITHUB_TOKEN` 镜像推送用、`ASSETS_SOURCE` 取素材用）走**密钥仓库（Keystore）**：独立 private 仓存 `env.yml`，`.cnb.yml` 各流水线 `imports:` 引用注入。CNB 没有 GitHub 式仓库级 secret，这是平台既定机制。
- **不建 GitHub assets 镜像仓**：少一个仓、少一条推送流水线、素材少一份公网副本、token 过期是构建可见失败。代价是发版构建依赖 CNB 在线——可接受（自有 infra，且失败可见）。
- **不 pin ref**（YAGNI，单人项目）：clone main tip。接受「同一代码 tag 重建可能换到不同素材」——仅发生在故意更新素材时，不是缺陷。
- 快照仓设为 **private**（素材版权材料，不对外）。private 是**可见性姿态而非 containment**：按 Q1，安装包公开分发，素材随之公开；真正的边界是 LICENSE 与 release notes 的版权声明（MIT 仅覆盖代码）。

## 4. 触发与版本

- `v*` tag push 触发发版 + `workflow_dispatch` 手动补发；`npm version` 手动管理；CI 校验 tag 与 `package.json` version 一致（不一致即失败）。
- 不上 conventional-commits 自动发版：内部工具要「人按一下才发」，避免半成品变成 updater 可收的新版。

## 5. 门禁与存量债

- 门禁 = `npm test` + `npm run build` + `npm run assets:check`——定义了就永远绿。
- `npm run lint` / `npm run test:types` 存量错（HANDOFF 记录在案）不进门禁，另排 chore 票逐项清理。

## 6. 发版语义与签名

- 首个 Release 即**正式 Release**（非 draft / 非 prerelease）：draft 对 updater 不可见，内部验收绕不开「发出去才能被更新发现」。
- 本期**不做**代码签名 / 公证：mac Gatekeeper / win SmartScreen 的代价**双落地**——README 下载节 + 发版 workflow 的 `notes` job（三平台发布完成后用 `gh release edit` 把未签名告知与发行说明写进 release notes 头部）。
- **版本描述的单一来源 = 仓库根 `RELEASE_NOTES.md`**（`build.releaseInfo.releaseNotesFile` 指定；放根目录是 issue 04 锁测禁根 `build/` 夹之故）：electron-builder 读它写进 `latest.yml` 的 `releaseNotes`（产品内更新弹窗，ADR-0021 §2「有发行说明则附上」）；GitHub release 正文由 workflow `notes` job 从同一文件拼装（发布器 payload 只有 `tag_name/name/draft/prerelease`，**不写 body**——2026-10-19 源码实证）。发版 = 更新此文件 → 提交 → 打 `v*` tag。

## 7. 国内副本

- 每天 22:00 定时（Asia/Shanghai，平台固定）轮询 GitHub latest release → 有新版本下载安装包 → CNB release（`cnbcool/attachments` 插件 / Release API，内置 `CNB_TOKEN`）；幂等跳过已镜像版本。频率口径：发版是手动低频事件，轮询只为「免看管」——**不加密频率换时效**；要即时补镜像走 `web_trigger` 手动触发（页面「构建 → 手动触发构建」或分支详情页「镜像国内副本」按钮，见 `.cnb/web_trigger.yml`），与 cron 同一脚本。
- **下载镜像，非更新源**：updater 仍只认 GitHub 正式 Release（ADR-0021 §3「不做第二源」不动）。

## 8. 否决

- 双向自动同步（CNB ↔ GitHub）：冲突治理 + 双边 CI，单人项目纯负担；PR 回流靠人（§2）。
- CNB 重建 mac/win 安装包：无节点；且破坏单一构建真相。
- GitHub 作为开发主仓：开发工作流（云开发环境、门禁、素材邻近性）全在 CNB。
- GitHub assets 镜像仓：直连 CNB（§3）更轻——少一仓一 job、失败可见。
- assets pin ref：YAGNI（见 §3）。
- 自动打 tag 自动发版：不可控（见 §4）。
