# ADR-0017: 渲染密度整数比不变量（位图 : 物理 = 整数）

- **状态**：Accepted（定案于 chart-preview 08 四轮验收 grill，2026-09-30；用户逐问拍板 Q5–Q9。**2026-10-02 两次修订**：默认缩放锚点重定基（读数口径），票 10 布局落地后再上移物理基准——见 §5）
- **背景**：三轮验收（整数密度阶梯 1/2/4 + mip 不上采样钳制，记录见 `.scratch/chart-preview/issues/08` 的三轮验收段）后，用户实机**仍有台阶感锯齿**。环境实测：**dpr 1.25**（1920×1080 @125% OS 缩放）、浏览器 100%、高清档、预览缩放 185%。逐档验算暴露根因：整数阶梯的「干净」结论只在 dpr-1 / dpr-2 屏成立——dpr 1.25 下所有在用档位的 位图:物理 比全非整数（面板标准 2/1.25 = **1.6**、高清 4/1.25 = **3.2**；工具栏固定 3× backing = 3/1.25 = **2.4**）。浏览器对**大倍率非整数下采样**的滤波会跳采样点，音符细环被不均匀取样——正是用户看到的台阶感；也解释了「上轮有改善（mip 钳制修掉了糊）但锯齿仍在（重采样还在）」。同理，用户报告的工作台左侧键型工具图标锯齿（dpr 越大越严重）与面板是**同一根因的第二处表现**。
- **结论**：见 §1 不变量与 §2–§4 落点。默认缩放锚点变更见 §5。
- **变更触发**：任何新的「位图 → 屏幕」显示链路（新面板、新图标、新导出档）都必须满足 §1 不变量；要偏离须先改本文件并经用户确认。

---

## 1. 不变量

> **任何"烘成位图再交给浏览器显示"的链路，缓冲密度必须是设备像素比的整数倍：`density = dpr × k`，`k ∈ ℤ⁺`（k = 相对物理像素的超采样倍数）。**

原理：`density = dpr × k` 时 位图:物理 = k，浏览器做的是干净的 k 倍盒式下采样，不跳采样点；任何非整数比（1.6×、2.4×、3.2×）都会在细特征（音符白环、亚像素格线）上产生不均匀取样 = 台阶感。「密度取整数」是 dpr-1/dpr-2 屏的特例近似，不是一般解——**整数性要落在 `density/dpr` 上，不是 density 上**。

## 2. 各链路落点

| 链路 | 口径 | 变更 |
| --- | --- | --- |
| 预览面板（`resolvePanelDpr`） | `dpr × k`，k = 流畅 1 / **标准 1** / **高清 2** | 三轮的 `max(dpr, 整数阶梯)` 废止 |
| 工作台画布（`resolveCanvasDpr`） | `min(dpr, 整数阶梯)` **不变** | 它逐帧按物理像素直绘，本来就 1:1，无此问题 |
| 长图导出（`exportPanels`） | 固定密度 2，不读窗口（ADR-0016 §7）**不变** | 导出没有"显示端重采样"环节 |
| 工具栏音符小图标（`NoteIconGlyph`） | backing = `dpr × 2`（下限 2）+ 监听 resize（dpr 变化）重绘 | 三轮前留下的「固定 3× 与 dpr 解耦」取舍废止 |
| mip 取级（`mipLevelFor`） | 钳制收紧为 `min(lMax, lNoUp)`：细轴会从级位图**上采样**时宁取原图单步下采样（`imageSmoothing: high` 对 ≤~4× 单步可接受），不上采样优先 | 三轮的 `Math.max(lNoUp, 1)` 在细轴分比 ∈ (1,2) 时强制升一级、违背自己注释宣称的口径，废止 |

## 3. 代价（用户 Q8 拍板接受）

- **dpr-1 屏标准档从 2× 超采样变 1:1**（高清 4× → 2×）：1:1 与 2× 都是干净采样，细线 AA 依赖绘制期平滑（与工作台画布同口径）。三轮加余量针对的「2.5× 非整档」问题已由本不变量根治，余量不再是必需品。
- **dpr ≥ 3 的高清档密度 = 6**（today 4）：干净比 2× 的代价，内存 ↑；由 06 票的淘汰口径压测一并收敛。
- **面板上 流畅 == 标准**（同为 1:1 物理）：两档差异只剩工作台画布侧（`min` 口径仍区分）。
- 内存方向总体**下降**：用户实机（dpr 1.25）高清档位图 = 今天 2.5²/4² ≈ **39%**；dpr-2 屏不变。

## 4. 被否的替代

- **维持整数阶梯、只在面板侧 snap 到 dpr 的倍数**（高清保 ~4× 手感）：dpr 1.25 下密度 5，内存 ×1.56（3 分钟谱全量 ≈445MB），换不回可感知的画质差。
- **显示倍率叠加**（CSS 放大已烘位图）：不增加像素，只重采样，回到老问题。
- **预览专用 noteSize 放大**：偏离谱面几何口径（Bestdori 对齐），绘制真相分裂。
- ~~**「185% 当成 100%」全口径重定基**~~：四轮曾判定「牵动面最大且需迁移已持久化设置、收益为零」而否；2026-10-02 用户实机看到滑杆读数「185%」后**改判采纳**——迁移顾虑是误判（zoom 不持久化），牵动面实际只有两个常量 + 导出档钉住。定案见 §5。

## 5. 默认缩放锚点（用户 Q3/Q6 拍板；2026-10-02 两次重定基修订）

- **现行口径（票 10 二次重定基后）**：
  - `DEFAULT_PREVIEW_ZOOM = 1` —— 滑杆读数 **100%**（不变）；
  - `PREVIEW_ES_STANDARD = 0.74`（= `1.85 / 3 × 1.2`）—— 100% = **用户舒适档**：票 10 布局扩大（舞台 1121×509 → 1390×603）后实测定档，音符较扩大前默认档 +20%（27.7 → 33.2 物理 px）、一屏 8.91 秒 ≈ 扩大前 8.74（精确持平点 121.4%，滑块步进取 120%）；面板 289 CSS px 宽；
  - 滑杆区间 0.3–3 不变（物理包络 87–866 CSS px 宽）；Bestdori 130px 对齐档（130 宽 / 537 高 ≈3.66 秒）改由 zoom ≈ 0.45 命中，不再是基准；
  - 导出「130 × 537」固定档**不吃这份基准**：`exportPanels` 用独立常量 `EXPORT_ES = 1/3`（不再 `esForZoom(…)`），预览两次重定基都不带导出物漂移。
- **为什么改（一）**：四轮把默认值钉在 1.85 的前提「预览 UI 没有百分比标签」**有误**——工具栏滑杆本就渲染百分比读数（`PreviewStaticToolbar` 的 `slider-value`），默认 1.85 直接亮出「185%」，用户判定其怪（滑杆位置该叫 100%）。
- **为什么改（二，票 10）**：布局扩大把高度预算 +18%（509.5 → 603），据此实测定档「音符 +20%、视野持平」的物理档；口径延续第一条约定——**默认位置恒读 100%**（`100% = 舒适档` 是相对约定，物理含义随布局演进；zoom 不持久化，无迁移）。
- **零迁移仍成立**：zoom 只活在预览页 React state（不持久化），没有已存值要搬；导出物形制不变（独立常量钉住）。
- **历史**：Q6 的本意就是「滑杆叫 100%、物理 = 当时 185% 的观感」；08 轮实现成了「默认值 1.85」（读数 185%），2026-10-02 实机验收修正为原意；同日票 10 布局落地后基准物理再上移 1.2×（读数口径不变）。
