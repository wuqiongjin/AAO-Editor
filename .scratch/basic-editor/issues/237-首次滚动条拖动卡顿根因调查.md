# 237 · 首次滚动条拖动卡顿根因调查

Type: research
Status: resolved

本票 resolved 仅表示本轮调查与可复跑信号已落档；产品尚未修复，GPU 内部资源/驱动成因未完全确认。

## 来源与范围

用户 2026-11-15：刚打开软件、第一次进入谱面画布，拖动滚动条起初概率卡一下，后续正常。要求先复现、分析，暂不修改代码。

Windows / Electron，DPR 1.25，100% 默认缩放；独立 userData 与既有测试工程副本（1268 个顶层音符，173.335 秒，含负 BPM）。原工程、产品源码和依赖未改；未重建 dist。现有 dist 的文件时间为 2026-11-15 14:24:58，源码与现有产物分开测，不声称二者是本次同一构建。

## 已验证的结论

**首次滚动中的 GPU 栅格 Flush 是已捕获的一个直接阻塞来源；目前缩小到音符瓦片向主画布的首次贴图提交路径，尚未细化到纹理上传/资源创建/驱动同步中的具体内部操作。** 不能把该现象直接套用为 233/234 的带体 CPU 扫描线问题。

关键消融保留瓦片构建，只移除 `noteLayerCache.draw` 中的 `ctx.drawImage(t.canvas, clipped.sx, …)`，首次专项由 76.7ms 降为 37.1ms；因此不能仅以 CPU 瓦片已经预热或图片 load 完成推断首次实际贴图一定平滑。

另外存在启动阶段原生主线程长任务，与立即开始的首次拖动重叠。必须等待启动阶段结束后再做绘制消融，否则即使跳过 renderChart / 滚动业务回调，首次拖动窗口仍可能包含启动长任务。启动任务内部尚未完整归因，不以 GPU Flush 统一解释所有卡顿。

### 时间线证据

- `idle-0`：先记录 5 秒静置再拖动。静置阶段已有 51.3ms 的渲染主线程 RunTask；首次实际拖动另有 72ms 间隔，与 `CrGpuMain → GpuChannel::ExecuteDeferredRequest → RasterDecoderImpl::DoEndRasterCHROMIUM::Flush` 的 **67.3ms** 重合。
- `delayed-baseline-0` 再次复现相同 GPU 路径 **69.3ms**，对应首次拖动开始后约 129ms 处的 **76.7ms** 回调间隔。此时无 JS LongTask；只看 renderChart / JS 回调计时会漏报。
- `compile-0` 的未延迟首次拖动还捕获到同一路径 74.9ms，并与启动主线程任务重叠。V8 编译事件未显示一个足以解释此次停顿的长编译任务。
- trace 中可见外部内存压力及频繁 MajorGC，但不能把与停顿邻近的 GC 一律当成其原因；多数 GC 本体只有数毫秒，另有后续独立长 GC。

### 已排除 / 结论边界

- 跳过 BGM、跳过全部 AudioEngine 加载和键音包初始化后，立即拖动仍可慢；音频初始化不是所有停顿的充分解释。
- 等待 5 秒仍复现首次 GPU Flush，单纯增加初始化等待不足以消除。
- `CanvasSpriteIcon.ensureImagesLoaded` / `warmupBandStripStyles`、瓦片 CPU 预热不能单凭完成就证明 GPU 已暖好。源码定位：`src/rendering/render.ts:1965` 编排静态层和音符层；`src/rendering/pipeline/noteLayerCache.ts` 负责离屏瓦片创建及 drawImage 提交；`src/ui/CanvasSpriteIcon.tsx` 负责精灵切片/mip 绘制。
- 尚未确认具体是某张新精灵首次使用、瓦片 GPU 资源创建、着色器首次编译还是驱动同步；**不把这些候选写成已经证实的根因**。
- 禁用 GPU Canvas 会引入持续卡顿，不是修复方案。所有消融均改变像素/行为，只用于定位，未实施产品修复。

## 可复跑的专项信号

`node .scratch/diagnostics/scroll-start-20261115/probe.mjs --delay=5000 --trials=1 --tag=delayed-baseline --trace --assert-smooth` 已实际返回退出码 **1**；跳过画布绘制、只跳过音符层的对应首次专项返回 **0**。

后续若修复，应保留冷进程 + 真滑块拖动 + 相同可见内容，测 GPU timeline 和回调到达间隔，并验证像素一致；不能以移除绘制、禁用 GPU 或只测 JS 耗时当作通过。
