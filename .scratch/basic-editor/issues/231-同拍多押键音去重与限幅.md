Blocked by: —

## 来源

用户 2026-11-11 四问：① 当前音符音效（键音）的播放机制？② 多押（同一 beat 出现多个非 hidden 音符）时键音是否全部播放、这样设计合理吗？③ 同一 beat 存在多个**完全相同**音符时相同音效是否都播放、合理吗？④ 从听感 / 性能角度分析。

本轮只做只读调查，**未改任何代码**。以下「现状」为代码确证的事实；「待拍板」是尚未定案的问题清单，留待后续 grill，拍板结论追加进本票「定案」节，不另开票。

## 现状（代码确证）

**播放链路**：`AudioEngine.setChart()` → `buildKeyEvents()` 把谱面平铺成 `KeySoundEvent[]` → `tick()`（`KEY_SCHEDULE_AHEAD = 2.0s` 预排，`setInterval` 200ms + rAF 双驱动，推进式游标）→ 逐条 `playTick()` → `scheduleKeySample()`（每次新建 `AudioBufferSourceNode` + `GainNode`，固定 0.9 峰值，`src.start(when)` 样本级定时）→ `seGain → masterGain → destination`。采样未就绪时 `scheduleKeyTone()` 振荡器兜底（0.12 峰值）。这是**时间线自动回放，不经过任何击打判定**；唯一手势入口是素材页试听 `previewKeySample()`，绕过事件表。

**三个答案**：

| 问 | 答 |
| --- | --- |
| 多押是否全部播放 | **是**。`buildKeyEvents` 对每个音符 / 每条滑条每个非 hidden 连接点各 `push` 一条（`src/audio/AudioTiming.ts:112-139`），最后仅 `out.sort((a,b) => a.time - b.time)`（`:140`）；`tick()` 的 `while` 对同 `time` 的每条事件都 `playTick()`（`src/audio/AudioEngine.ts:524-537`）。全链路无内容级去重、无限流、无并发上限 |
| hidden 口径 | 只过滤 `ConnectionNote.hidden` 与所有 `beat < 0`（`AudioTiming.ts:115,120,129`）；`Single`/`Directional` 数据模型无 `hidden` 字段（`src/chart/types.ts:95`）；`BPM`/`System` 不发声。与 `CONTEXT.md:67` 一致 |
| 完全相同音符 | **是，重复播放**。两个相同音符 → 两个完全相同的 `{time, lane, kind, tier}` 事件 → 同一 `AudioBuffer`、同一 `when`、同一包络各播一次。数据层确实允许这类重叠音符且刻意保真（ADR-0001 重叠音符、issue 224、`NoteReplacementRules.ts:763-769`），主要来自特型谱面导入 / 片段库 / 代码修改 |

**四个关键事实**（决定了后面的分析）：

1. **`lane` 在音频侧不参与发声决策**：`src/audio/` 下 `evt.lane` 只出现在 `KeySoundEvent` 字段定义（`AudioTiming.ts:62`）、`buildKeyEvents` 的 `push(...)`（`:108-133`）与 `KeySound.ts:1` 注释；`tick`/`playTick` 只读 `time`/`kind`/`tier`（`AudioEngine.ts:539-556` 签名不含 lane）。加上 ADR-0004 §7「按击打样式分类、**不做 per-lane 音高**」，以及 `tap` 与 `slide` 共用同一个 `perfect.mp3`（`src/audio/gen/samples.skin00.gen.ts:9-10`）——同拍 N 个 tap 不是 N 个不同击打声，而是**同一采样的 N 次同相叠加**。
2. **唯一的「去重」是游标幂等**：`keyIndex` 防止同一事件被 rAF 与 `setInterval` 重复调度；`KeySoundSampleBank` 的 `cache` / `inflight` 是 **Map**（`keySoundSamples.ts:130-131`）做采样路径 / 解码缓存去重，模块级 `allSampleSrcs()` 的 `Set`（同文件 `:168`）仅供 preload；`scheduled` Set 是待撤销节点集合（无容量检查）。都不是按 `(time, kind, tier)` 的内容去重。
3. **无混音保护**：全仓无 `DynamicsCompressor` / limiter / pan / voice pool / polyphony limit；`scheduleKeySample` 的 4ms attack 与尾部淡出（`src/audio/keySoundSamples.ts:49-53`）防的是单声 click，不是叠加削波。2s lookahead 意味着预排窗口内节点早已 `start(when)`，播放时无法再按实际并发数动态调整。
4. **三处各自建表，但共用同一个函数 / 采样加载 / 音量口径**：工作台实时（`AudioEngine.setChart`，`:415`）、仿真场实时（`simPlayback.ts:134`）、离线视频导出（`exportVideo.ts:263` → `renderAudioTrack.ts:93-107` 对整谱逐事件建节点后一次性 `startRendering()`）各调一次 `buildKeyEvents` 生成自己的数组；离线侧还多一层 `!isFinite || time<0 || time>=duration` 过滤与整体 `+openingSeconds`（`renderAudioTrack.ts:98,103`）。ADR-0016 `:69` 原文只写「导出音轨口径：同一份事件表（`AudioTiming.buildKeyEvents`）+ 同一份采样加载 + 同一份音量口径（`settings.audio`）；不新建第二套调度 / 音量」，**未出现「三链路」字样**，约束范围是「离线音轨对齐既有实时 `AudioEngine`」。

## 已确证的问题（事实层，不需拍板）

**听感**

- **实测峰值（2026-11-12）**：用 `miniaudio` 解码仓库内真实 mp3，按 `src/audio/keySoundSamples.ts:47-53` 的固定 `0.9` 包络叠加计算（44100Hz 单声道；默认包 `skin00`，`seVolume=1`、`volume=1`，见 `AppSettings.ts:498`、`CONTEXT.md:249`）。`perfect.mp3` **原始峰值只有 0.446** → 单声实际峰值 **0.402**、2 押 **0.803（0 削波）**、3 押 **1.205（91 个样本削波）**、7 押 **2.811**。票面此前「2 押即越过 ±1.0」是按「采样原始峰值 = 1.0」推的，**不成立**；只有切到 `skin02`（原始峰值 0.985，2 押 1.774）或 `skin03`（0.717，2 押 1.291）才成立。注：`when` 在 `tick` 的 `while` 内逐条以 `ctx.currentTime + (evt.time - playhead)/rate` 计算（`AudioEngine.ts:533`），并非共享同一变量。
- 同刻**混 kind**（`skin00`）：tap+flick+skill = **0.743，0 削波**；4 种不同键音同刻 = 1.107（仅 **1 个**样本越界）；6 种不同采样同刻 = 2.105（704 个样本，但需 tap/flick/skill + 3 档方向键同时同刻，近乎不可能）。
- **快速连打**（`skin00`）：8 分（4 声）0.508、16 分（6 声）0.722、32 分（12 声）0.878，**均不削波**；极端组合「16 分连打每拍 3 种」1.547（69 个样本 ≈ 1.6ms）、「32 分连打每拍 2 种」1.459（122 个样本）。前几轮「混 kind / 连打照样破音」的判断同样基于错误前提，实际轻微到可忽略。
- 多押这一最重要的节奏信息被表达成「同一声更响 / 更厚」，听不出是 2 押还是 3 押；键音本该帮作者校对击打点密度，现在反而模糊了它。
- `CONTEXT.md:71`「同拍两点实机无法同时击打」是判定口径，音频侧却按 N 次发声，两者口径不一致。
- 同拍但 `kind` 不同（tap+flick+slide）时叠加不同音色、能听出层次，这部分保留有价值；问题集中在**同种音色**。注意 `tap` 与 `slide` 指向同一份 `perfect.mp3`，按 `kind` 分「不同音色」并不等于按采样分。
- 完全相同音符属于数据噪声被放大成音量异常，听感信息量为零。

**性能**

- 每声新建 2 个节点，无 voice pool / 并发上限 / voice stealing；`cancelScheduled()` 是状态变更时全量 `stop()`，不是新声抢占旧声（issue 226 已修的是「旧谱残留发声」）。节点创建 / 销毁与 GC 抖动随押数线性增长。
- 2s 预排窗口放大同时挂起量；离线导出最极端（整谱一次性建节点，无分段流式渲染）。
- **不宜夸大，但基线要改**：`AudioBuffer` 全局共享（含 `touchAudioBuffer` 预热）、`start(when)` 是样本级定时；但 `perfect.mp3` 实际是 **0.748s**（`keySoundSamples.ts:10-11`），包络播到 `buffer.duration` 自然结束（`:51-53`），`0.06s` 只用于振荡器兜底。即 BPM 120 的 16 分连打（间隔 0.125s）**单轨已有约 6 个采样尾同时存在**，与押数无关；风险集中在特型谱（阶梯谱 / 分叉绿条 / 高密度重叠）与长时长导出。早期 `issues/03` 提过「对象池 / 限制并发，避免 3000-5000 音符卡顿」，至今未落地。

## 定案

**定案时间**：2026-11-12，六轮 grill + Q16 重问，用户逐条 OK；同日用户确认「收敛并实现」。以下即用户定案，取代「待拍板」与「实现落点候选」两节的历史候选项。

### 语义

- **Q1 / Q4′（语义 C）**：键音 = 「同刻同一份发音只发声一次、不同发音各一次」的击打反馈，不是「每个击打点的忠实回声」；原推荐 B「每时刻只 1 声」作废。编辑器预览**不需要**对谱面数据保真到「连重叠音符都各发一声」。
- **Q5（数据层与音频层解耦）**：谱面数据层继续保真重叠音符（ADR-0001 / issue 224）；音频层是独立的**发声计划表**，归并只减少触发次数，**不等于不发声** —— 同刻结点仍是有效击打点、仍然发声；不是屏蔽结点、不是静音、不是删谱面音符、不是「逐结点发声失效」。ADR-0004 §7 修订必须写「逐结点计入、同刻归并」。
- **Q2 / Q3（术语）**：音频侧统一用「同刻键音事件」，基准为**时间轴秒 `time`**，不按作者轴 beat；术语写进 `CONTEXT.md` 音频域，不新建 `GLOSSARY.md`。
- **Q12（押数）**：押数**不另做可听表达**（不做 humanize / pan / per-lane 音高 / 按押数换采样），由画面表达；写进 `CONTEXT.md` 音频域。ADR-0004 §7「不做 per-lane 音高」口径**不变**。

### 归并口径

- **Q9（落点与键）**：合并落在 `src/audio/AudioTiming.ts` 的 `buildKeyEvents`，按 `(time, 采样等价键)` 归并，一处覆盖工作台实时 / 仿真场 / 视频导出三条链路（ADR-0016 §5）。事件表是发声计划表，归并条目 ≠ 删谱面音符，组内仍发声一次。
- **Q5′（同一份发音）**：按**解析后的采样文件**判定，不按 `kind` / `tier`。`buildKeyEvents` 三参、拿不到运行时 `keySet`，而四包 `tap ≡ slide` 共享关系一致，故静态化为 **6 类等价键**：`tap ≡ slide`（`perfect.mp3`）、`flick`、`skill`、`directional` tier 1/2/3。该前提由单测守住，将来包数据变了要回来改口径。
- **Q10（同刻）**：严格 `time` 相等，**不加容差**。
- **Q6（滑条）**：滑条同拍结点一并归并，仍逐结点计入、组内发一次声。

### 范围边界

- **Q11（砍掉限幅）**：本票只做 Q9 合并；**不做** limiter / compressor / 增益补偿 / 并发上限。理由：PCM 实测显示 Q9 合并后「同刻同采样」场景全部回到单声（最响 `skin02` ≤0.887），限幅无收益且会带来「后随单声变小」风险。混 kind 同刻与快速连打保持现状。票内 Q3 的 limiter / 增益候选与「实现落点候选」表里挂 limiter 的条目作废。
- **Q13（性能）**：本票不碰性能；限流 / voice pool / 对象池 / 离线分段渲染另开 `chore` 票。仓库内无并发导致性能问题的实测证据。
- **Q7（开关 / 试听）**：`seVolume = 0` 即键音静音，**不新增布尔开关**；素材页 `previewKeySample()` 只共享音量口径、**不纳入归并**。
- **Q15（lane）**：删除 `KeySoundEvent.lane` 及 `buildKeyEvents` 里的拷贝（音频侧 0 消费点），同步更新 `AudioTiming.test.ts` 的 `toEqual` 断言。
- **Q14（键种口径）**：击打样式 = **5 类** `{ tap, flick, skill, slide, directional }`；`directional` 的 tier 1/2/3 是 1 种键音 + 3 份采样。`ADR-0004:97` 四类→五类、`:74` 占位包按现状校正、§10 加「键种口径以 §7 为准」。
- **Q8 / Q16（验收）**：三张样本谱（多押 / 同刻混 kind / 完全相同音符）+ 用户手工 A/B，不加运行时开关；**砍掉 `OfflineAudioContext` PCM 峰值 ≤ 0 dBFS 硬阈值**，锁测 = 单测 + 静态源码断言（见「锁测」节）。真机听感单测覆盖不到。

### 事实基线

- 「2 押即越过 ±1.0」「混 kind / 连打照样破音」基于「采样原始峰值 = 1.0」的错误前提，由 2026-11-12 PCM 实测校正；「PCM / dBFS」的白话解释与 Q16 重问见 Comments。票面「现状」与「已确证的问题」两节保留为历史存档，数字以 Comments 的实测条目为准，不作实现前提。
