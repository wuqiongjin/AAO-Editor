# 166 · 冷启动打开工作台，视口停在非开头（=90s）位置，点播放才归位

Type: bug
Status: claimed（2026-10-09 根因已定位并实测复现；修法已拍板，实现中）

## 来源

用户 2026-10-09 反馈：每次重新打开程序再打开工作台，滚动条不在开头（偏上）、谱面画布内容跟着滚动条、播放条秒数也不在开头；点播放后三者立刻归位到开头。用户提示"之前有 issue 记录过、表现类似"。

判定为**新票**（不是 24 / 75 的复发）：24 = 导入谱面代码后按秒重锚跳尾、75 = PlayBar 定位后切页再滚跳回旧位置，二者都是**会话内**的滚动错位；本票是**冷启动恢复**这一条独立通路，且根因比它们多一层（锚点秒数被"旧 scrollY + 新几何"污染）。三票共用同一批代码（`PlaybackScrollModel` 按秒重锚状态机 / `useChartViewSession` 三段 DOM 不变量），本票引用 24 / 75 / architecture-refactor 09 作为上下文。

## 症状（实测复现，Playwright + dev server）

复现步骤：新建工程 → 音频页把谱面时长改 120s → 重新加载页面（= 重启程序，默认落在工程管理页）→ 打开工作台。

| | 期望（ADR-0005 §7「打开画布定位到谱面开头（beat 0）」） | 实测 |
| --- | --- | --- |
| 滚动条 | 置底（ratio = 1.0） | `scrollTop=13200 / maxScroll=52800`，**ratio = 0.25** |
| 画布 | beat 0 在判定线 | 画布 scrollY 同样 = 13200 → 判定线处 = **90.0s** |
| 播放条秒数 | 00:00.0 | **与画面一致的大值（用户实测 01:30）**；本轮脚本复现出 00:00.0（不同步变体）与 1.498s 两型，同一通路 |
| 点播放后 | — | RAF 每帧写画布 + 滚动条 → 立刻回到 0s（`ratio=0.993`，`00:00.7`），与用户描述一致 |

`13200 = 30s × 440px/s` —— 正是**默认 30s 谱面**的 `chartEndVirtualY`；即"打开"这一刻的滚动位置是**恢复前**那份几何留下的。

## 根因

主链一句话：**「打开定位 beat 0」没有自己的落点，只实现为"首次 virtualHeight 落地时置底一次"，而那一次发生在工程恢复之前**；恢复到达后走的是通用的「按秒重锚」（语义 = 保留当前秒数，issue 24 定案），于是"打开=开头"被"保留位置"覆盖。恢复里那句 `seek(0)` 只在一帧内按**旧几何**重写了画布/滚动条，随后就被重锚冲掉。

时序证据（`[diag]` 实测日志，冷启动）：

1. `canvas MOUNT initialScrollY=13200 chartEndY=13200` —— 画布按**默认 30s / 空谱面**挂载并完成置底（`useChartViewSession.ts:119-145`），`markInitialized()`。
2. **RC-2 置底不登记回声**：置底分支写 `scrollTop` 时没有 `registerScrollEcho`（对比 :142 的比例回写分支有），于是它自己引发的 scroll 事件被 `onScrollbarScroll` 当成手滚 → 反算 scrollY + `engine.seek(1.498)` + 秒数写回。实测：
   `onScrollbarScroll top=12650 echo=null suppressed=false` → `canvas setScrollY req=12541` → `onScrollbarScroll -> seek seconds=1.498`。
   用户侧的 01:30 是同一条通路（事件派发时 DOM 高度已是新值 → 反算出 90s，同时写画布与秒数）。
3. `handleProjectRestore durationSeconds=120` → `seek(0)`（旧几何）→ `canvas setScrollY 13200`，anchor 回 0。
4. **RC-1 锚点污染（把视图钉在假秒数的直接原因）**：几何换到 52800 后，**子组件** `FinalVirtualCanvas` 的 effect（`FinalVirtualCanvas.tsx:881-885`，`onScrollChange`）先于**父组件** `useScrollModel` 的 `noteChartEndChange`（`useScrollModel.ts:71-74`）执行，于是"旧 scrollY + 新几何"先喂进 `noteScrollObserved`，把 anchor 从 0 刷成 90；pending 之后才置位，重锚便"忠实"地把视图重锚到 90s。实测：
   `canvas onScrollChange y=13200 vh=53624 chartEndY=52800` → `noteScrollObserved … anchor 0.000 -> 90.000` → `noteChartEndChange 120|… anchor=90` → `takePendingReAnchor anchor=90.000` → `target y=13200 top=13200`。
5. **RC-3 重锚读到旧 maxScroll（issue 24 同款）**：effect2 依赖含 `chartEndKey`，会在 `virtualHeight` 落地前先跑一次，读到旧 DOM 高度（实测 `maxScroll=13200` → 算出 `top=3300`），靠后续 effect1 的比例回写兜回。

点播放能归位：`usePlaybackCoordinator` 的 RAF 每帧用 `engine.getSeconds()`（= 0）同时写 `canvas.setScrollY` 与 `container.scrollTop`（:103-109），两条真相源被播放头统一——这也解释了"播放后一切正常"。

补充：视口会话在页面**未激活**时就已挂载并完成置底（保活挂载，`AppShell.tsx:101-103`），修复不能假设"页面已可见 / 已有布局"。

## 修法（2026-10-09 用户拍板：A = 全修，分两步）

### 第一步（必杀本次症状）：主因 + RC-2

1. **给"打开/恢复 → 归零"一个显式落点**（修主因）：会话新增 `resetToStart()` —— 置位"待归零"，由 effect 在**下一次提交**（几何已是恢复后的新值）按当前 DOM 写权威值：`scrollTargetForSeconds(0, maxScroll)` 同源写 `canvas.setScrollY` + `container.scrollTop` + 锚点归 0 + 清 pending + 登记回声，并把判定线处秒数上报为 0（纠正陈旧 scroll 事件写歪的秒数 —— 用户侧的 01:30 就是这条）。由 `handleProjectRestore` / `onRecordAudioChanged` 调用（这两处本来就在 `seek(0)`，语义不变，只是让它真正生效）。
   - **必须与 RC-2 同做**：否则归零写进去后，置底那个**陈旧 scroll 事件**仍会把它覆盖回 90s（用户实测秒数 01:30 正是这条通路）。
   - 回声 TTL 仅 100ms，冷启动主线程忙时可能过期 → 恢复后的显式归零必须是权威落点；备选（不优先）：把置底推迟到恢复结算后（`persistence.isSettled` 门控），须防"无工程时永不置底"。
2. **置底补登记回声**（修 RC-2）：`initialScrollDone` 分支写 `scrollTop` 后同样 `registerScrollEcho`，消掉伪 seek 与它带来的秒数/锚点污染。

### 第二步（机制收口）：RC-1 + RC-3（第一步验收通过后做）

**排序建议（2026-10-10）**：先做 RC-1（有独立致病路径、改动小），RC-3 待 RC-1 落地后实测再定 —— 不在未复现的路径上改状态机（票 75 同款口径）。
- RC-1 的独立致病路径：**任何"时长变大"的非恢复路径**（音频解码落定真实时长、导入谱面代码改时长）。用户停在开头时，画布用"旧 scrollY + 新几何"把锚点刷成 `(新末端 − 旧scrollY) / 密度` 秒 → 重锚把视图钉到这个假秒数（本票实测的 90s 就是这么来的）。第一步只在**恢复路径**上绕开了它。
- 修法：把 pending 置位从 effect 前移到渲染期（几何变化那一刻），使"几何已变、尚未重锚"窗口内的 `noteScrollObserved` 不再刷新锚点（约 5 行 + 锁测）。
- 守门：issue 24 定案「改谱长保留当前秒」必须仍成立 —— 先落一条**红** DOM 测试（"停在 0s → 时长增长 → 仍在 0s"），并复跑 24 的行为锁。

3. **堵住锚点污染窗口**（RC-1，**已实现 2026-10-10**）：`PlaybackScrollModel.configure(geometry, scale, chartEndKey)` —— 置位待重锚与几何注入**同帧**（模型内按"key 与上次不同"置位，幂等）；`useScrollModel` 改为渲染期注入 key，删掉原 effect 置位（死通道）。于是"几何已变、尚未重锚"窗口内的 `noteScrollObserved` 一律 SKIP，锚点不再被"旧 scrollY + 新几何"刷成假秒数。
   - **实测定性：硬化，不是症状修复。** A/B（临时 `git stash` 撤掉 RC-1 后复跑浏览器）：冷启动插桩查锚点跳变 —— **修复前后都观察不到** `anchor 0 → 90`；谱面代码路径（60s→200s、200s→400s）两次都停在预期秒数。即第一步落地后原污染序列已不再被触发，RC-1 去掉的是那条"子 effect 先于父 effect"的隐式顺序契约（评审 Standards 轴点名的隐患）。
   - 保留理由：~10 行、全量门禁绿、issue 24 回归实测通过；不保留则那条顺序契约继续裸奔。取舍权在用户。
4. **重锚只在 virtualHeight 落地后消费**（RC-3，与 24 同款）：effect2 现状会在同一 commit 先按旧高度消费一次并清 pending。
5. 须守 issue 24 定案「编辑中改谱长保留当前秒数、不归零」的回归。
