## 症状

1. `FinalVirtualCanvas.tsx` 1048 行里内联着**整套操作编排**：
   `handleMouseDown:460` / `handlePointerMove:509` / `handlePointerUp:564` /
   `handleToolClick:599` / `handleDoubleClick:612` / `handleContextMenu:627` /
   `applyBoxAction:363` / `applyOps:275` / `beginDragCandidate:418` / `snapPos:268`。
   4px 阈值仲裁、单击/框选/拖拽三条通路的分派、Slide 锚点生命周期全在这一个组件里。
2. **编排层零测试**。`tests/` 里没有任何一个文件 import `FinalVirtualCanvas`、
   `handleToolClick`、`beginDragCandidate`、`applyOps`。被 ADR-0008 §9「规则表逐行落单测锁表」
   锁住的只有它们调用的**纯规则核心**（`ToolActionMatrix` / `NoteReplacementRules` / `SlideCombination`）。
   → 改编排 = 无网作业，只能凭手感验收。
3. **两条通路绕过分派矩阵**（leakage）：
   - `handleContextMenu:640` 右键删除直连 `deleteSelection`，不走 `ToolActionMatrix`；
   - 粘贴有两个入口：`ToolActionMatrix:184` 与 `EditingProvider:110`，各自调 `pasteChartNotes`。
4. **光标 / 视口 / 起点标记各有两份 state，双向同步**：
   - `hoverPos`（画布 px，`FinalVirtualCanvas:198`）↔ `UIProvider.mousePosition`（beat/lane，`UIProvider.tsx:50`）——
     每次 mousemove 各写一次（`:517`、`:521`）；
   - `viewport.scale` ↔ `ui.scale` —— 三个同步 effect（`:152` / `:841` / `:895`）+ wheel 回写（`:746`）；
   - `markerBeat`（`:200`）↔ `PlaybackProvider.markerBeat`（`:31`）—— 推过去后从未读回。
   `Editor.tsx:285-288` 已为此打了 workaround 注释（`mousePosition` 每次 move 换新引用 → 改走 ref），
   说明这是**已知并且被绕过**的问题，不是理论风险。
   历史上 issue 10 / 36 / 55 的漂移类缺陷全部出自这条缝。

## 根因

操作的**编排层**（手势状态机）与**宿主**（React 组件 + DOM 事件 + 绘制）没有 seam。
组件既当输入设备适配器，又当语义决策者，又当绘制发起者——于是：

- 语义决策无法脱离 DOM 测试（症状 2）；
- 同一个语义（粘贴 / 删除）因为"从哪进来"不同而有两条实现（症状 3）；
- 坐标需要在"画布 px"与"谱面 beat/lane"之间来回搬，搬的过程中长出三份互相同步的 state（症状 4）。

## 更正：原「粘贴两个入口」不是 leak，撤回

评审报告与切片 1 把「粘贴有 `ToolActionMatrix:184` 与 `EditingProvider:110` 两个入口」列为 leak。
**读码后撤回**：两者调用的是**同一个** `pasteChartNotes`（`NoteReplacementRules:544`），

## 切片 4：修复框选过程中滚动导致起点漂移（2026-09-10，**首个行为修复**）

**用户报的缺陷（既有，非本轮引入）**：按住拖出框选矩形后滚动，起点不锁在最初那个拍/轨道；
直到鼠标再动一下（触发 `handlePointerMove`）才"啪"地跳回正确位置。

**根因**：`selectionBox` state 存的是**画布坐标**——它是依赖 `viewport.scrollY` 的**派生值**。
而重算只发生在 `handlePointerMove`。滚动不产生 mousemove，于是缓存的画布坐标失效：
矩形继续钉在画布的同一像素位置，视觉上起点随滚动漂到别的拍。

**修法**：新增 `marqueeCursorRef`（光标的画布坐标，鼠标不动时不变），
加一个依赖 `viewport` 的 effect，在框选进行中（已过阈值 ∧ 非拖拽）用
「起点虚拟坐标 + 光标画布坐标」重算矩形。矩形在滚动全程锁住最初那个拍与轨道。

**为什么我的测试没抓到**：切片 3 的 `marqueeRect` 测试断言的是**函数**
（给定新 viewport 重算 → 结果正确，确实正确），而 bug 在**状态**（不重算）。
**锁了函数，没锁行为** —— 测试设计失误，记下来。
本轮补一条「起点画布坐标随滚动平移 600×es」的测试，把"不能缓存"这个前提钉住。

**验证**：`tsc -b` 0 错误；`vitest` **762 通过 / 47 文件**（761 + 1，零回归）；
`eslint` 0 error（3 条 warning 既有）。
**待用户在页面验收**（滚动漂移属视觉行为，单测覆盖不到 effect 层）。

> **与候选 3 同族**：本缺陷的本质是「把派生值（画布坐标）当 state 存」。
> `hoverPos`（画布 px）↔ `mousePosition`（beat/lane）也是同一病 —— 候选 3 不只是"少几个 state"，
> 而是"别把派生值缓存成 state"。本缺陷是这条原则的活证据。

### 结论二：只改两处（各自的理由不同，不都靠数字）

1. `src/visual/coords.ts` —— 可见集按 `Coords` 惰性缓存。**理由不是提速，是删冗余**：
   `renderChart` 一帧有 **4 个取用点**（BPM 标线 / 同时点击线 / BPM 数值 / 瓦片层选中描边），
   每次都新建数组且线性扫全部 span。`Coords` 生命周期 = 一帧（渲染与命中各自现造），
   故缓存**不跨帧、不失效**，语义完全不变。4 个取用点 → **2 次实际计算**。
   ⚠️ **帧耗时 0.31 → 0.30ms，收益在噪声内**（表内如实记录）。要并掉最后 1 次得改
   `drawNotesLayer` 签名，边际收益 <0.1ms，**不做**。
2. `src/chart/editing/NoteDragging.ts` ②占位表 —— **只建落点窗口内的键**。**这条有数字**：
   占位键 = `beat|subBeat|lane` **精确相等**才可能命中，故真实拍位在窗口外的对象
   不可能与任何落点键相等 → 先做一次纯数值窗口预筛（0.04ms），再只对窗口内对象建键。
   **保守超集裁剪**（EPS 只放宽不收紧），不漏不误判。1.83 → **0.50 ms**（复测区间 0.46–0.65）。

   - 紧凑选区（本测量：20 件落在 0–28 拍）→ 窗口 ≈ 36 拍 → **3.6×**；

## 切片 6：候选 5 收口（2026-09-10）

### 5-a 静态层失效键补 `verticalRatio`（已实现 —— **定性为潜在陈旧加固，非用户可见缺陷**）

改动：`src/visual/staticLayerCache.ts` +7 行 —— basis 类型增 `verticalRatio`、
`nb` 取 `rc.geometry.verticalRatio`、失效比较链加一行。

**已证实的（结构事实）**：只改纵向比例而 surface / scale / scrollY / bpmEvents / chartEndBeat
全不变时，改前 basis 命中 → 位图停留在旧比例。而旧比例的内容确实不同（临时探针实测：
ratio 1 / 2 的静态层绘制调用 **178 vs 114 条**，序列不一致；探针已删，结论留此）。

**未证实、且被用户证伪的（可观测性）**：用户在当前 UI 路径下**未能复现**"网格陈旧"。
掩盖机制未查实（页面是保活挂载，`.app-page` 只 `opacity:0` 非 `display:none`，故不是切页改尺寸；
推测是改纵向比例引起内容总高变化 → 滚动量随之变化 → 顺带触发重建）。本机无 Playwright，
未做浏览器实测。
→ 故本项是**失效键完整性**加固，不是缺陷修复；**行为零变化属预期，不是没生效。**

保留理由：加一个失效维度只会让重建变多、不会变少，行为风险为 0；且瓦片缓存本就把
`verticalRatio` 当全量失效维度（`noteLayerCache.ts:77`，注释明写"纵向比例改变 timeline 高度
→ pos 空间平移，需全量失效"），静态层与之不一致本身就是缺陷。
与 issue 29 问题1（漏加背景皮肤字段）同族：都是"加了新渲染维度，忘了扩失效比较链"—— **第二次**。

**回归网**：`RendererPerf.test.ts` 增 1 条结构护栏（改纵向比例必须重建）；注释里写明
"不是用户可见缺陷的回归测试"，避免后人误读。

### 5-b 播放 HUD 解耦：**证据否决，不做**

handoff §4 候选 5 第二条称"播放 HUD 寄生在画布组件 → 播放进度变化重渲画布组件"。读码后否决：

- `currentSeconds` 确实每帧变（`usePlaybackCoordinator.ts:94`）；
- 但同一 loop 的 `:99-100` `canvas.setScrollY(targetScrollY)` **同时**改了 `viewport.scrollY`，
  而 `viewport` 在 `renderChart` 依赖里（`FinalVirtualCanvas.tsx:679`）→ **播放时画布组件本来
  就要每帧重渲 + 每帧重绘**，抽走 HUD 省不掉任何一次；
- 能省的唯一场景「`currentSeconds` 变而 `scrollY` 不变」实际不存在：播放 RAF / seek（`:134-135`）/
  拖滚动条（`Editor.tsx:256,260`）三条路径都同时改这两个值。

→ 与候选 2 的 rAF 合帧同档：**证据否决**。**候选 5 至此收口。**

### 教训（记给后续，本轮栽的）

**「结构事实」≠「用户可见症状」。** 本轮把"缓存键少一个维度"（已证实）直接说成
"真 bug / 你能看见"（未证实），并据此把它排到候选 4 之前。用户未能复现。
→ 报告缺陷时，证据链要标清**最后一环是什么**：是"代码里有这个缺口"，还是"用户会看到错"。
只有后者才配叫 bug；前者只能叫**潜在陈旧 / 加固**，且必须如实写明"可观测性未证实"。
（与 handoff §5 第 3 条「别把看起来重复当缺陷，先验证」是同一原则的另一端：
那次是"看起来像缺陷"，这次是"看起来像症状"。）
