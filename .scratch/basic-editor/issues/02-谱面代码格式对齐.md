## Question

编辑器的谱面代码格式（`docs/plans/谱面代码规则文档.md` 定义的 Bestdori 风格 JSON 数组）与 **Bestdori 社区谱面上传/导入的真实格式** 是否一致？当前 `ChartConverter.ts` 的导出行格式是否需要调整才能与 Bestdori 互通？

请调研：
- `docs/plans/外部/sonolus-bandori-engine` 里的 `lib/src/bestdori/convert.ts`（`bestdoriToLevelData`）以及需求文档引用的 bestdori / BanGConverter 链接。
- Bestdori 谱面 JSON 的真实 schema（notes 结构、bpm 结构、滑条 connections 表示、skill 等字段）。
- 结论：内部编辑器格式是维持现状，还是需要对齐到一个"可导入 Bestdori / 可被 sonolus 引擎消费"的规范格式？这对"谱面代码生成精确性"是一个待决的事实。

## Answer（结论）

research 子代理对照 vendored `sonolus-bandori-engine/lib/src/bestdori/` 与 Bestdori 社区格式：

- **结论：编辑器内部格式与 Bestdori 高度兼容，无需重设计。** BPM（beat,bpm）、Single（beat,lane,flick）、Directional（beat,lane,direction,width）、Slide（connections[{beat,lane,hidden,flick}]）结构一致。
- **仅需导出侧做字段规范化**：`direction` 编辑器用 "Left"/"Right" 字符串，引擎映射为 -1/1 数字；`hidden`/`flick` 兼容。
- 需扩展的：skill 当前"暂不支持"（文档明示），要进 Bestdori 需确定映射。

**含义**：谱面代码生成/解析的"格式正确性"基本已达标；真正要做的是 **Bestdori 导入/导出适配器 + 字段规范化**，而非推倒格式。这直接影响 08 谱面代码编辑器的同步策略。

## 原则（issue 59 §1 定案，2026-09-09 记）

> **本编辑器不追求兼容 bestdori 的边界行为；只接受"有意义的谱面代码"。**

- 判断基准：bestdori 能"吃下"不等于我们要接受。**语义空洞、几乎无人这么写**的写法（例：`type:"Slide"` / `"Long"` 只剩 0/1 个 connection、`type` 改 `"Single"` 却留着 `connections`、滑条 / 长条端点 `hidden:true`）一律**报错拒绝**，**不做兼容、不做自动纠正、不静默修正**。
- **这不是"减少兼容"的借口**：Bestdori 的**一等类型**（`BPM` / `Single` / `Directional` / `Long` / `Slide` / `System`，见 vendored `sonolus-bandori-engine/lib/src/bestdori/convert.ts` 的 handler 表）必须完整接受，一个都不能因为"我们内部不常用"而拒收或丢弃。
- **`Long` 是 `Slide` 的别名，不是独立类型**：Bestdori 侧两者同构且共用 `longAndSlide` handler，本编辑器侧 `src/chart/types.ts` 也注明 SlideNote / LongNote 结构完全等价、画布全程并列处理。故代码里写 `type:"Long"` 合法 → 按 Slide 同一套规则校验 → 归一为内部 SlideNote；序列化方向不变（内部长条也写 `"Slide"`），往返不产生类型漂移。
- 未来所有"要不要兼容 bestdori"的判断，以这条为基准（含导入 / 导出适配器、`direction` 之类字段规范化）。
- 落地：`validateChartCode` 一次收集全部错误（`ValidationError[]`），调用方（谱面代码弹窗的应用 / 导入）**撞错整份拒**。
- 允许的例外只有"显式完整改写"：把整条 Slide 改成一条合法 `Single`（删 `connections` + 补 `beat`/`lane`）是**合法编辑**，不是兼容特例。
