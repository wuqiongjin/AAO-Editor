## Question

谱面画布在两类**离散布局变化**时，轨道宽度会"变窄一下"再恢复，导致谱面看起来跳动、且分不清哪个状态是对的：

1. 从其它 Tab 切换回工作台页时；
2. 展开/折叠左侧工具栏或右侧面板（`button` 收起/展开控件）时。

## 复现

- 打开工作台，展开/折叠任意侧栏，观察谱面轨道短暂变窄再回弹（画布已铺满但仍按旧宽度计算轨道尺寸）。
- 切到音频/Tab 再切回工作台，同样出现。

## 根因

渲染面的 `surface` 由 `ResizeObserver` 度量 `chartAreaRef` 而来（ADR-0006 §1）。issue 36 F2 为修复"连续窗口缩放"每帧 `setSurface` 造成的几何/缓冲反复重建卡顿，引入了 **150ms 尾随防抖**：

- 尾随防抖期间 `surface.w` 仍是**旧值**；
- `canvas` 的 CSS 已是 `width:100%`（新容器宽度），而轨道几何/`effectiveScale` 的 `fitWidth` 用的是**旧 `surface.w`**；
- 结果：在防抖窗口（约 150ms）内，轨道按旧宽度计算、又被拉伸到新画布宽度显示 → 轨道短暂变窄/错位，随后 `surface` 结算才恢复正确。

"连续窗口缩放"需要合并（issue 36 性能），但"折叠/展开侧栏、切回工作台"是**单次离散变化**，也会被塞进同一个尾随防抖 → 不该延迟却延迟了。用户"不确定哪个态是对的"正是因为短暂进入了 stale 态。

## 方案与实现

### 第一轮（2026-08-16）：前沿立即应用 + 尾随合并

`src/pages/Editor.tsx` 的 ResizeObserver effect：

- 一次布局突发的**首次**变化立即 `setSurface`（消除轨道宽度闪烁；也覆盖首次挂载）；
- 若度量在 150ms 内继续到来，则仅保留最后一次、等停止后再结算一次（合并连续 resize，性能与 issue 36 一致）。

### 第二轮（2026-08-16）：前沿跟随最新 + 持续流量变尾随合并

第一轮仍残留一两帧闪烁（切页）与"先变宽/变窄再回归"（折叠/展开侧栏）。根因：**一次离散突发常含多个 RO 回调**——

- 切页：`.app-page` 在 `display:none → block` 间切换，RO 会先报 `{0,0}` 再报实际宽；
- 折叠/展开侧栏：同帧内容布局可能让 chart 容器宽经历多个中间值。

旧逻辑只对突发**首个**回调前沿应用，其余回调在 150ms 内仅刷新 `lastValue` 不应用 → 尾随结算前轨道按陈旧宽度显示最长 150ms。

修订为 `src/pages/Editor.tsx`：

- `leading`：独立离散事件（与上一回调间隔 ≥ 100ms），或突发早期（密集且持续 < 150ms）的**每个新值**都立即 `commit` → 离散布局全程按最新宽度渲染，无陈旧帧（`{0,0}→实际宽`、侧栏多次改宽都会逐帧收敛到最终值）；
- `trailing`：仅当回调持续密集 ≥ 150ms（真正的连续窗口缩放）才定性为"流"，并入尾部结算一次（保留 issue 36 性能——连续拖动仅起始约 150ms 密集应用，此后合并且停止后结算最终值）。

## 验证

- `tsc --noEmit` 0 错误；vitest 180/180 通过（两轮均）。
- 逻辑推导（第二轮）：
  - 切走 tab：RO 报 `{0,0}`（`!dense` → 独立事件）立即应用（页面隐藏，不可见）；切回 tab 报实际宽，若间隔 <100ms 视为同一突发早期 → 立即应用实际宽 → 可见帧即正确宽度，无一两帧陈旧；
  - 折叠/展开侧栏：多次 RO 回调在突发早期均立即应用 → 轨道逐帧收敛到最终宽，不再"变宽再回归 150ms"；
  - 连续窗口缩放：起始约 150ms 密集逐条应用后转入尾随合并，拖动结束结算一次 → 未回归 issue 36 性能目标。

## Answer（结论）

**最终根因（第三轮，复现驱动）**：前两轮只处理了 `surface` **状态值的时序**（ResizeObserver 防抖/合并），但实测复现显示真正残留的闪烁来自另一层——**canvas 元素 CSS 尺寸与绘制内容脱节一帧**：

1. **切回工作台页（`{0,0}` 兜底拉伸）**：切走时 `.app-page` `display:none` → RO 报 `{0,0}`；若 `{0,0}` 被提交，`FinalVirtualCanvas` 会兜底成固定 `DEFAULT_SURFACE={750,900}`，而真实容器≠750 → `width:100%` 的 canvas 把 750 宽缓冲拉伸铺满真实宽度 → 轨道被横向拉宽一帧。**修复**：RO 侧直接跳过 0 尺寸事件（`Editor.tsx`），不提交、也不推进突发/尾随状态，保持上一真实 surface 直到重新测得真实尺寸 → 切回即正确。

2. **折叠/展开侧栏（canvas `width:100%` 造成的一帧错位）**：轨道水平居中 `trackStartX=(surface.w−轨道宽)/2` 由 `surface` 决定，而 `surface` 由 RO 异步测得、晚一帧才更新。canvas CSS 若用 `width:100%` 会在容器变宽瞬间立刻撑到新宽度，但 `surface`（决定轨道中心）还停在旧值 → 出现一帧「canvas 已变宽、轨道仍画在旧中心」的错位（轨道整体偏移，随后回归）。**修复**：canvas 的 CSS 尺寸改用 `surface` 的 px 值（`FinalVirtualCanvas.tsx`），使 DOM 尺寸与绘制内容始终同步；过渡那帧旧尺寸 canvas 由外层 flex 居中，轨道仍保持居中 → 无错位帧。稳态下 `surface` 恒等于容器宽，canvas 仍铺满容器，仅 0 一帧旧尺寸居中（黑色边距）。

这三轮均已落地。**前两轮的 RO 前沿/尾随逻辑保留**（用于连续窗口缩放的性能合并，issue 36），第三轮新增两处才能真正消除闪烁。

## 验证（第三轮，逐步像素级复现）

用 rAF 逐帧读取 canvas 缓冲像素，量测轨道左右缘（span）与宽度，确认修复前后差异：

- **面板折叠修复前**：`cssW 666, 轨道[168,453]`（一帧，canvas 已变宽但轨道未动）→ 下一帧 `轨道[273,558]`（回归居中）＝错位闪烁。
- **面板折叠修复后**：`cssW 666, 轨道[273,558]` 直接到位，**无中间错位帧**。
- **Tab 切换修复后**：切回工作台帧 `vis=1, cssW=666, 轨道[273,558]` 立即正确，无 `{0,0}`→750 拉伸、无陈旧帧。
- 轨道宽度全程恒定 285（用户缩放态，非 fitWidth 钳制态）；肉眼所见的"变宽变窄"实为上述错位/拉伸帧。

- `tsc --noEmit` 0 错误；vitest 180/180 通过。复现均在开发服务器实测（`https://irrihmhm08-5173.cnb.run/`）。

### Tab 切回：第三轮后的逐帧复核（2026-08-16）

针对用户反馈的「切回工作台仍有一两帧中间态」，再次逐帧像素级复核：

- 已确认整体架构：`AppShell.tsx` 四页**保活挂载**，切换只改父 div 的 `is-active`（`display:none/block`），canvas 从不重建；切回**不重跑** mount 序列（surface 初始/滚动锚定都只首屏一次）。
- 切回时 `surface` 被保留（RO 侧跳过 `{0,0}`），canvas CSS 随 `surface`，故首帧即正确。
- 逐帧 rAF 测量：切回的第一可见帧，内容行 Y、画布高、轨道 span 与「切走前」及「最终态」**三者完全一致**——无水平偏移、**无垂直滚动偏移**、无陈旧帧。即切回是**原子帧**，未测得可复现的中间态。
- 结论：当前代码下该中间态**无法复现**；若用户偶见一两帧轻闪，更可能是 `display:none→block` 触发的浏览器合成层切换的一帧微闪（合成层级、非渲染逻辑可控、随环境而异），影响很小。按用户判据「不认定为问题则不必处理」，本次不再改动；如后续仍明显，可考虑让非激活页改用 `visibility:hidden` 保持合成（有性能取舍）。
