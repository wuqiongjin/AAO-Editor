# 215 · 窗口切回前台谱面下落加速与卡顿

Type: bug
Status: resolved

## 来源

用户反馈：
谱面画布处于播放中时，如果前台有其它窗口，通过切换窗口切换回谱面画布时，有概率出现：谱面突然由"慢"到"快"加速下落的一个过程（也能感觉到卡顿）。

## 用户确认的复现条件（2026-11-04 / 2026-11-06 对齐）

1. **时钟无关性**：有音频文件播放 / 无音频文件（纯合成时间线）均能复现；
2. **遮挡窗口特征**：不同应用窗口遮挡表现差异明显——普通 Win32/GDI 应用（如 `notepad--`）遮挡**不会复现**；具备 GPU 硬件加速的 DirectComposition/D3D11 窗口（如 `QQ NT` 聊天窗口）遮挡**能复现**；
3. **窗口遮挡与切换方式**：AAO Editor 全程**未被最小化**，且与 QQ 窗口处于**半遮挡**状态；使用 `Alt+Tab` 快速切换，**窗口切换速度越快，触发概率越高、表现越明显**；
4. **运行环境**：开发环境（`npm run electron:dev`）与已打包客户端均一致，屏幕物理刷新率为 60Hz（`1920x1080 @ 60Hz`，Windows `125%` 缩放 `devicePixelRatio = 1.25`，`NVIDIA GeForce GTX 1650`）。

## 四轮排查演进与根因拆解

### 第一轮：Occlusion 节流假设缺乏实测支撑（Commit `234afaf5`，已回退）
- 早期假设 Chromium 遮挡计算直接挂起了局部半遮挡窗口。但初期在无真实遮挡物、未复现物理掉帧的情况下仅做了粗粒度开关测试，未能触及真正病灶。

### 第二轮：追帧限速反而引入次生“由慢到快圆滑过渡感”
- 在 `AudioEngine.getSeconds` 中引入了 `isDroppedFrameHitch` 追帧限速（将单帧步幅压制为 `nominalFrameSec * 1.25`），试图阻止掉帧后的暴冲。
- **用户实测反馈**：
  > "切换完之后，还是会卡顿一下，然后此时音符继续往下落的过程可能没有之前那么突兀了，而是稍微圆滑过渡到正常下落的感觉(但是绝对不是一直保持正常下落播放的效果)。我希望不管怎么切换，都一直保持正常播放。"
- 限速器将突发掉帧转换为 15 帧（约 250ms）的渐进爬升/衰减过程，肉眼直接感知为明显的“加速度过渡感”。

### 第三轮：假想合成环境与真机脱节
- 上一任 Agent 编写了单进程内开子窗口模拟 QQ 的测试脚本（`main-diag-hook.cjs`），测得“0 丢帧”，误以为是 Chromium 原生遮挡特性（`CalculateNativeWinOcclusion`）所致。
- 但用户真机实测窗口处于**半遮挡**状态（Chromium 原生遮挡检测只在 100% 完全遮挡时才会生效），用户反馈“实测没有任何变化”。

### 第四轮：真机 HUD 遥测捕获物理真相，精准锁定 DWM 硬件图层争抢

#### 1. 真实物理数据捕获
通过在播放主循环中注入原生 DOM 遥测 HUD，用户在真实桌面与 QQ NT 进行快速 `Alt+Tab` 切换时，捕获到了核心数据：
- **`Hitches (83 total)`**：短时间内触发密集丢帧；
- **精准的 VSync 整数倍停顿**：
  - `33.1ms / 33.3ms`：精确等于 2 个 VSync 周期（$16.67\text{ms} \times 2$，丢 1 帧）
  - `49.9ms`：精确等于 3 个 VSync 周期（$16.67\text{ms} \times 3$，丢 2 帧）
  - `66.4ms / 66.7ms`：精确等于 4 个 VSync 周期（$16.67\text{ms} \times 4$，丢 3 帧）
  - 峰值超过 100ms（连续丢失 6 帧以上）；
- **位移跳变与速度阶梯**：
  - 正常 60Hz 每帧下落 `7.3px`；
  - 丢 3 帧（66.7ms）时，画面停滞不动 4 帧时间，随后一帧跳跃 `29.3px`，接着递减至 `22.0px`、`14.7px`，最后回落至 `7.3px`。
  - **停滞 $\to$ 暴冲 29px $\to$ 逐步回落到 7.3px** 的剧烈跳跃，在大脑视觉残留中直接体现为“先卡顿，然后由慢到快加速过渡”。

#### 2. 底层物理根因：Windows DWM DirectComposition 硬件多平面图层（MPO）竞争
- **为什么 Notepad-- 不会，而 QQ NT 必然复现**：
  - Notepad-- 是传统 Win32/GDI 程序，没有 DirectComposition 视觉树和 D3D11 交换链，DWM 仅做基本桌面重定向合成；
  - QQ NT 与 AAO Editor 同为 Chromium 架构，各自持有独立的 DirectComposition 视觉树与 D3D11 交换链。
  - 在 Windows 10/11 + NVIDIA 驱动下，DWM 默认使用多平面叠加（MPO / Hardware Overlays）。两个硬件图层在前后台快速切换时，显卡驱动与 DWM 在硬件平面所有权交接过程中，**会短暂挂起/阻塞正在切出或切入窗口的 `IDXGISwapChain::Present` 调用**，造成合成器向上游渲染器停发 2~4 个周期的 VSync 信号。

## 终极修复方案

### 1. Windows 平台禁用 DirectComposition（`electron/main.cjs`）
在主进程启动前注入命令行开关：
```js
// issue 215：Windows 平台禁用 DirectComposition，避免与 QQ NT 等 D3D11 硬件加速应用在 Alt+Tab 快速切换时
// 因 Windows DWM 多平面叠加层（MPO / Hardware Overlays）图层抢占与重建导致 IDXGISwapChain::Present 阻塞、丢帧与视觉跳变。
// 同时禁用原生窗口遮挡计算与后台节流，保证窗口在后台或半遮挡切换时合成管线持续平稳。
if (process.platform === 'win32' && app && app.commandLine && typeof app.commandLine.appendSwitch === 'function') {
    app.commandLine.appendSwitch('disable-direct-composition');
    app.commandLine.appendSwitch('disable-features', 'CalculateNativeWinOcclusion,IntensiveWakeUpThrottling');
    app.commandLine.appendSwitch('disable-backgrounding-occluded-windows');
    app.commandLine.appendSwitch('disable-renderer-backgrounding');
    app.commandLine.appendSwitch('disable-background-timer-throttling');
}
```
并在 `BrowserWindow` 的 `webPreferences` 中配置 `backgroundThrottling: false`。

- **工作机制**：
  Chromium 依然 100% 使用 NVIDIA GTX 1650 显卡硬件进行 D3D11/ANGLE 光栅化与着色，但与 DWM 的交付方式退回到标准翻转模型（Flip Model / 窗口重定向），不再参与 DWM MPO 硬件图层竞争。
- **效果**：
  彻底消除两个 GPU 窗口在 Alt+Tab 交接时的 `Present` 挂起，丢帧数彻底归零。

### 2. 彻底清理上一任 Agent 假想防御与补偿代码（遵从 Ponytail 极简原则）
- **回退 `AudioEngine.ts`**：
  恢复原始极简的时钟读取实现（纯双时钟，无 70 行冗余锁相环、滤波与斜率限制），无需为不存在的掉帧做时钟补偿；
- **回退 `FinalVirtualCanvas.tsx` / `simPlayback.ts` / `usePlaybackCoordinator.ts`**：
  移除无谓的跨帧 ref 缓存、时钟时间戳强穿透及临时调试 HUD；
- **回退渲染管线**：
  移除 `staticLayerCache.ts` 复杂的双缓冲条带与 `noteLayerCache.ts` 的 4ms 早期排水补偿。
