# 64 · 谱面工程自动落盘失效（刷新页面丢内容）

Type: task
Status: resolved（2026-09-09 实现落地，浏览器验收待用户）
Blocked by:

## 来源

issue 55/56 验收后用户复报的遗留问题 #5（2026-09-09）：「谱面画布的内容不会临时保存了，导致刷新页面就丢了」。违反 ADR-0005 §6「编辑**即自动保存**（防抖 ~800ms），重开页面需恢复」。

## 根因（已定位）

`src/chart/project/useChartProjectPersistence.ts` 把 **merger 的销毁挂在了"每次 notes 变化都要重跑"的 effect 的 cleanup 上**：

```
useEffect(() => {
  merger.schedule(buildProject());          // merger = 本次 render 顶部捕获的实例
  return () => { mergerRef.current.destroy(); mergerRef.current = null; };
}, [notes, durationSeconds, debounceMs]);
```

React 的时序是「render（捕获旧实例）→ 上一轮 cleanup（destroy + 置 null）→ 本轮 effect」，于是：

1. render #2 顶部 `merger = A`（此刻 ref 还是 A）；
2. cleanup of effect #1 → `A.destroy()`、`ref = null`；
3. effect #2 执行 `A.schedule(...)` → `ChartProjectPersistenceMerger.schedule` 开头 `if (this.destroyed) return` → **静默丢弃**。

→ **第一次编辑之后，防抖落盘永远不再发生**。之后每次 commit 都是「render 里新建实例 → 同一轮 cleanup 立刻销毁它 → effect 打在死实例上」。（音频那条 `saveNow()` 路径之所以看起来还活着，只是因为导入音频通常不改 `notes` → 上一轮 deps effect 不重跑、cleanup 不触发，恰好落在新建且未销毁的实例上；一旦编辑过音符，它同样会打在死实例上。）恢复路径（挂载 `store.get()`）本身是好的，所以现象正是"改完刷新就丢"。

同一时序坑在 2026-09-02 的 `useSurfaceSize`（commit 6331269 "tmp修复部分bug"）里已经用「cleanup 不置 null + effect 内 lazy 重建/判 destroyed」修过一次，本 hook 漏了。

## 修法

**销毁只属于"真正卸载"，与"依赖变化"彻底分开**；merger 一律经 lazy getter 取（被销毁过就重建）——与 `useSurfaceSize` 同一套修法：

| 文件 | 改动 |
| --- | --- |
| `src/chart/project/ChartProjectPersistenceMerger.ts` | 新增 `get isDestroyed()`（调用方据此判定实例是否还可用；`destroy` 语义不变） |
| `src/chart/project/useChartProjectPersistence.ts` | ① render 顶部**不再捕获** merger，改 `ensureMerger()`：ref 为空**或已 destroyed** → 新建；② 防抖 effect 去掉 cleanup（timer 重置本就由 `schedule` 内部 `clearTimeout` 负责），卸载单独一条 effect 走 `flush()`（ADR-0005 §6"切页时写入"）；③ `saveNow` 也走 `ensureMerger()` |

StrictMode 双挂载：卸载只做 `flush`（不销毁）→ 第二轮继续用同一实例，不再有"打在已销毁对象上"的窗口。

## 验收

- 单测：`ChartProjectPersistenceMerger.test.ts` 补 `isDestroyed` 口径（销毁后 schedule/saveNow 均无副作用）；新增 `ChartProjectPersistence.test.ts` 源级回归锁——本 hook 里**不得**再出现 `.destroy(` / `mergerRef.current = null`，merger 必须经 `ensureMerger()` 取用。
- 浏览器实测：放几个音符 → 等 ~1s → **刷新** → 内容仍在（画布 + 谱面代码 + 谱面时长）。
- 回归：导入/清除音频后刷新仍在；「切到别的页面再回工作台」不丢；IndexedDB `bangdream.chartproject` 里 `notes` 随编辑更新。

## 第二轮（用户选方案 B：还要收掉"编辑完立刻刷新"的窗口）

修完上面那处后用户复测仍丢内容，补挖出**第二个成因**，并落地 B 方案：

**成因 2 · 初始空谱面回写**：挂载那一次 deps effect 会用**初始空 `notes`** 排一次保存；恢复读（`store.get()`）若比防抖窗口慢（Electron 文件后端要读 `audio.bin`、大谱面 JSON 也大），空谱面先落盘 → 已存工程被覆盖 → 现象同样是"刷新就丢"。
**成因 3 · 卸载 flush 反噬**：第一轮把"卸载前 flush"挂在 `useEffect(() => () => flush(...), [])` 上，但 **StrictMode 双挂载会在挂载瞬间就跑一次 cleanup**，此时 `notes` 还是初始空谱面 → 恰好制造成因 2。且应用壳五页保活挂载（issue 28），"切页"根本不触发 Editor 卸载，这条路径既危险又没用。

| 文件 | 改动 |
| --- | --- |
| `useChartProjectPersistence.ts` | ① 新增 `restoreSettledRef`（`store.get()` 结算后才置 true），**未落地前一律不落盘**（`schedule` / `flush` 两处都守）；② 卸载 flush **删除**，改为 `visibilitychange`(hidden) + `pagehide` 强制 `flush`——刷新/关标签/切后台都覆盖，且不会有 StrictMode 空谱面回写；③ **防抖保持 800ms 不动**（ADR-0005 §6）：缩短它只是按比例放大 IDB/文件写入次数，密集谱面不划算，真正会丢数据的场景已由隐藏 flush 兜住 |

## 第三轮（真正的主因：**恢复在 StrictMode 下被整轮跳过**）

前两轮修完用户复测仍"刷新后谱面 + 音频全丢"，重新从恢复端查，定位到**最致命的一处**——它让整条持久化链路在 dev 下从头到尾都是死的：

```
useEffect(() => {
  let cancelled = false;
  store.get().then(p => { if (cancelled) return; onRestore(p); });
  return () => { cancelled = true; };      // ← 元凶
}, []);
```

`main.tsx` 开了 `StrictMode`，React 对 effect 跑 **setup → cleanup → setup**：
1. setup#1 发起 `store.get()`（闭包捕获 `cancelled=false`）；
2. cleanup#1 把 `cancelled` 置 `true`；
3. setup#2 因 `restoredRef` 已置位**直接 return，不再发起第二次 get()**；
4. promise 落地 → 看到 `cancelled === true` → **恢复被丢弃**。

叠加第二轮引入的 `restoreSettledRef`（`.finally` 里判 `!cancelled` 才置位）→ 该标志**永远为 false** → 自动保存也被永久关掉。
即：**什么都存不进去，也什么都读不出来**，现象就是"刷新必丢"。

> 这处自 issue 46（2026-08-29 抽 hook）起就存在——当时用 build 产物验收（build 不双调用 effect）所以没暴露。

| 文件 | 改动 |
| --- | --- |
| `useChartProjectPersistence.ts` | ① 恢复 effect **去掉 cleanup 取消**（一次性挂载读取，晚到的 promise 无害）；`restoreSettledRef` 在 `.finally` **无条件置位**；② 自动保存 deps 补 `audioName` / `audioBlob`（导入音频不改 notes；且 `AudioSession.importAudio` 的 `persistNow()` 在 `emit()` 之前调用、那时 ref 还是旧 null ⇒ 只有靠 deps 再排一次才能真带上音频落盘）；③ 落盘失败 / 读取失败**不再静默**，改 `console.warn`（静默吞异常是这个问题藏了一个月的原因） |

## Comments

- 2026-09-09 实现：修法如上表，未新增 `cancel()`（结算路径改用 `flush`，与 ADR-0005 §6 的"切页时写入"直接对齐，`cancel` 会是无人调用的死 API）。
- 2026-09-09 第二轮（方案 B）：补成因 2 / 成因 3，见上节。
- 2026-09-09 第三轮：补**主因**（StrictMode 下恢复被 cleanup 取消）+ 音频字段漏进 deps + 静默吞异常，见上节。源级回归锁 `ChartProjectPersistence.test.ts` 增至 8 例（新增"不得出现 cancelled""audioName/audioBlob 必须在 deps 里"）。tsc 0 / vitest 696 全绿。浏览器验收待用户。
- 教训：**「一次性挂载读取」的 effect 不要写 cleanup 取消**——StrictMode 的 setup→cleanup→setup 会让"取消"生效、而第二次 setup 又因去重标志早退，请求再也不会重发。同类写法在别处也要警惕。
