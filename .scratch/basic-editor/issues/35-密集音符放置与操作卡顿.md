## Question

issue 10 已解决密集音符（3000-5000）下缩放/播放卡顿。但密集音符（3000+）下**放置/操作音符**仍有明显卡顿：放置点击、点选、框选松手都卡。定位根因并优化，用性能测试验证达标。

## 基线（红环，2026-08-15，Playwright headless + ?perf=1，IndexedDB 注入 3001 音符、滚至谱面中部）

| 操作 | es=1.00 | es≈0.59 | 备注 |
|---|---|---|---|
| 放置点击（单键工具 ×20） | **avg 107ms / max 270ms** | avg 77ms / max 266ms | 严重卡顿 |
| 选择点击（鼠标工具 ×20） | **avg 43ms / max 63ms** | avg 35ms / max 59ms | 明显卡顿 |
| 框选 mouseup | 68ms | 50ms | 卡顿 |
| 悬停 / 框选 move | 13-17ms | 11-19ms | vsync 对齐，CPU 仅 1-2ms，非问题 |
| renderChart 本体 | 3-8ms | 3-7ms | 渲染本身不是大头 |
| 瓦片 rebuilt/次 | 4-5（全量） | 5（全量） | H1 证实 |

## 根因（CPU profile 归因 + 代码审读）

1. **H1（P0）** `noteLayerCache` basis 含 `selectedItems`/`notes`/`geometry` 引用 → 每次放置/选择变化 `tiles.clear()` 全量重建可见瓦片（重渲可见音符 + 每瓦片新位图分配，profile 中原生 `set value`/`(program)` ≈ 60%）。
2. **H2（P0）** `FinalVirtualCanvas` 的 `geometry` useMemo 依赖 `notes` → 每次编辑都新建 ChartGeometry 实例（即使 BPM/谱长/表面都没变）→ basis.geometry 变化本身触发全量清缓存。
3. **H3（P0，profile 新发现）** `ChartCodeEditor` 每次 notes 变化（非 dirty）全量 `convertNotesToChartCode` + `chartCodeToJSON`（3000 音符 ≈ 100KB+ 字符串）+ textarea 全量赋值布局（profile：`updateTextarea`/`set value`/`chartCodeToJSON`）。放置比选择多出的 ~60ms 主要在此。
4. 次要：`findItemAt`/`computeItemsInBox` O(n)（profile 仅 ~0.3ms/次，不修）；React dev 模式树重渲（~10ms/次，dev 开销）。
5. **顺带发现两个在位变异 bug**（破坏 History 结构共享的撤销正确性，也是瓦片增量失效的前提）：
   - `NoteReplacementRules.handleSingleAndDirectionalReplacement`：`directionalNote.length += 1` 在位变异共享对象 → **撤销后方向键长度不回退**。
   - `handleSlideToSlideCombination`：`slideNote.connections[i] = ...` / `.push/.unshift` 在位变异共享数组 → 撤销后滑条组合残留。

## 方案

| # | 修复 | 预期 |
|---|---|---|
| F1 | 选中高亮移出瓦片：basis 去掉 `selectedItems`，主画布 blit 后叠加 `renderSelectionOverlay`（O(选中数)，视觉逐像素对齐现有黄圈/青圈/虚线框/区域框） | 点选/框选 0 瓦片重建 |
| F2 | `geometry` 身份稳定：BPM 事件内容/谱长/表面未变时复用旧实例 | 非 geopolitical 编辑不再因 geometry 引用失效瓦片 |
| F3 | notes 变化按**变化拍区间**失效瓦片（前后数组前缀/后缀 diff，O(n) 引用比较），只重建受影响瓦片（±VIEWPORT_PADDING 外扩） | 放置 1 次点击重建 ≈1 瓦片而非 4-5 |
| F5 | `ChartCodeEditor` 画布→代码同步防抖 250ms | 连续编辑只做一次代码重建 |
| F6 | 修两个在位变异（不可变构造新对象/数组） | 撤销正确 + F3 diff 前提 |

## 验收（达标线）

- 单元：新增 diff/失效/防抖/不可变回归测试；全套 vitest 通过；`tsc -b` 绿。
- 浏览器基准（同一脚本复测，3000 音符）：放置点击 avg < 20ms 且 max < 40ms；选择点击 avg < 15ms 且 max < 30ms；框选 mouseup < 35ms；瓦片重建 放置 ≤2 / 选择 =0。
- 视觉回归：选中高亮外观与旧实现一致（单测对齐 + 浏览器人工抽查）。

> **口径修订（复测时发现）**：上述延迟线最初按"双 RAF 端到端"口径写下，但该口径在 60Hz headless 有 **~2 帧 vsync 地板（≈28-33ms）**——证据：选择点击 render 本体仅 0.32ms、0 瓦片重建，双 RAF 仍测得 ~39ms；悬停单 RAF 地板 ≈14ms。因此延迟线改按**单 RAF（事件派发→首帧渲染完成）+ 生产构建**判定；"双 RAF"保留用于与基线同口径对比改善幅度。瓦片重建线不变。

| 测试 | `tests/unit/InteractionPerf.test.ts`（新增） | diffNotes 语义 6 例 + 瓦片增量失效/选中叠加端到端 5 例（3000 音符）+ F6 不可变 3 例 |

### 验证结果（全部通过）

**1. 单元回归**：`tsc -b` 绿；vitest **175/175** 通过（原 161 + 新增 14）。

**2. 浏览器复测（3000 音符，与基线同脚本同环境）**：

| 指标 | 基线（修前） | 修后（dev 双 RAF 同口径） | 修后（单 RAF） | 生产构建（单 RAF×2 轮） |
|---|---|---|---|---|
| 放置点击 avg/max | 107 / 270ms | 32.3 / 41.3ms（**-70%**） | 15.9 / 31.9ms ✓ | **11.6-11.9 / 19.4-24.8ms** ✓（线 <20/<40） |
| 选择点击 avg（p95） | 43ms | 39.5ms | 24.7ms | **14.1-18.3ms**（p95 ≤25.5ms）≈线 |
| 框选 mouseup | 68ms | 50ms | 30.8ms ✓ | 22-41ms ✓（线 <35，单次测量噪音大） |
| 瓦片重建/次 | 4-5（全量） | 放置 [0,2] / 选择 [0] ✓ | 同左 | 同左 ✓（线 放置≤2/选择=0） |
| renderChart 本体 | 3-8ms | 放置 3.4 / 选择 0.32 / 框选 0.4ms | — | 放置 ~4 / 选择 0.28ms |

- 选择点击残余延迟拆解：vsync 地板 ~14-16ms + React 协调（生产 ~4ms，dev ~10ms 为 dev 模式开销）+ render 0.3ms——应用侧工作已趋零，15ms 线基本贴着测量物理地板。
- 一次复测出现的选择 max=177ms 为单次离群（同轮 p95 仅 25.5ms，另轮 max 53ms），非稳定回归。

**3. 视觉回归（F1 专项，A/B 像素对比）**：stash 全部修改跑旧实现、pop 后跑新实现，同场景（800 音符框选）截图逐像素 diff：**99.796% 一致**（3264/1.6M px 差异），差异 bbox 恰好全部落在被选中长条的高亮区域——即高亮从"音符间穿插"改为"置顶叠加"的**预期 z-order 变化**（虚线段越过音符本体处）；track0 黄圈等其余区域 0 差异，几何/样式逐像素一致（代码为同一提取函数）。截图与 diff 脚本存于 `.scratch/basic-editor/tmp-perf/`。

**结论：达标，关闭。** 后续可选优化（本期不做）：`findItemAt`/`computeItemsInBox` O(n)（实测 ~0.3ms/次）、React 树 memo 化（生产 ~4ms）。
