# 132 · 撤销栈内存无上限（文本 + notes 两处）

Type: chore
Status: open

## 来源

issue 102 实测 / 评审时暴露的派生问题；用户 2026-09-21 要求立票跟踪，**本次不做**。

## 症状

撤销栈（`src/chart/editing/History.ts`）**没有任何容量上限**，快照只增不减，且两处都在用：

| 栈 | 谁在压 | 单份快照代价 | 触发密度 |
| --- | --- | --- | --- |
| **文本栈** | 谱面代码弹窗：每输入一个字 / 每次程序化改动 | **整份代码文本**：5000 音符 ≈ 364KB、1w ≈ 735KB | 每敲一个字一次 → 连打百字即几十 MB |
| **notes 栈** | `EditingProvider`：放置 / 删除 / 移动 / 粘贴 / 应用代码等每次编辑 | **整份音符指针数组**（8B × 音符数；5000 音符 ≈ 40KB、1w ≈ 80KB）+ 被改音符的新对象（未改音符靠结构共享复用引用，不复制本体） | 一次编辑一次 → 慢得多，但长会话、大谱面同样累积 |

两处都只在「弹窗关闭 / `resetNotes`」时才整体释放。表现为内存持续上涨 → GC 压力 → 越用越卡，
极端情况 OOM。notes 栈靠结构共享比文本栈便宜约一个数量级，但**同一类问题**（无上限 + 只增不减）。

## 根因

`pushHistory` / `pushHistoryIfChanged` 只做「压栈 + 截断 redo 分支」，没有容量维度；
文本栈无法结构共享（每份快照都是一整个字符串），notes 栈虽结构共享却仍每步复制整份指针数组。

## 修法（待定，未拍板）

- ① 给 `History` 加**可选容量上限**（如 `pushHistoryCapped(state, item, cap)`：超出丢最旧的），
  两处各按自己的代价定 N（文本栈 N 小、notes 栈 N 大）。——**会改「能撤销多少步」的语义**，需 grill。
- ② 文本栈改存**增量 patch**（撤销 = 反向应用）——最省内存，实现复杂度高。
- ③ notes 栈若只想省数组：快照改存「diff + 长度」，代价是要重写撤销/重做，暂不推荐。
动手前先 grill 拍板（撤销深度 vs 复杂度）。

## 锁测

1. `tests/unit/chart/editing/History.test.ts` 补容量用例：上限生效、超出丢最旧、上限内语义不变。
2. 行为等价性（照 issue 70「不变量逐条锁」口径）：
   - 文本栈：连续输入 N+1 次后仍能撤销到「最近 N 步」，不抛错、不产生空栈；
   - notes 栈：连续编辑 N+1 次后撤销/重做逐条仍对齐（含 `pushHistoryIfChanged` 的去重语义不被破坏）。
3. `tests/perf/`：断言「连打 K 次 / 连续编辑 K 次后栈长度 ≤ 上限」（测栈长度，不测真实 MB，
   避免机器差异）。

## 附带（同模块，做容量上限时顺手）

文本栈用的是 `pushHistory`，**没有** notes 侧 `pushHistoryIfChanged` 的「内容没变就不占栈位」去重
（`notesEqual` 那套语义的文本版 = 字符串相等）。表现为：改回去又改回来会各占一步，
Ctrl+Z 要多按几次才退得掉真实改动（issue 57 bug4 的同款毛病在文本侧的残留）。

## 排查过的其它项（**不入本票**）

- 只有这两处撤销栈（`History` 的消费者 = `EditingProvider` 的 notes 栈 + 弹窗的文本栈），无第三处。
- 文本栈与 notes 栈互不相通、应用后文本栈重置、关闭弹窗丢弃草稿、换档重建草稿 ——
  都是 issue 37 / 59 的**单向同步定案**，不是缺陷，不动。
- 段参数（缓动 / 曲线配置）与选中态、剪贴板不入撤销栈 —— ADR-0009「参数随行、点集为真相」
  与既有定案；若将来要「撤销一次缓动调整」属新能力，另开 feature 票。
