# 249 · 谱面滚动条与 Playbar 往返拖动卡顿

Type: bug
Status: resolved

## 来源与症状

用户 2026-11-23 报告原生滑块大幅往返时，谱面画布与 Playbar 偶发停住，随后追上滑块。同日要求先建票，再修复和验证。暂停态拖动仍应设定播放头并同步画布，见 ADR-0004。

2026-11-24 用户复测 `git diff --cached` 后重新打开：
1. 原生滚动条高倍拖动较基线好转，但**来回拖动 Playbar 进度条依然严重卡顿**（缩放越高越明显）；
2. **谱面画布正常播放出现回退**：在 `npm run build` + `npm run electron:dev`、窗口最大化、约 200% 缩放下切到 `Retribution ~ Cycle of Redemption ~` 直接正常播放，肉眼可感到部分段落偶发掉帧，明显不如基线（`488bd3b6`）。

## 根因

### 1. 滚动条与 Playbar 共有的主线程瓶颈（高倍放大）
暂停态大幅往返（无论是原生滚动条还是 Playbar 进度条）进入未缓存的冷区时，`FinalVirtualCanvas` 的 `useLayoutEffect` 在提交期间调用 `noteLayerCache.draw()` 同步执行 `renderTile()`（含完整 SP 滑条扫描线光栅化 `rasterBandRuns`）。300% 下单块瓦片缓冲约 12.3 MiB、64 MiB 缓存仅容约 5 块，往返拖出几屏即频繁淘汰重建，单帧主线程阻塞可达 60–150 ms；由于 Playbar DOM 与画布共用主线程，表现为两者一起卡顿。

Playbar 链路另有额外放大：
- `PlayBar.tsx` 的 `handlePointerMove` 未按 rAF 合帧；
- `usePlaybackCoordinator.ts` 的 `seek()` 在暂停态末尾无条件调用 `stopPlayback()`，重复执行一次 `engine.pause` / `setCurrentSeconds` / `setScrollY` / `scrollTop` 写入。

### 2. 原生滚动条的合成/GPU 停顿（待剥离 Portal 后复核）
Windows Electron 在基线（`488bd3b6`）100% 缩放下曾录到 299–379 ms 的更新空档（Chromium 等待前一帧 GPU 栅格、合成线程继续推进滑块）。后续慢拖定位到冷瓦片预览的多矩形 `ctx.clip()` 触发 Skia 两次约 57 / 60 ms 的驱动着色器链接与约 22 ms 路径栅格，合并或省略全视口裁切后系统显示间隔降至 33.2 ms。见[复现与对照](../../diagnostics/scroll-drag-20261123/README.md)。

### 3. [⚠️ 错误方向警示] 首轮 `git diff --cached` 方案中已证实走偏的部分（勿沿用）

> **警示**：以下 3 项改动为首轮尝试的错误方向，会直接引入播放掉帧或漏修 Playbar，后续实现**应废弃**，不要以它们为前提继续打补丁：

1. **❌ Portal 拆层 + 全屏透明覆盖层压在 `<canvas>` 上方**（`WorkspacePage.tsx/css`、`FinalVirtualCanvas.tsx`）：
   - 首轮把 `<canvas>` 拆到 `.ws-chart-paint`，同时把 `z-index: 1` 的全屏滚动宿主 `.ws-chart-scroll` 与全屏 `will-change: transform` 透明层 `.ws-chart-viewport` 叠压在 `<canvas>` 上方，并移除了 `<canvas>` 的 `backgroundColor: '#000000'` 与 `z-index: 10`。
   - **已证实的播放回退**：播放循环每 33 ms 同步一次 `container.scrollTop`，在画布上方触发频繁局部合成提交（`STATE_PRESENTED_PARTIAL`）。
     - 100% 前台播放（10s）：`STATE_PRESENTED_PARTIAL` 从基线 **5 次**暴涨至 **233 次**，管线延迟 P95 从 **18.2 ms** 恶化至 **49.9 ms**，桌面呈现最大间隔从 **16.8 ms** 恶化至 **33.3 ms**。
     - `Retribution ~ Cycle of Redemption ~` 200% 最大化播放（`mid_90s` 15s）：基线 `STATE_PRESENTED_PARTIAL = 0`、`pipeLat p50 = 16.6 ms`、`presentedAll max = 17.5 ms`；首轮版本暴涨至 **`STATE_PRESENTED_PARTIAL = 759`、`pipeLat p50 = 33.2 ms`、`presentedAll max = 33.2 ms`**（与用户肉眼观测的偶发掉帧吻合）。
2. **❌ 仅对 `source === 'scrollbar'` 开启冷区延迟预览、刻意排除 Playbar `seek()`**：
   - 导致 300% 来回拖动 Playbar 仍走同步 `renderTile()`：`月胧-Test1` 300% 录到 10 次主线程长任务（最长 68 ms，共 578 ms，刷新率跌至 43.2 fps）；`Retribution` 300% 录到 8 次长任务（最长 148.2 ms，共 983 ms，`STATE_DROPPED = 54`）。
3. **❌ `bandRasters` 的 `JSON.stringify(input)` 缓存与 `deleteTile` 同步 `canvas.width = 0`**：
   - 属于为旧同步路径打的补丁，在拖拽统一走延迟预览后收益极低，反而在 300% 播放高频淘汰瓦片时叠加提交/释放抖动（`249-merged-clip-3-230344` 播放 `TimerFire` 达 45.0 ms、桌面最大间隔 66.5 ms）。

## 最终实现方案

1. **废弃首轮 Portal 拆层与辅助补丁**，保持基线顶层 `<canvas>` DOM 结构与播放合成路径零变化；
2. **统一交互式冷区延迟预览**：`FinalVirtualCanvas.setScrollY(scrollY, source?: 'scrollbar' | 'playbar')` 同时接收滚动条（`useChartViewSession.onScrollbarScroll`）与 PlayBar 拖拽（`usePlaybackCoordinator.setScrubbing` + `seek()`）的交互来源；`noteLayerCache` 在暂停态交互定位进入冷区时仅绘制音符与滑条几何填充（`previewSlideBands`），合并相邻冷瓦片裁切矩形（全视口时跳过 `ctx.clip()`），停稳 80 ms 且经过两次 `requestAnimationFrame` 后异步分片光栅精细瓦片并经 `onScrollTileReady` 重绘；程序化单次定位（双击时间码 / 标记点跳转）仍当帧同步绘制精细瓦片；
3. **消除 PlayBar 拖动冗余开销**：`PlayBar.tsx` 拖拽期间按 `requestAnimationFrame` 合流 `pointerMove`（`pointerDown` 即时定位，`pointerUp`/`pointerCancel` 先冲洗待定定位再退出拖拽态）；`usePlaybackCoordinator.seek()` 统一登记 `onProgrammaticScroll` 回声并在已暂停态跳过冗余 `stopPlayback()` 二次同步。

## Answer

废弃首轮 Portal 拆层与多余缓存补丁，恢复基线顶层 `<canvas>` DOM 保证正常播放零回退；将「冷区几何预览 + 相邻范围合并裁切 + 停稳双 rAF 异步分片补建精细瓦片」统一接入滚动条与 `PlayBar` 拖拽，并为 `PlayBar` 拖动补齐 `requestAnimationFrame` 合流、暂停态 `seek()` 跳过冗余 `stopPlayback()` 及统一登记 `scrollTop` 回声。全量测试、静态锁与 `Retribution` 200% 播放 / 300% 拖动 Electron 实测均通过。
