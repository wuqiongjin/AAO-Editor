# 102 · 完整谱面代码弹窗打开卡一会（700~800 音符即卡，3000~5000 更久）

Type: bug
Status: resolved

## 来源

用户 2026-09-12 复报第七批 #3e。

## 症状

工具栏「谱面代码」打开完整谱面代码时，初始加载卡一会；700~800 音符的正常谱面就会卡，3000~5000 音符卡得更久。

## 根因

打开与击键都在主线程同步跑全量重活：

1. 打开 = `convertNotesToChartCode`（全谱 O(n) 遍历 + beat 排序，`src/chart/editing/ChartConverter.ts:54-87`）→ `JSON.stringify(_, null, 4)`（`:213-215`）→ 全量文本一次性塞进受控 `<textarea>` 并同步渲染（`ChartCodeEditorModal.tsx:89-102,74-80`）；无延迟填充、无分片、无虚拟化、无 Worker。
2. **每次击键**全量 `JSON.parse` + 逐条结构校验 `validateChartCode`（`ChartCodeEditorModal.tsx:108-115,152-168`；`ChartConverter.ts:375-503`）→ 大谱面打字同样卡（与本症状同根，一并修）。
3. 受控 textarea 每键触发全文 React 重渲染。

## 修法

**定案（用户 2026-09-21）**：先走方案 A —— 弹窗**显示**的代码改成「每条音符一行」的紧凑 JSON；
「另存为」落盘仍为 4 空格（issue 118 定案 + `ChartCodeExportSaveAs` 锁测钉住），两处不共用一份序列化。
1w 音符少见，略微卡顿可接受；若日后要彻底解决再上虚拟滚动编辑器（方案 B）。

本轮实现口径（待验收）：

- 打开两段式：弹窗立即出（空壳 + 占位/loading），序列化走 `startTransition`/`requestIdleCallback` 后再填充，不阻塞弹窗首帧。
- 校验移出击键热路径：防抖（~250ms）；大谱面把 parse+validate 下放到 Worker（`ChartConverter` 校验是纯函数，可低成本抽出）。
- 序列化侧若仍慢（3000~5000），排序/建对象分帧或入 Worker；大文本渲染若仍卡，走 textarea 自解方案（只读分帧填充等，实现时实测决定）。

## 锁测

1. 单测（`tests/unit/`，可测纯函数 + 静态源码断言，照 `EditorAudioSessionRefactor.test.ts` 惯例）：`ChartConverter` 新增 5000 音符基准用例（serialize、validate 各限时，钉住性能不回退）；断言弹窗打开路径不在挂载同步执行 stringify、击键校验走防抖（修复前红）。
2. 单测覆盖不到 React 渲染与真实观感 → Playwright 实测（生产构建）：点「谱面代码」→ 文本可见计时，700~800 音符 < 100ms、5000 音符首帧出壳 < 50ms；脚本不入库。手工验收 = 用户页面开大谱面不卡。

## Comments

### 2026-09-20 实现落地（待用户验收，口径见「本机实现口径」= 上文「修法」）

改动（三段，都落在 `ChartCodeEditorModal.tsx` + 一个新纯模块）：

1. **打开两段式**：`regenerateDraft()` —— 同步阶段只清空文本 + 置 `generating`（弹窗骨架 + 占位符先上屏），
   序列化 + `JSON.stringify` 推到 `scheduleIdleTask`(`requestIdleCallback`，退化 `setTimeout(0)`) 之后，
   在 `startTransition` 里落进撤销栈。「从画布刷新」同走这条路。空壳期 `readOnly` 且「应用」禁用、`isDirty` 不置位
   （loading 不当"草稿为空"，Esc / 点遮罩直接关，不弹丢弃确认）。
2. **textarea 改非受控**：去掉 `value={chartCode}`，DOM 文本由浏览器持有；新增单向同步 effect，
   只在「React 文本 ≠ DOM 文本」时写一次（覆盖填充 / 撤销 / 重做 / 重置 / 刷新 / Tab / 粘贴）。
   `handleKeyDown` 里的 `ta.value` 读数改为按需构造（普通键入键不再读全文）。
3. **击键校验防抖 250ms**：新增纯模块 `src/chart/editing/DebouncedTask.ts`（连发折叠 / flush / cancel，可单测）；
   「应用」走 `validationTask.cancel()` + 同步 `validateCode` 即时结算。
   新增 i18n `chartCode.generating`（zh-CN / en）。

### 实测（headless Chromium + 生产构建 `vite preview`，5000 音符 = 858551 字符；800 音符 = 136551 字符）

| 指标 | 修复前 | 修复后 |
| --- | --- | --- |
| 800 音符 · 弹窗骨架上屏 | 骨架与文本挤在同一帧，该帧 ~72ms | 12.8ms（文本后到） |
| 800 音符 · 文本上屏 | 11.9ms + 后置长帧 59ms | 84.9ms（一次性长帧 55ms） |
| 5000 音符 · 弹窗骨架上屏 | 27.9ms + **随后 334ms 无帧** | **5.4ms**（连续两帧空壳：5.4 / 10.1ms） |
| 5000 音符 · 文本上屏 | 同上冻结后才出 | 332ms（`longtask` 308ms 起于 24ms） |
| 击键 · 800 音符 | settled 5/19/19ms | 4/21/21ms |
| 击键 · 5000 音符 | settled 94/44/47ms | 66/41/42ms |

**关键结论（与票面根因不同）**：真实击键里 React 受控并没有在重写 DOM —— 原生键入后 `node.value` 已等于新值，
React 的 `updateWrapper` 会跳过赋值。纯 JS 也不是大头：5000 音符 `convertNotesToChartCode` 1.9ms、
`chartCodeToJSON` 3.7ms、`validateChartCodeJSON` 10.5ms（node 计时）。
**裸 textarea 对照实验**（无 React，858KB）：插入一个字符同样要 input 30ms / settled 60~100ms，
`wrap=off` / `white-space:pre` 只省 ~15%。即 ~40~70ms/键的剩余延迟是 **Blink 自身的文本重排**，
在普通 `<textarea>` 里躲不掉 —— 要再往下压只能上虚拟滚动编辑器（CodeMirror 那一类），那是独立命题，未做。

### 2026-09-21 · 方案 A（用户拍板）：显示改「每条音符一行」

`chartCodeToCompactJSON`（新增，只服务弹窗显示）：`[\n` + 每条音符 `JSON.stringify` 一行 + `\n]`。
对象视图仍用 `noteViewCodeToJSON`（只有一条音符，行数无所谓，缩进更可读）。
解析侧不受影响（JSON 不认空白）——应用 / 校验 / 复制出来的仍是合法谱面代码，且更接近 Bestdori 自己的排版。

**为什么是行数不是体积**（同机裸 textarea 对照，见上文 4/21 表）：行数砍到 1/5 → 首次布局快 5~10 倍；
只把缩进从 4 降到 2（体积 −25%、行数不变）几乎没用。
