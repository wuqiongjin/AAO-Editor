## Question

用户报告 4 个问题（2026-08-15）：

1. issue 35 后密集谱（3000+）放置仍体感略有卡顿，要求与少量音符时操作延迟一致（基本无延迟），可能需架构/更底层整改。
2. 内存占用大：普通 200-300MB，密集 400+MB；3000+ 音符下缩放浏览器窗口时页面布局明显卡顿一下才适配（疑为问题 1 部分原因）。
3. 连续 Slide 自下向上连接扩展时，后半截渲染不出来；缩放或在其附近放置其它音符后才出现。
4. notes 统计未计入 Slide 中间非 hidden 结点。

## 根因

| # | 问题 | 根因 |
|---|---|---|
| 1 | 放置残余延迟 | `Editor` 每次编辑同步跑 `engine.setChart`（内含 `buildKeyEvents` O(n log n)）在提交路径上；另见 #2 的 resize 全量重建链 |
| 2a | 窗口缩放卡顿 | `ResizeObserver` 每帧回调 `setSurface` → geometry 重建（surface 变化）+ 瓦片全量重建 + 重锚链，3000+ 音符下每帧都在做 |
| 2b | 内存 | 瓦片缓存预算 96MB + 瓦片 dpr 无上限（高分屏 2.0×，RGBA 位图常驻数十 MB）；高倍直渲模式下瓦片位图不释放 |
| 3 | Slide 后半截缺失 | `invalidateTilesForBeatRange` 把 pos 区间端点算反：pos = positionOfBeat(beat) 随 beat **递增**（旧注释误记为递减），低拍端 pos 小、高拍端 pos 大，旧实现命名颠倒传给 `tileIndexRange` → 跨多拍变更（滑条合并/扩展）只失效区间一端的 1 块瓦片，其余滞留陈旧；另 `handleSlideToSlideCombination` 中 `slideEndpointManager.updateEndpoints` 在 `removeOverlappedNotes`（splice 移位下标）**之前**调用，用旧下标定位滑条会合并错目标 |
| 4 | notes 统计 | 统计口径只按音符条目数，滑条/长条未按非 hidden 结点数计（与按键音 `buildKeyEvents` 口径不一致） |

## Comments

### 2026-08-15 二轮：残余卡顿深度诊断（只分析未修改）

**用户反馈**：issue35 + 一轮修复后，密集谱（3000+）下放置/编辑仍有明显延迟；且密集谱下操作浏览器标签页（缩放页面、调整浏览器宽高）明显卡顿，CPU/内存占用飙升。

**方法（诊断回路）**：Playwright headless Chromium + CDP（`Emulation.setCPUThrottlingRate` 模拟真机、`Profiler` 100µs 采样归因、`Emulation.setDeviceMetricsOverride` 模拟浏览器缩放），IndexedDB 注入 3104 结点密集谱，Event Timing + LongTask API 直接测用户症状。**关键：一轮验证在 dpr=1 无节流下全绿（放置 p95=56ms、0 longtask），与用户体感不符 → 环境差异是漏判根源。加 CPU 节流 ×4 + dpr=2 后两个症状全部复现。**

**测量矩阵（p95 / longtask 数）**：

| 场景（×4 节流, dpr2） | 密集 dev | 密集 prod | 稀疏 prod |
|---|---|---|---|
| 放置点击 | 192-208ms / 25 | 104-120ms / 12 | 72ms / 2 |
| 拖拽音符（20 步） | 1 lt (81ms) | 1 lt (52ms) | — |
| mousemove 扫掠 | 0-1 lt | 0 lt | 0 lt |
| 缩放+改窗口（8 次结算） | 571ms / 6 | 530-663ms / 6-9 | 404ms / 6 |
| renderChart 均值 | 16ms | 15.7-18.6ms | 8.6ms |

**单次点击 CPU 归因（prod ×4 dpr2，细采样 Profiler）——决定性对照**：

| | 右面板展开（默认） | 右面板收起 |
|---|---|---|
| 单击 wall / CPU | 685ms / 218ms | **111ms / 35ms** |
| getBoundingClientRect | **57.7%** | 0 |
| textarea `set value` | 9.8% | 0 |
| 剩余构成 | (program) 21.9%（canvas 光栅） | setTransform 14.6% + drawImage 8.9% + (program) 43% |

**根因结论（按证据排序）**：

1. **RC-A【主因，密集专属】ChartCodeEditor 受控 textarea 的全量代码同步布局抖动**：每次编辑（250ms 防抖后）`convertNotesToChartCode + chartCodeToJSON`（O(n)，密集谱 100-300KB 字符串）→ React 受控 `value={chartCode}` 重赋值 → 巨型文本布局失效；**下一次画布鼠标事件 `cssToCanvas` 的 `getBoundingClientRect` 强制同步重排**（57.7% CPU ≈ ×4 下 ~125ms）。代码体积 ∝ 音符数 → 完美解释"少量音符不卡、密集明显卡"。（注：一轮验证曾测"收起面板无改善"为误导——该轮 p95 混入了后续 mousemove/persist longtask；单点击微基准下差异 6 倍。）
2. **RC-B【固定地板】renderChart 每次交互全量重绘静态层**：背景填充×2、网格/小节线/sub-beat 线、BPM 文本、判定线每帧重画（仅音符层有瓦片缓存）。dpr2 快机 ≈6ms/帧 → 用户机器 ×4-6 = 25-35ms 地板，dev 模式再翻倍。
3. **RC-C【缩放/窗口卡顿】每次尺寸结算的全量重建链**：浏览器缩放/改窗口 → innerWidth/Height 变 → RO 150ms 防抖结算 → geometry 重建 + canvas 缓冲重分配 + **瓦片全清重建**（basis.surfaceW/dpr 变化）+ 双渲染（virtualHeight 级联 setViewport）。每次结算 ≈35ms 真机成本，连续操作反复触发 → CPU/内存飙升（缓冲+瓦片反复重分配）。密集谱瓦片重建更贵（+30%）。（注：纯 dpr 变化不触发应用——缩放症状全部来自 CSS 尺寸变化路径。）
4. **RC-D【dev 放大器】React 开发模式**：jsxDEV 9.9% + dev 校验 + 双渲染，把上述一切翻倍（放置 208 vs 120ms）。用户日常跑 dev.sh。

**已排除**：DOM 规模（687 节点）、拖拽路径（高效）、mousemove 渲染（prod 0 longtask）、键音 setChart（已防抖，2.3%）、瓦片增量失效（正常，单次重建 ~1 块且按区间裁剪）。

**修复方向（待用户确认后实施）**：
- F1（对应 RC-A）：代码同步与 textarea 解耦——面板折叠/不可见时不同步不渲染 textarea；改为懒同步（展开时才重建代码）；或代码生成移至 idle/Worker。
- F2（RC-B）：静态层（背景/网格/小节线/BPM 文本/判定线）离屏缓存，仅 scale/surface/beatDisplay/BPM 事件变化时重建；主帧 = blit(bg)+blit(tiles)+动态叠加。
- F3（RC-C）：surface 变化不清空瓦片（blit 缩放数学已支持）；合并结算链避免双渲染；缓冲复用。
- F4（RC-D）：先请用户在生产构建下复测；代码侧下沉 hoverPos 减少全树重渲。

**复现回路**：`node diag36.mjs`（TAG/DPR/THROTTLE/SPARSE/NO_CODEPANEL 环境变量矩阵）+ `node attr36.mjs`（单事件 CPU 归因），脚本在 /tmp（容器内），关键结果存 `/tmp/diag36-*.json`、`/tmp/attr36-*.json`。
