# 33-视频导出背压失效：慢编码器上在途帧无界增长 ⇒ 页面白屏 + 导出失败

Type: bug
Status: resolved 实现（2026-10-11；**待用户真机验收** —— 本工作区无 GPU，复现 / 复验走 Playwright 的 Firefox 与 Chromium）

**来源**：用户 2026-10-11 报「视频导出时经常整个页面变成灰白色，最后导出失败；此时切到谱面画布等其它页面，内容非常诡异」+ 截图（工作台画布挤压、残留「导出失败」提示）。

## 症状

- 导出跑到一半浏览器**整页变灰白 / 失去响应**，随后**导出失败**（UI 只有一句「导出失败」，原始错误被域层 `console.error` 吞掉）。
- 失败之后**同页其它画布**（工作台谱面画布等）渲染错乱 —— 渲染进程被内存压力压垮后回收画布 backing store 的典型表现。
- **不是每次都炸**：与浏览器 / 机器 / 谱面长度相关（用户原话「经常」）。

## 根因

`muxer.ts` 的"背压"只**限速**、不限**量**：

```ts
videoEncoder.encode(frame, { keyFrame: ... });
if (videoEncoder.encodeQueueSize > MAX_ENCODE_QUEUE) await sleepTick();  // 等一拍 0ms 就继续
```

编码器比出帧慢时，`sleepTick` 挡不住提交（每拍仍塞一帧），**在途帧数随总帧数线性涨**，而一帧就是一整张位图（720p ≈ 3 MB / 1080p ≈ 8 MB）⇒ 内存 ≈ 帧数 × 帧位图。1080p / 109 秒的谱 = 6840 帧，够把任何机器压垮。

## 实测（`.cache/export-fail-repro.mjs`，30s @720p，同一份活）

| | Firefox 修前 | Firefox 修后 | Chromium 修前/修后 |
| --- | --- | --- | --- |
| `encodeQueueSize` 峰值 | **1511** | **31** | 9 / 31 以下 |
| 进程 RSS 峰值 | **6273 MB** | **1022 MB** | 738 / 738 MB |
| 时长 | 96 s（19 s 出帧 + **76 s flush**） | 93 s（连续流水） | 29 s |
| 提交 1800 帧时的已输出 | **262** | 1768 | 1800 |

→ 同一份代码，**Firefox 的 VP9 比出帧慢 7 倍**（Chromium 软编吃得下），所以只有它炸；内存与耗时都随"编码器相对出帧的慢速"放大。

## 修法（本轮实现口径，待验收）

在途**计数**闸门（`createEncodeGate`）替掉 `sleepTick`（口径以**第二版**为准，第一版已被上一条 Comments 推翻）：

1. 在途 ≥ `MAX_ENCODE_QUEUE`（**32**）就**等编码器吐帧**（输出回调唤醒），不再"等一拍"；在途恒 ≤ 32 ⇒ 内存硬上限（1080p ≈ 266 MB）。
2. 等 `STARVE_MS`（**1 s**）没有输出 ⇒ **`flush()` 逼它吐**（`flush()` 保证把已提交的吐出来 ⇒ 打不破的状态一定能打破，**按 API 语义不死锁**）。实测 Firefox 的 VP9 在途只有 8 帧时永不吐第一帧 —— 正是这类"不自己吐"的编码器需要这条路，而"放宽上限"没用（见上一条 Comments）。
3. `abort()` / 编码器报错都要把等背压的唤醒；**取消要穿透背压**（`isCancelled` 进 sink：等背压前后与切音轨时都查）；音频通道用同一套机制。

## 锁测

`tests/unit/preview/video/MuxerBackpressure.test.ts`（3 条，**先红后绿**；先跑确认过 `expected 50 to be less than or equal to 8`）：

1. 假 `VideoEncoder` 一帧都不消化 ⇒ 在途被压在上限内、`addFrame` **等住**（旧实现 50 帧全提交）；
2. 停摆时 `addFrame` 等住，编码器报错 / `abort()` 必须把它唤醒（否则导出挂死）；
3. 编码器**要攒一批才吐第一帧**（`primeNeeded > 上限`，照 Firefox VP9）⇒ 仍必须跑完。

为什么单测够：本 bug 的现场就是"编码器相对出帧慢"与"编码器起搏需求深"，用一个只记账、不消化的假编码器即可**精确**造出来（真编码器的吞帧行为不可控，端到端反而不可复现）；真实浏览器的量级对照见上表。

## Comments

### 2026-10-11 过程

- 先按现场建探针（真 Chromium 软编）**没复现**：109s @1080p 含开场跑通、峰值 ~1 GB；换 Firefox 立刻复现量级（同活 6.2 GB），instrument 到 `encodeQueueSize` 才算坐实根因。
- **第一版修法（在途上限 8 + 等输出）在 Firefox 上死等**：它的 VP9 攒不够一批不吐第一帧 ⇒ 上限 8 时永远等不到输出。故补「起搏退让」两条（翻倍 + 封顶），上限最终取 32（起搏需求在 9~32 之间）。
- 顺带两条**观察项**（另议，本票不改）：① 导出失败原因只进 `console.error`，用户看不到任何线索（本次排障全靠探针抓 console）；② 封装是**整条视频攒内存**、末尾还 `new Uint8Array(target.buffer)` 再拷一份（用户那条 109s 导出 = 116 MB × 2~3 份），长谱的第二个内存来源，与 [32](./32-封装库迁移评估mediabunny.md) 的流式落盘方向相关。

### 2026-10-11 第二刀：**上一版修法自己引入死锁，用户当场撞到**

用户报「导出停在『正在导出画面（2100 / 2100 帧）』永不结束，点取消也没反应」。定位：

- 进度是 `addFrame` 返回**之后**才报的（`frameDriver.ts`）⇒ `2100/2100` 说明**出帧循环已经跑完**；
- 卡的是其后 `sink.addAudio()`（`exportVideo.ts` 里那步没有进度上报，所以卡片文案停在最后一条 frames 进度）；
- 取消只在出帧循环里查 ⇒ 到这一步取消钮形同虚设。

根因（**上一版修法自带的**）：退让写成"把上限翻倍后重等"，涨到封顶值（128）后
`while (在途 >= 上限)` 永远成立 —— **放宽上限不产生输出，所以它打不破"在途 ≥ 上限"这个状态**。
它只在"编码器**永不**自己吐"时才暴露（Firefox/Chromium 实测都会自己吐，所以没被测到）。

修法（第二版，已落）：

- 兜底改成 **`flush()`**：`flush()` 保证把已提交的都吐出来 ⇒ 状态一定能被打破，**按 API 语义就没法死锁**；
  阈值 `STARVE_MS = 1000`（健康编码器一帧几十毫秒，正常不会触发）；
- 去掉"上限翻倍 / 封顶"那一套（`PRIME_IN_FLIGHT` 撤销），在途恒 ≤ `MAX_ENCODE_QUEUE` = 32 ⇒ 内存上限更硬；
- **取消穿透背压**：`createVideoSink` 收 `isCancelled`，在 `addFrame` 等背压前后、`addAudio` 每块前后都查；
  取消 → `abort()` + 抛错，编排层把它判成「已取消」而不是失败。

锁测（`MuxerBackpressure.test.ts` 从 3 条加到 6 条，**先红后绿**；红的是后 3 条）：

4. 编码器**只在 flush 时吐** + 帧数超过上限（192 帧）⇒ 必须跑完（旧实现：只提交 128 就永久卡死）；
5. **音频通道**同一场景（用户卡的就是这一步）⇒ 不许挂死；
6. 等背压时点取消 ⇒ 必须退出（旧实现：取消被无视，仍返回 resolved）。

### 2026-10-11 第三刀：真正吊死用户的是**记账残渣**（音频输入≠输出）

第二版上线后用户仍卡在「正在导出画面（2100 / 2100 帧）」，但**取消已经能用**。这两条把卡点钉死了：

- 那句文案只在 `frames` 阶段出现（`phaseText`）⇒ 若真的在等音频，卡片会显示上一条 frames 进度 ——
  因为 `addAudio` **不上报新进度**（`muxing` 的进度在它之后）。所以卡点就在 `addAudio`；
- 取消能用 ⇒ 它在闸门的 `await` 里（我的取消检查在其中），不是同步卡死、也不是卡在 `finish()`。

根因：**在途计数按「输入:输出 = 1:1」记账，而音频编码器不是 1:1**。
AAC 一帧是 **1024 采样**，而 `addAudio` 按 `audioChunkFrames()` = **960** 采样一块喂
⇒ 约 6% 的输入永远不会变成输出 ⇒ `提交 − 输出` 只涨不还，闸门永远等不满。
真编码器自己是健康的（它攒够就吐），账本是我们自己记歪的。
这条只在**有 AAC 的机器**上出现 —— 本工作区的 headless Chromium 与 Firefox 都只有 Opus
（Opus 一帧正好 960 采样 = 我们的块大小，天然 1:1），所以我们怎么跑都复现不出来，用户一跑就中。

修法：闸门等不到输出时的兜底改成两条路（`recover()`）：

1. **对账**（`encodeQueueSize` < 上限 / 读不到）：编码器手上没压着活 ⇒ 是我们的记账残渣，
   把计数清回 0 即可 —— 不打断 GOP、不多花时间；
2. **逼吐**（`encodeQueueSize` ≥ 上限）：编码器确实压着活不吐（起搏不够深）⇒ `flush()` 后清账。

另：输出回调里的自减夹在 0（对账后仍可能有输出在路上，别让计数变负、短暂放大闸门）。

锁测（第 7 条，**先红后绿**）：

7. 假音频编码器**每 2 个输入吐 1 个输出**（`drainMode: 'when-ready'`，照 AAC 的比例）⇒ 200 块必须跑完；
   并断言走的是**对账**而不是 flush（`flushCount === 0`）。旧实现：`timeout`（吊死）。
