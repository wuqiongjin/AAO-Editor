# 07-视频导出

Type: feature
Status: open
Blocked by: 05, 06

**来源**：chart-preview/01 定案 3（用户 2026-09-30）：**离线逐帧 + 含音频**。无对标实现——Bestdori 前端 0 处编码 / 录制代码（research 笔记 §1.2），这条路要自己走通。

## 链路

```
任意秒出帧（05 的同一函数，固定 surface / dpr）
  → 逐帧离屏出帧（t = k / fps，k = 0..ceil(duration × fps)）
  → VideoEncoder（WebCodecs；codec 由 06 实测定）
  → 封装（mp4 / webm；库由 06 实测定）
音轨：OfflineAudioContext 渲染 BGM + 键音 → AudioEncoder → 同一容器
  → 二进制另存（Electron 通道，复用 03 建的；浏览器降级 <a download>）
```

## 规格默认（本轮实现口径，待验收）

- **1920×1080 / 60fps**；**mp4（H.264 + AAC）优先，webm（VP9 + Opus）兜底**（以 06 的 `isConfigSupported` 实测结论为准，实现时定死并在 UI 说明）。
- 时长 = 谱面长度（有音频 = 音频时长，ADR-0005）。
- 音量口径与播放一致（BGM + `settings.audio.seVolume`），提供**静音导出**。
- 导出耗时 ≥ 歌曲时长（离线逐帧）：UI 必须给**进度 + 取消 + 失败态**；长谱导出不得阻塞页面交互（worker / 分片 + 让出主线程）。

## 离线音轨的接缝（本票最深的一处）

- 现状：`AudioEngine` 的 `buffer` / `sampleCache` / `loadSample` 全 private，仓库无任何对外交出 `AudioBuffer` 的接口（`probeAudioDuration.ts` 只回 `duration`）。
- 口径：**同一份事件表**（`AudioTiming.buildKeyEvents`）+ **同一份采样加载**（现 engine 内的 `loadSample`）→ 用 `OfflineAudioContext` 渲染成一条音轨；**不新建第二套音量 / 调度口径**。接缝形态实现时定（engine 只读访问器 vs 抽出独立的采样加载模块 + 离线渲染器），但**不得**让导出绕开既有键音口径。
- 持久化：不落中间音轨文件（内存里直接喂 `AudioEncoder`）。

## 锁测

- `tests/unit/preview/video/ExportTimeline.test.ts`：帧数 = `ceil(duration × fps)`、帧时间戳与 `pts` 单调、音轨长度与视频对齐（不早停 / 不重复末帧）；倒流区与 `beat < 0` 的口径与画布播放一致。
- `tests/dom/preview/VideoExportFlow.test.tsx`：进度 / 取消 / 编码器不可用时的降级提示（`isConfigSupported` 为 false → 明确文案，不静默失败）。

## Comments

- 2026-10-07 票 20（动态预览播放器控件）定案转入两条：① **动态形态工具栏的「导出」入口随本票落地**（票 20 只做全屏，不做禁用占位钮）；② 音量口径取 `settings.audio.volume`（票 20 新增的持久化主音量）+ `settings.audio.seVolume`。
- 2026-10-09 **06 票实测回填**（全表在 `docs/research/chart-preview-export-limits.md` §5；环境 = Chromium 153 / Linux / **软光栅**，是最坏情况）→ 票面「规格默认」待定的几项据此定：
  - **容器 / 编码**：`isConfigSupported` 实测 —— 视频 `avc1.640028`（High 4.0）**可用**，`avc1.42001f`（Baseline）**不可用**，`vp8`/`vp09`/`av01` 全可用；音频**只有 `opus` 可用**，`mp4a.40.2`/`40.5`（AAC）、`flac`、`alaw`、`ulaw` 全 false。⇒ **票面「mp4（H.264 + AAC）优先」写不进代码：mp4 只能是 H.264 + Opus**（`mp4-muxer` 支持 `opus` 音轨）。webm（VP9 + Opus）是零意外组合。**定案时要在 mp4+Opus（兼容播放器少）与 webm（编辑软件 / Safari 不友好）之间选一个默认，另一个兜底。**
  - **硬门槛：H.264 的边长必须偶数**。`fitDesignSurface(1920,1080)` 给的是 `1920×1079` → `isConfigSupported` = **false**；取偶数（1078）才 true。导出尺寸要自己向下取偶，别直接拿场地几何去 `configure`（失败形态只是「不支持」，不报错指路）。
  - **依赖**：`mp4-muxer` 5.2.2（ESM 69 KB / gzip 14 KB）与 `webm-muxer` 5.1.4（65 KB / gzip 12 KB）都是 0 依赖单文件 —— **引依赖代价很小，不要自写 EBML / ISOBMFF**。体积照票面要求记在这里。
  - **性能与进度 UI 口径**：端到端（仿真场出帧 → `VideoFrame` 快照 → 编码）1080p **15.8 fps（0.26× 实时）**、720p 42.8 fps（0.71×）、540p 68.5 fps（1.14×）；**瓶颈是快照（强制光栅 + 拷贝，62 ms/帧 @1080p），编码器入队本身只 0.9 ms/帧**。⇒ ① **进度按帧数走**，不要按「≈ 歌曲时长」估（软光栅下实测约 4 倍）；② 规格给**分辨率档**（1080p / 720p）让用户挑比硬钉 1080p 稳；③ 别指望降码率提速 —— 编码不是瓶颈。**真机 GPU 光栅下这些数会显著变好，1080p/60 是否够要真机复测（本工作区无 GPU，且 Electron 跑不起来，见 research §1）。**
  - **能不能离开主线程**：worker 里 `OffscreenCanvas` + 2d、`VideoEncoder`、`VideoFrame(offscreenCanvas)` 都可用；**但 worker 没有 `Image`**，`CanvasSpriteIcon` 的图集缓存是 `HTMLImageElement`。实测把图集字节传进 worker 再 `createImageBitmap` 可行（2048×1024）⇒ 走 worker 要给它补一条 `ImageBitmap` 通路，不是免费改动（research §4 末）。
