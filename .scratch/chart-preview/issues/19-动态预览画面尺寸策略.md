# 19 · 动态预览画面尺寸策略（满宽 vs contain）

Type: grilling
Status: resolved 实现（2026-10-07，待用户验收 —— 拍板见「定案」，实现与实测见 Answer）

**来源**：2026-10-07 用户验收票 05 问题 1 —— "预览画面占用空间还是有点小（尺寸竟然比 bestdori 还小...），左侧和右侧的空白太大了"。

**为什么是 grilling**：这不是"画错了"，是**画面尺寸策略**要拍板（动 CONTEXT「设计面」/ 票 05 的场地口径，可能还要动票 10 的"整页不滚"）。拍板结论写进本票，实现落点同票。

## 现状（实测，`.cache/sim-layout.mjs`，dpr 1）

| 视口 | 舞台 | 场地 | 左右空白 | 场地占舞台宽 |
| --- | --- | --- | --- | --- |
| 1440×900 | 1340×764 | 1281×720 | 各 30 | 96% |
| 1680×1000 | 1580×864 | 1459×820 | 各 61 | 92% |
| 1920×1080 | 1820×944 | 1601×900 | 各 110 | 88% |
| 2560×1440 | 2460×1304 | 1920×1079 | 各 270 | 78% |
| 2560×1080 | 2460×944 | 1601×900 | 各 430 | 65% |

- **根因**：`fitDesignSurface` 把设计面（1334:750）**contain** 进舞台；舞台高度又被页头（≈56）+ 工具栏（≈40）+ 播放条（34+间距）+ padding（24/16）吃掉 ⇒ **窗越宽 / 越扁，左右空白越大**。大屏上 `SIM_FIELD_LIMITS.maxW = 1920` 再补一刀（2560×1440 那行正是被它钳的）。
- **对照 Bestdori**：`stageWidth = 容器宽`、`stageHeight = 750 × stageWidth/1334`（**宽定高**，页面自己滚）⇒ 它永远满宽；音符/场地/判定线的几何都相对 `stageWidth` 算，所以满宽不影响内部比例。

## 定案（用户 2026-10-07）

> 用户原话："不一定要满宽吧，只是现在的太小了，导致左右两侧空白太大。我接受不满宽，也接受左右两侧有空白，这没问题。"

⇒ **保持 contain（不满宽），左右留白接受；本票只做"把画面做大"**。满宽两案（A 滚动 / B 顶部裁切）**不做**，登记如下备查：

- A 满宽（照 Bestdori：`stageHeight = 750×stageWidth/1334` + 页面滚）—— 否决。
- B 满宽 + 顶部裁切（判定线锚在下部）—— 否决。

**本轮实现口径（待验收）**：

1. **撤/抬 `SIM_FIELD_LIMITS.maxW = 1920`**：它是大屏的硬瓶颈（2560×1440 实测场地 1920×1079，而舞台还有 2460×1260 可用 ⇒ 抬到 2560 即 **2242×1260，面积 +32%**）。新上限按"位图预算"定：`w × 密度 ≤ 4096`（dpr 2 时位图 8192×4608 ≈ 37.7M px ≈ 151 MB —— 逐帧直绘的画布，这个量级可接受；实现后加一条像素/内存实测记账）。
2. **动态形态减 chrome，把高度还给画面**：`.preview-page` 的 padding（24/16 → 12/8）+ 播放条那条的高度预算（`.pv-bar` 34 + `gap` 10 = 44；候选：缩到 32+6，或让播放条**叠在场地底部**——后者再省 38px，但会盖住判定线以下的背景区，实现时按观感定）。1920×1080 下预计 1601×900 → **~1720×968（面积 +15%）**。
3. 页头（模式切换行）/ 工具栏 / 谱面切换器**不动**（票 10 / 15 的口径）。
4. 其余视口（1440×900 是宽度受限那档）随 §1 与 §2 自然增大。

## 落点

- `src/pages/preview/PreviewPage.css`：`.preview-page`（动态形态的 padding）/ `.pv-stage` / `.pv-bar`。
- ADR-0016 §2（场地口径）+ CONTEXT「设计面」「仿真场」相应更新（仍 contain，只改上界与页面留白）。
- 锁测：`SimGeometry.test.ts` 的尺寸分支（窄 / 宽 / 极扁三档 + 新上界）；`scripts/sim-shot.mjs` 打印的场地盒与比例（修完仍是 1.7787，尺寸变大）。

## Answer

2026-10-07 实现（待用户验收）。

- `simGeometry.SIM_FIELD_LIMITS.maxW`：`1920 → 2560`（位图预算：dpr 2 → 5120×2880 ≈ 14.7M px ≈ 59 MB）。
- `PreviewPage.tsx` / `PreviewPage.css`：动态形态挂 `.preview-page.is-video` —— 页 padding 40 → 20、页头行 22 → 16、工具栏下留白 10 → 8、播放条 44 → 40（`min-height` 34 → 32 + `.pv-stage` gap 10 → 8）。
- `CONTEXT.md`「设计面」：上限改 2560；顺带把票 18 的"场地三图按设计 px 1:1"口径记进词条。

**实测（`.cache/sim-layout.mjs`，dpr 1）**

| 视口 | 修前场地 / 占舞台宽 | 修后场地 / 占舞台宽 | 面积 |
| --- | --- | --- | --- |
| 1440×900 | 1281×720 / 96% | 1338×752 / 98% | +9% |
| 1680×1000 | 1459×820 / 92% | 1515×852 / 94% | +8% |
| 1920×1080 | 1601×900 / 88% | 1658×932 / 90% | +7% |
| 2560×1440 | 1920×1079 / 78%（**被上界钳住**） | **2298×1292 / 93%** | **+43%** |
| 2560×1080 | 1601×900 / 65% | 1658×932 / 67% | +7% |

- 锁测：`SimGeometry.test.ts` +1 例（上界字面值 2560 + 2560 宽舞台长到上界且比例不变）；`PreviewPageWiring.test.ts` +1 例（`.is-video` 类 + CSS 两条规则）。`npm test` / `npx tsc -b` / eslint 全绿。
- 未做（用户已明确接受）：满宽两案；"扁而宽"窗口（2560×1080 那类）仍是高度受限（65% → 67%）—— 要更大只能动满宽或顶部裁切。
- 2026-10-07 **评审后的口径对账**（不改代码）：「定案」§1 那句位图预算 `w × 密度 ≤ 4096` 与 Answer 的 `maxW = 2560`（dpr 2 → 5120×2880）**自相矛盾**（同段举的 8192×4608 也与"≤4096"对不上）。以 **Answer 为准**（2560 是拍板后实测过的数：2560×1440 上 +43% 面积）；位图预算按 **dpr 2 ≈ 14.7M px ≈ 59 MB** 记（逐帧直绘画布，这个量级可接受），「≤4096」那句按誊写笔误处理。dpr 3 的机器位图会到 7680×4320 —— 登记观察项，不在本票。

- **2026-10-08 用户追问"刚才的结论是什么、我好像没感受到变化 / 为什么有两侧黑边"（结论回填，本票不改代码）**：

  1. **本票的定案与改动**（见上）：保持 contain、不满宽，只把画面做大 —— `maxW` 1920 → 2560 + 动态形态页面留白收一档（页 padding 40→20、页头行 22→16、工具栏下留白 10→8、播放条 44→40）。
  2. **"没感受到变化" = 符合预期**：实测 1920×1080 下场地只从 1601×900 → 1658×932（**+7%**），肉眼几乎不可见；大屏才吃到绝大部分收益（2560×1440：1920×1079 → 2298×1292，**+43%**，因为它原本被 `maxW` 硬钳住）。要"再看明显大"，只能靠页面上剩下的那些高度 —— 而它们已被票 10 / 15 的地基与行高档钉住（页头 / 工具栏不动）。
  3. **两侧黑边是 contain 的本性，不是画错**：舞台高度被页头 + 工具栏 + 播放条吃掉（约 120px）后，舞台宽高比**比设计面 1334:750（≈16:9）更扁** ⇒ 按 contain 就是"按高铺满、左右留白"；这些留白就是看到的黑边。Bestdori 能"最大化正好塞满屏幕"，是因为它的舞台是**宽定高 + 页面自己滚**（`stageHeight = 750 × stageWidth / 1334`）—— 这正是 2026-10-07 已否决的方案 A。
  4. **舞台进真全屏时黑边自然消失**：chrome（页头 / 工具栏 / 播放条所在的那一排随全屏退场）没了，舞台比例 = 屏幕比例 ≈ 16:9 ≈ 设计面比例 ⇒ 画布几乎铺满；只剩播放条占的那 40px 高度。注意这与"浏览器窗口最大化"是两回事 —— 窗口最大化时 chrome 仍在，黑边仍在。
  5. **结论**：本轮的改动与定案一致，用户看到的"基本没变 + 两侧黑边"是这套策略的正常表现，不需要再改。若将来要"像 Bestdori 一样塞满视口宽度"，必须重开本票的满宽两案（A 滚动 / B 顶部裁切）并重新拍板 —— 本次用户明确表示"不一定非要改，我需要结论"，故不动代码、保持 Status 不变。
