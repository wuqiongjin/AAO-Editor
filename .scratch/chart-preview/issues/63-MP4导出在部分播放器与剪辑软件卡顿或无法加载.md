# 63 · MP4 导出视频在部分播放器 / 剪辑软件卡顿或无法加载

Type: bug
Status: resolved 实现（2026-11-12 已实现；随机访问用户真机复验通过；盒结构核对 / 报障软件逐项清单待做）
Blocked by: none

## 来源与症状

用户反馈：mp4 格式导出的视频在一些视频播放器和剪辑软件中会出现播放卡顿或无法正常加载显示。环境 / 软件不详 —— 本轮已自行实测定位。

## 实测环境

Chromium **153.0.8010.12**（Playwright v1243，Linux / SwiftShader；与 `docs/research/chart-preview-export-limits.md` §1 同环境）。页面走 dev server 同源，用**产品 `createVideoSink`** 真编码出一份 1920×1080 / 60fps MP4（`/tmp/probe-real.mp4`），再解析 ISOBMFF 盒结构 + 塞回 `<video>` 播放。本工作区无 QuickTime / NLE，第三方软件兼容性按既有文档与盒结构判定。

## 根因（确认 2 条，排除 4 条）

反馈里的两个症状来自**两件不相干的事**，碰巧都出现在 MP4 上：

**① 「无法正常加载」= MP4 壳里装的是 Opus，不是 AAC（既定行为，非缺陷）。** 实测 `AudioEncoder.isConfigSupported('mp4a.40.2')` = **false**、`opus` = **true**（与 research §5.1 一致）⇒ 手选 MP4 时 `candidateOrder('mp4')`（`exportSpec.ts:163-170`）产出 **MP4 + Opus**。真文件盒结构：`Opus` + `dOps`，**无 `mp4a` / `esds`**。QuickTime / Safari / 多数剪辑软件认的是 mp4 壳里的 AAC，换 Opus 一样放不出。文件本身**没坏**：Chromium `<video>` 能 `loadedmetadata`（1920×1080）并正常 `play()`。
**这是 `CONTEXT.md:218` 已定案的行为**：「只有用户手选 mp4 且本机无 AAC 时才落到它，代价由面板说明当场讲清」；代码里也确有 `note.mp4Opus` 提示（`VideoExportFlow.test.tsx:221-227`）。默认「自动（推荐）」不踩这一格（探不到 AAC 自动退 WebM）。用户 2026-11-11 明确：**手选 MP4 就该出 MP4，不自动转 WebM、尊重手选** ⇒ 本票不改这一格、不改定案。若日后要消除该兼容面，须单独改 `CONTEXT.md:218` 并另开票。

**② 「播放卡顿」= 全片没有周期关键帧（本票要修的缺陷）。** `muxer.ts:377` `keyFrame: queuedFrames === 0` —— 只强制**第 0 帧**，其余全交给编码器；`latencyMode:'quality'`（:281-283）。实测类谱面场景（静态背景 + 少量移动元素，**300 帧 / 5 s**）H.264 **只吐 1 个 key chunk**（`stss` entry_count=1、sync samples=[1]）；高动态合成场景也只按场景切换吐（60 帧 2 个）。⇒ 拖进度条 / 剪辑时间线刮擦 / 生成缩略图都要从第 0 帧解码。**`createVideoSink` 是 MP4 / WebM 共用的 ⇒ WebM 导出同样受影响**。

**已实测排除**（原候选，别再往这几个方向修）：
- `fastStart:'in-memory'` 已开（`muxer.ts:239-240`）：真文件 `ftyp > moov > mdat`，moov 前置 ✓。
- H.264 Level 过高：请求的是 `avc1.640033`（L5.1），但编码器自己写进 `avcC` 的是 **level=0x2a（L4.2）**，与 1080p60 匹配 ✓ —— `exportSpec.ts:114` 的 codec 字符串 ≠ 文件里的 level。
- 逐帧 round PTS 成 VFR：`frameTimestampUs`（`exportSpec.ts:229-231`）输出 16666/16667 μs 交替，但 mp4-muxer 换算到 timescale=60 后 `stts` 是**单段 delta=1（恒定帧率）** ✓。
- B 帧 / ctts：`quality` 下实测输出时间戳**单调**（`nonMonotonicPairs=0`）、文件**无 `ctts`** ✓（其它平台编码器仍是潜在风险，本机不触发）。

## 修法（本轮不改代码）

只做一件：**周期性强制关键帧**（如每 2 s 一次 `keyFrame:true`），改在 `createVideoSink.addFrame`（`muxer.ts:377` 一带），MP4 / WebM 共用 sink 一起受益。`latencyMode` / codec 字符串 / 时间戳口径都不动（已实测排除）。mp4+Opus 那一格按既有定案保持不动。

## 锁测

- 关键帧节奏可用 `addVideoChunkRaw` 在 Node 里复现并断言 `stss` 同步样本数 ≥ N（无需浏览器）。
- **落地（2026-11-12）**：`tests/unit/preview/video/VideoKeyFrames.test.ts` 两条用例看守 —— ①「5s / 60fps 的 MP4 每 2s 有一个同步样本」：假 `VideoEncoder` + 假 `EncodedVideoChunk` 走**真实 `mp4-muxer`**（生产 `addVideoChunk` → 内部即 `addVideoChunkRaw`），`finish()` 的真字节解析 `stss`，断言 `[1,121,241]`（旧实现 `[1]` ⇒ 红）；②「WebM 共用 sink 同节奏」：10fps / 45 帧断言 `keyFrame` 标志 `[0,20,40]`（写死 120 帧 ⇒ 红）⇒ 逼出按 `fps × 2` 推导，不写死 60fps。Node 环境即可跑，无需浏览器。
- 第三方软件兼容性必须真机验收（本轮环境无 QuickTime / NLE）：手工清单 = 导出后核 `avcC` level、`stss` 条目、`Opus` vs `mp4a`，再在报障软件里逐项复验。
- 若日后改 mp4+Opus 的 UI 拦截，`VideoExportFlow.test.tsx` 补例（本票不做）。
