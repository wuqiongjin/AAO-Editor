# 24 · 动态预览音符下落速度档：范围与输入形态

Type: grilling
Status: open（**已拍板** 2026-10-08，实现落点在本票，待实现）
Blocked by: —

**来源**：2026-10-07 用户对票 05 / 20 验收后提的问题 6 —— "音符下落速度，要支持到 1-12 这个范围，最小单位是 0.1，最好能手动输入数字？"

**为什么是 grilling**：范围牵动接近模型 `T = (12 − n)/2` 的定义域（12 处退化），且需要用户拍板"要不要为了 12 引入一个下限常量"。拍完的实现写进同一张票。

## 现状

- 设置域：`SIM_NOTE_SPEED_RANGE = { min: 1, max: 11, step: 0.5, fallback: 9.5 }`（`src/chart/config/AppSettings.ts:208`），`normalizeNoteSpeed` 按步长吸附后夹取，落 `settings.preview.noteSpeed`（additive，不 bump schemaVersion）。
- 模型：`simGeometry.approachSeconds(n) = (12 − n) / 2` ⇒ 档位 1..11 → `T` 5.5s..0.5s；`n = 12` 时 `T = 0`，`approachA` 的分母被兜成 `Number.EPSILON` ⇒ 音符只在压线那一瞬出现，模型无定义（这也是票面上界取 11 的原因）。
- UI：`PreviewDisplayPanel` 的 `NoteSpeed` = 一个滑杆（`min 1 / max 11 / step 0.5`）+ 只读读数，**不能手动输入数字**。

## Bestdori 实测（反编译，同一 bundle）

```js
// fldNoteSpeed 那一组控件
i("my-numeric-input", { attrs: { min: 1, max: 11, small: .1, large: .5, display: "1" } })
```

⇒ Bestdori 模拟器自己就是 **1..11 + 数字输入框 + 小数步进 0.1 / 粗步进 0.5**；它的上界同样是 11 —— 用的是同一个 `(12 − n)/2` 公式。

## 三个方案

- **A · 照 Bestdori：1..11 / 步长 0.1 / 数字输入框**（`small .1 large .5` 的两个步进照抄），滑杆保留做粗调。
  - 得：零特例，两边逐位同手感。
  - 失：用户在游戏里确实用到 12 档（用户原话"游戏里真的支持 1…12，1…11 是很老的版本了"），预览里够不到这一档。
- **B · 1..12 + 给窗口一个下限**（推荐）：`T = max(T_MIN, (12 − n) / 2)`，`T_MIN` 取 **0.1s**（`n ≥ 11.8` 都是 0.1s 窗口，行为连续、无跳变）。
  - 得：档位与游戏一致（1..12），12 不再是"退化/炸掉"，而是一个有定义的极短接近窗口。
  - 失：多一个模型常量要进 CONTEXT「接近模型」；`n > 11.8` 这几档手感趋同（"差不多就行"，用户已表示预览不追求精细）。
- **C · 1..12 + 换映射**（不推荐）：改线性映射 `T = 5.5 − (n − 1) × 5.25/11`（12 → 0.25s），不再照 Bestdori 公式。
  - 失：与 Bestdori 的速度手感不再逐位对齐 —— 同一张谱在两边看起来不一样快；也丢了"12 档 = 游戏里同一档"的可解释性。

➡️ **推荐 B**：用户已说了预览"速度差不多就行"，要的是"范围对得上游戏 + 能输入数字"；一个 `T_MIN` 常量比"换一套自己发明的映射"便宜，也比"封在 11"更贴近用户实机习惯。

## 待拍板（2026-10-08 已拍板，结论见下一节）

- ~~**Q1 · 范围口径 A / B / C**~~ → **= B**。
- ~~**Q2 · 输入形态**~~ → **数字输入框为主 + 滑杆（step 0.1）为辅**，步进按钮走 Bestdori 同款小 0.1 / 大 0.5（照搬这两个步进值，版式套既有的 `.slider-control` / `.slider-value`，另起一个数值输入控件变体）。
- ~~**Q3 · 默认档要不要动**~~ → **不动**（维持 9.5，用户 2026-10-07 定案"比较适合预览谱面的速度"）。

## 定案（用户 2026-10-08）

> 用户原话："我偏向于，1...12 对标游戏（sonolus 应该也支持）。未来我可能会开发类似 sonolus 的 bangdream 特化软件，说不定现在的这些**以游戏为标准**的功能可以派上用场。你提到的拍板，我同意你的推荐。"

1. **范围 = 1..12，步长 0.1，默认值不动（9.5）** ⇒ 采用 **案 B**：`T = max(T_MIN, (12 − n)/2)`，`T_MIN = 0.1s`（`n ≥ 11.8` 都是 0.1s 窗口，连续无跳变）。**否决**案 A（照 Bestdori 封 11）与案 C（自造线性映射）。
2. **为什么以游戏为准**（用户理由，登记在案）：(a) 现状 1..11 是**老版本游戏**的档位，现代 BanG Dream 就是 1..12；(b) 用户未来可能做 BanG Dream 特化的类似 Sonolus 的东西，届时"以游戏为准"的这份口径可以直接带过去 ⇒ **偏好置信 > 逐位照抄 Bestdori 模拟器**。这条也顺手定了本 effort 的一条优先级：**当 Bestdori 参照实现与游戏本身冲突时，优先游戏**（此前默认是对 Bestdori bundle 逐位对齐）。
   - 代价已知：`n > 11.8` 那几档在接近模型里趋同（预览"差不多就行"）；且多一个模型常量要养。
3. **UI**：数字输入框为主 + 滑杆（step 0.1）+ 步进按钮（小 0.1 / 大 0.5，照 Bestdori 的 `small/large`）。

## 落点（定稿）

- `src/chart/config/AppSettings.ts`：`SIM_NOTE_SPEED_RANGE` → `{ min: 1, max: 12, step: 0.1, fallback: 9.5 }` + `normalizeNoteSpeed`（老数据 9.5 与新步长都合法 ⇒ additive，不 bump schemaVersion）。
- `src/preview/video/sim/simGeometry.ts`：`APPROACH_MIN_SECONDS = 0.1`（新常量进 `APPROACH` 一族），`approachSeconds(n) = max(APPROACH_MIN_SECONDS, (12 − normalizeNoteSpeed(n)) / 2)`。
- `src/pages/preview/PreviewDisplayPanel.tsx`：`NoteSpeed` 改成「数字输入框 + 滑杆 + 步进」，版式复用面板里既有的 `.slider-control` / `.slider-value`，不自创一套控件皮肤。
- 文档：CONTEXT「接近模型」补"12 档的下限 + 为什么"，ADR-0016 §1.2 若原文写了"档位 1..11"顺手改。

## 锁测

- `tests/unit/chart/AppSettingsNoteSpeed.test.ts`（若无则新增，或并入既有 AppSettings 测试）：9.5 不吸附；`12.4` → 12；`0.9` → 1；非有限 → 9.5；步长吸附到 0.1（如 `9.55` → `9.6`）。
- `tests/unit/preview/video/SimGeometry.test.ts`：`approachSeconds(12) === APPROACH_MIN_SECONDS` 且 **`> 0`**（今天差的 0 那条要能红）；`approachSeconds(11.8)` 同值；`approachA` 在 `T = T_MIN` 下 Δ = −T 仍 ≈ 0.058。
- DOM：`PreviewDisplayPanel` 输入 `12` 后被接受（旧写法会把它夹到 11 ⇒ 必红）；`11.9` 输入 → 读数 `11.9`。
- 手工：同一张谱在 9.5 / 12 两档下观看，音符仍可见、抵达判定线的时序连续（不出"突然全屏白一下"这种炸掉的表现）。
