# 27 · 全屏播放的左右黑边（= 播放条占的那一行）

Type: grilling
Status: resolved（2026-10-09 根因实测坐实 + **修法已拍板**：E「播放条浮在画面上」，**且只在全屏态浮**；**已实现**：`PreviewPage.css` 全屏段两条覆盖 + 锁测 8+2 例，真机三档实测黑边 0，见下方 Answer）

## 来源

2026-10-09 用户：「**全屏播放下**，左侧和右侧有黑边」。

用户随即澄清两点（同日）：① 说的是**全屏播放态**，不是窗口最大化态；②「全屏下不存在什么满宽还是不满宽」⇒ 本票与票 19 的 contain / 满宽之争**无关**。

## 症状（全屏实测，`.cache/pv-fs-edge.mjs`，DPR 1）

全屏舞台底色 = `--canvas-bg` = **rgb(12, 14, 17)**（`.preview-stage:fullscreen`，`PreviewPage.css` L523-539）⇒ 留白本身就是近黑的，与窗口态那层（露出的其实是页面底色，见文末 Comments）不是一回事。

| 屏幕 | 舞台（=屏幕）比例 | 现状场地 | 左右黑边 |
|---|---|---|---|
| 1920×1080 (16:9) | 1.778 | 1850×1040 | 各 **35px**（占屏宽 3.6%） |
| 2560×1440 (16:9) | 1.778 | 2490×1400 | 各 **35px**（2.7%） |
| 1920×1200 (16:10) | 1.600 | 1920×1079 | 各 **0px** |
| 3440×1440 (21:9) | 2.389 | 2490×1400 | 各 **475px**（27.6%，另一成因，见 F） |

## 根因（已实测坐实）

16:9 屏幕比例 **1.7778** ≈ 设计面 **1.7787** ⇒ **画面只要吃掉整个屏幕高度，宽度就正好铺满**，本不该有黑边。

而全屏下画面**没能吃掉整个屏幕高度**：`.pv-stage` 是 flex column，播放条（`play-bar--preview` `min-height: 32`，票 23 #3 定动态形态留住它）+ `gap: 8` 占掉 **40px**。

⇒ 画面高 `1080 − 40 = 1040` ⇒ 宽 `1040 × 1.7787 = 1850` ⇒ 每侧黑边 `(1920 − 1850) / 2 = 35px`。

**黑边宽度 = 播放条占的那 40px × 1.7787 / 2 = 35.6px**，与实测逐位吻合。**黑边的唯一来源就是播放条占的这一行。**（16:10 屏幕比例 1.6 < 1.7787 ⇒ 宽度受限、本来就 0 黑边，所以只有 16:9 及更扁的屏幕才看得到这条黑边。）

## 修法（**E**，已拍板）

- **E · 播放条浮在画面上（不占独立行）**：画面吃掉整个舞台高度。
  实测 1920×1080：场地 1850×1040 → **1920×1079**，**黑边 0px**，画面面积 **+7.7%**；2560×1440 同理 **+5.7%**。
  - 票 19 §2 已把它列为候选：「让播放条叠在场地底部 —— 再省 38px，但会盖住判定线以下的背景区，实现时按观感定」。
  - 代价：播放条压在画面底部。判定线在 `0.82H`，播放条约 32px 高 ⇒ 只压到 `0.97H` 以下那一小条，**不压判定线本身**。
- **F · 抬 `SIM_FIELD_LIMITS.maxW`（只治 21:9，与本票主因无关）**：3440×1440 下画面被 `maxW = 2560` 钳住 ⇒ 黑边 440px。要不要抬上界另议（dpr 位图预算见票 19 Answer：dpr 2 ≈ 14.7M px）。

## 定案（用户 2026-10-09 拍板：**E，且只在全屏态浮**）

**Q1 = 只全屏浮**（窗口态播放条照旧占独立行）。三条理由：

1. **两态的"留白"根本不是一回事**：全屏态舞台底色是 `--canvas-bg`（近黑）⇒ 留白是**黑边**；窗口态 `.preview-stage.is-filled { background: none }` ⇒ 留白露出的是**页面底色**，与页面其他区域同色，**不构成视觉问题**，没有"要消掉"的对象。
2. **窗口态播放条占一排是票 05 的用户定案**（"播放控件 = 舞台底部一排，照 Bestdori"），不该为这 40px 推翻。
3. **语境不同**：全屏是沉浸观看，画面占满屏幕合理；窗口是工作界面，把播放条压在画面底部反而挡住画面下缘、碍事。

⇒ 改动的面收在 `.preview-stage:fullscreen` 这一段的覆盖里，窗口态行为一字不动。

**Q2 = 21:9 先不管**（= F，与播放条无关，是 `maxW` 的成因；本机非带鱼屏，登记观察项，需要时另开票）。

- 画面底部被压住的那一条 = 判定线（`0.82H`）**以下**的背景区，不挡判定线与音符（票 19 §2「会盖住判定线以下的背景区，实现时按观感定」）。

## Answer（2026-10-09 实现）

### 落地

`src/pages/preview/PreviewPage.css` 的「全屏预览」段后补两条（作用面全在全屏块里，窗口态一字不动）：

```css
.preview-stage:fullscreen .pv-stage { gap: 0 !important; }
.preview-stage:fullscreen .play-bar--preview {
  position: absolute !important; left/right/bottom: var(--space-3) !important;
  min-height: 0 !important;
  background: linear-gradient(to top, color-mix(in srgb, var(--canvas-bg) 72%, transparent), transparent);
  border-radius: var(--radius-md);
}
```

（`relative` 那条**没有**：倍速面板的含块本来就是 `.pv-rate` 自己 —— 它自带 `position: relative`，与播放条改不改定位无关。实测面板底 = 触钮顶 − 8px，改前改后同一位置。）

### 实现时冒出来的一条新根因：这两条覆盖**必须 `!important`**

第一版按"提高特异性"写（`.preview-stage:fullscreen .pv-stage`），实测**不生效**：全屏下 gap 还是 8px、场地还是 1850×1040。坐实是本机 Chromium 里**特异性恰好打平、源序在后的一方赢**：

- `:fullscreen` 只计**一个类**（与 `:hover` 同档，但 Chromium 里确实计）⇒ `.preview-stage:fullscreen .pv-stage` = 0-3-0；
- 对手 `.preview-page.is-video .pv-stage`（以及 `… .play-bar--preview` 的 `min-height: 32px`）也是 **0-3-0**，却排在文件后面（第 812 / 816 行）。

证据链（都在真 `requestFullscreen` 下）：同一份规则 —— ① 摘掉 `!important` → gap 仍 8px；② 删掉 `.preview-page.is-video .pv-stage` 那条 → 立刻 0；③ 原样塞进"后到"的 `<style>` 标签 → 也 0；④ 选择器提到 `.preview-page .preview-stage:fullscreen:fullscreen …`（0-5-0）→ 压得住。⇒ 不用"再多堆两层选择器"这种脆写法，改用本文件既有的手法（`.is-palette-swap` 那条就是 `transition: none !important`），代价仍收在全屏这一块里。这条坑与本文件 511-515 行记的那条（两规则同权、靠源码序决胜负）是同一个。

### 真机实测（Playwright，真 `requestFullscreen`，DPR 1）

| 屏幕 | 场地（修前） | 场地（修后） | 左右黑边 | 画面面积 |
|---|---|---|---|---|
| 1920×1080 (16:9) | 1850×1040 | **1920×1079** | 35 → **0** | **+7.7%** |
| 2560×1440 (16:9) | 2490×1400 | **2560×1439** | 35 → **0** | **+5.7%** |
| 1920×1200 (16:10) | 1920×1079 | 1920×1079 | 0 → 0 | 0（本来就按宽铺满） |

- 播放条浮起后：`[12, 1040, 1896, 28]`（离舞台下缘 12px 内缩，底衬与它一起收进去）；**判定线 y = 886**（0.82×1079），播放条顶在它下方 154px ⇒ 不压判定线、也不压线上方的音符区。
- **倍速面板锚点不受影响**：面板底 = 触钮顶 − 8px（改前改后同一位置）—— 含块是 `.pv-rate` 自己（它自带 `position: relative`），播放条怎么定位都够不着它。
- **窗口态一字未动**：进出全屏往返逐项比对（舞台 / 场地 / 场地 client / 画面 / 播放条 / `position` / `gap`）**全部相等**；窗口态播放条仍 `[76,1040,1820,32]`、占独立行。
- 逐像素读底（16:9 与 16:10 两档）：播放条那一行底下是 `#0c0e11`，台上前景对比 **17.7:1**（WCAG AAA 之上）。衬底那层浅渐变实测**肉眼不可见**（开 / 关同点同色）—— 留着当"极矮视口下画面被压到播放条下方"的兜底，不构成可见变化。
- 播放条高度由 32 → **28**（`min-height` 让位、内容自己撑）。这两处（12px 内缩 + 28px 高）落点分两种屏幕：**16:9 及更扁**的画面已铺满屏高，落在画面自带的**黑下缘**（画面画到屏底，那 1px 取整缝也在其中）；**16:10 这类更方的屏**上画面按宽铺满、上下各留 ~60px，播放条落在**画面下方**的舞台底上 —— 两种都不压在画面内容上。
