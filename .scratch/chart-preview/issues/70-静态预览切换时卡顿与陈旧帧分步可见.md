2. 能看到「编辑效果应用到静态预览的过程」：音符突然出现 / 移动，最终画面本身没问题；
3. 用户判断与票 69 是同一类问题，且静态预览没有像修好的动态形态那样的加载过程，怀疑「靠一小会的卡顿去加载」。

## 根因（代码链路定位，2026-11-13；实测数字见「调查与复现」）

1. **卡顿与票 69 同源，静态侧从未修过**。票 69 的 `waitForPaint()` + 分批派生只加在 `mode === 'video'`；`PreviewPage.switchMode` 对 static 直接切（票 69 注释自述「静态形态没有这一步，直接切」），`PreviewPage.tsx:451` 的加载骨架也只在 `pendingMode === 'video'` 时渲染。静态页首帧（实际发生在应用启动时的隐藏态，不是切页那一刻）的同步重活：`makePanelLayout`（`getBpmEvents` 全谱扫描 O(n log n) + `new ChartGeometry`，`panelLayout.ts:83-90,122-139`）、同步建全部 `panelCount` 个面板 DOM 槽（`StaticPreviewView.tsx:268,278-296`）、`useLayoutEffect` 里同步 for 循环逐格 `blitInto`（`StaticPreviewView.tsx:187-215,231-246`；每格一次 `renderFrame` + `directNotes: true` 直渲 + 每面板重建网格条带，`panelPainter.ts:111-150`）。整条链没有 `waitForPaint` / `yieldToMainThread`（这两个原语只在 `exportPanels.ts` 导出路径与票 69 动态分支）；`useLayoutEffect` 还跑在浏览器 paint **之前**，连「先画个骨架」都做不到。票 16 记录的是同一病（导出按钮先冻住再跳到结束），当时只修了导出路径。
2. **但不是「每次切进来重新加载」**。七页保活挂载（`AppShell.tsx:113-118`），隐藏用 `opacity/visibility`（仍占布局，`AppShell.css:311-334`），静态视图在后台就挂载并出过图，切回来不重挂。发生的是**重画**：`usePreviewScope` 激活时 `flushPersist → store.list/get` 异步重读（`usePreviewScope.ts:68-98`），但 `loaded` 不卸载、首帧直接给上一次访问的旧 `project/notes`（`:100-101`，`loading=false`）；异步回来后新 `project` → 新 `scene` → `painter` 换代 → 可见面板同步整批重画（`StaticPreviewView.tsx:88-102,221-246`）。
3. **「能看到编辑效果被应用」= 陈旧帧被看见了**，属缺陷而非预期过渡：旧数据帧 → 激活后异步重读 → 新 `scene` / 画家换代 → 可见面板整批重画。探测已坐实（见「调查与复现」）：工作台改谱之后、切回预览之前，隐藏页的 canvas **完全没重画**；点按后的第一帧仍是旧画面的像素，约 170~200ms 后像素签名才翻转。这是票 11 #2「切页后画面与数据不同步」的激活态版本。另有一层独立来源：`CanvasSpriteIcon` 首帧缺图直接不落笔，图集 / 独立切片 / mip 冷启动都是同步活（`docs/research/chart-preview-technical-baseline.md:131` 已把「首帧素材未就绪」列为已知项；票 68 在动态侧用 `prepareSimNoteSprites` 预热过，静态侧没接）。
   - **开票时的推测被探测否掉一条**：原以为「首次进入会先闪一下静态空态文案」（`PreviewPage.tsx:370` 的 `loading` 只挡空态判断）。实测点按后 4~12ms 舞台就已经有 6 张面板 canvas，没有 `pending` 文案 —— 因为保活页在应用启动时就挂载、`usePreviewScope` 的读 effect 不看 `active` 就已经跑过了。所以本票的「分步可见」不是空态闪现，而是**旧画布被显示了一段时间**。

## 实现口径（2026-11-13；按用户「最合适 / 性能最好 / 体验最好」授权自行判断，非用户逐字定案）

1. **先消掉无谓重画，而不是给重画加骨架**（`usePreviewScope.ts`）：激活重读仍是 `flushPersist → store.get()`，但只有「读回来的记录语义不同于上一份」才提交新 `project` 并递增 `dataVersion`。内容没变就保留旧身份 ⇒ `scene` / 画家不换代 ⇒ 零重画、零长任务。等价比较用 `JSON.stringify` 快路径 + 与键序无关的深层值兜底，**不用编辑域的 `notesEqual`**：它的音符类型表只认 `LDirectional`/`RDirectional`，真实谱里的原始 `Directional` 会落到 `return false`（首轮 GREEN 复测就栽在这里，每次激活仍重画）；`audioBlob`/`coverBlob` 排除在外。
2. **激活当帧就盖住旧画布**（`usePreviewScope.ts` 的 `checking` + `PreviewPage.tsx`）：读盘期间还不知道数据变没变，若等 `dataVersion` 才显示骨架，长谱约 200ms 的旧画面照样被看见。激活检测改走 `useLayoutEffect`，`checking` 在 paint 前置位；读回来没换代就撤掉（常态切回只多一层覆盖、**不重画**），真换代则由 `staticPaintDeferred` 撑到可见面板出完，中间不断档。
3. **只有真换代才分批出图**（`StaticPreviewView.tsx`）：`deferPaint` 时先 `waitForPaint()` 让骨架落地，再按格 `yieldToMainThread()`（复用票 16 原语，`PAINT_PANEL_CHUNK = 1`），出完回传 `paintVersion` 撤骨架；换代中途又换代由 effect cleanup 取消旧任务。常态（缩放 / 显示档 / 滚动 / hover）保持 `useLayoutEffect` 的 paint 前同步出图不变 —— issue 11 #2 靠它挡住换代那一帧的旧位图，不能为了分批挪到 paint 之后。
4. 骨架 = 不透明覆盖层 `.preview-stage__paint-pending` + 轻量 spinner（尊重 `prefers-reduced-motion`）+ `preview.static.loading` 中英各一条。未动 `getBpmEvents` / `ChartGeometry` 派生与全量 DOM 槽（见「结论边界」）。

- **编辑场景（分步可见坐实）**：工程记录整谱哈希从 `-1260926265` 变为 `142234741`（编辑确实落盘）；编辑后仍在**工作台**时，隐藏预览页的画布签名 `-69233644` **未变**（不重画）；点按预览后 dt=5ms 仍是旧签名、dt=172ms 翻成 `1669347864`，同轮 `clickToFirstBlit=183ms`、`panelBlits=6`（一次整批重画）。截图序列 0/60/140/260/450/800/1400ms 与首张的像素差为 0/11/11/11/11/11/16,303 —— 画面确实前后两张不同，用户看到的就是这个切换。

**修后复测（GREEN，2026-11-13；同探针 / 同语料 / 同环境，`results-after.json` / `visual-after.json` / `shots-visual-after/`）**：

| 谱长 | 阶段 | RED 点按→重画 | GREEN 点按→重画 | RED blit / 长任务 | GREEN blit / 长任务 |
| --- | --- | --- | --- | --- | --- |
| 1× | first | 85ms | 无重画 | 6 / 0 | 0 / 0 |
| 1× | repeat | 62ms | 无重画 | 6 / 0 | 0 / 0 |
| 4× | first | 144ms | 无重画 | 6 / 53ms | 0 / 62ms |

| 10× | repeat | 138ms | 无重画 | 6 / 59ms | 0 / 66ms |

- **常态切回零重画**：1×/4×/10× 的 `repeat` 与 1×/4× 的 `first` 全部 `panelBlits=0`；`states` 首项就是 `pending:正在更新谱面全景…`（骨架），随后 `canvas:6`，**旧像素签名不再出现在激活后的画面状态里**。
- **编辑场景**（`visual-after.json`）：工程记录哈希 `-1260926265 → 142234741`（134 条音符车道确实改了），隐藏页编辑后仍不重画；点按后 dt=5ms 是骨架、dt=105ms 直接是新像素 `1669347864`（RED：dt=5ms 旧像素 `-69233644`、dt=172ms 才翻成新像素），6 次 blit、0 条长任务。截图序列首张即骨架，与后续画面差 1,499,330 像素。
- **取舍与残留**：为让骨架在激活当帧出现，常态切回也会显示约 30~100ms 加载态（只盖一层 DOM，不出图）—— 判定「不能让用户看到旧音符」优先于「零加载态」。长谱仍各有 1 条 60~115ms 长任务，主要来自 `store.get()` 大记录反序列化 + 页面重渲（RED 同量级），不是出图、也不是等价比较（换成 `JSON.stringify` 快路径后数字未变）；这段时间骨架盖着，用户看到的是加载态而非冻住画面。10× `first` 仍换代一次：应用启动时 `CurrentProjectSession.open()` 改 `lastOpened` 与首次读盘存在竞态，`repeat` 已稳定为零重画。

**结论边界（如实记）**：① headless 软光栅，绝对值不能当真机数字；② `first/repeat` 是「新 context 首次切」与「同页再切」，不是 CDP `Disable cache` 的严格冷/热缓存，真机冷・热缓存仍需手工验收；③ 视觉模式每帧全量 `getImageData` 会饿死合成器，截图里画面变化的时刻（800~1400ms 之间）与 canvas 回写时刻（172ms）不一致 —— **时序以 drawImage 探针 / 像素签名为准，截图只作「画面确实变了」的旁证**；④ 已有同探针 RED→GREEN 对照（上表），但仍**没有真机首帧可见时刻与人工观感验收**；⑤ RED 的 1,201 音符档未触发 50ms 长任务阈值，却仍有 85ms 点按→重画间隔（异步 IndexedDB 读 + 若干短任务），说明「没有长任务」不等于「不卡」，GREEN 用 `panelBlits=0` 才真正消掉了这段。

**实现前的修法约束（留档，已按此实现）**：69 是「首帧同步派生没让出」，静态是「首帧已经画好但内容是旧的 + 激活后一次同步重画」。只补 `waitForPaint()` 不够，必须先把旧画布遮住 / 骨架化，再让可见面板分批出图。实际实现又多走一步：用等价比较把「无编辑切回」的重画整个消掉（见「实现口径」1）；`getBpmEvents` / `ChartGeometry` 派生与全量 DOM 槽按 GREEN 数字未拆（长谱残留长任务来自读盘，不是这两处），留待真机验收后判断。
