# 14 · 素材缓存与过期策略（曲库列表 / 单曲资源）

Type: grilling
Status: resolved
Blocked by: —

## 来源

用户 2026-10-10 对已完成导入功能的意见 #1，原话大意：

> 关于缓存清除问题。没必要每次启动全清除吧？
> a) 先确定哪些资源会被缓存
> b) 对于谱面列表（比如官方谱面列表）这种资源，不需要清除吧？因为用到的频率比较高，经常会浏览这些资源。
> c) 对于每首歌的资源，是否可以采用一些算法，确保只有那些超过多少天没使用的资源才被清除，其它的都在缓存当中？

未改代码，先根因。票 08 已 resolved，按记账规矩不回写；结论落在本票。

## 症状

- 「从官方谱面导入」每次**冷启动**都要重新拉曲库索引（约 400KB）+ 乐队索引。
- 同一首歌第二次导入（新工程）仍重新下载封面 / 音频。
- 用户感知为「每次启动全清除」。

## 根因（2026-10-10 走查）

**现状不存在「资源缓存」这种东西**，只有两块范围很窄的机制，各自被清 / 被丢：

1. **下载暂存 `<数据根>/downloads/` 启动清空** —— `app.whenReady` 里 `resetCommunityStaging`
   （`electron/main.cjs:339-341`、`electron/communityNet.cjs:324-329`）。这是 07 Q4 定案：
   暂存是「导入前的落脚区」的过程态，不攒上一轮没导入的半截文件。它**不是缓存**，
   但确实是用户看到「启动全清」的地方；且 08 已知未做：「导入后不删，靠下次启动清」。
2. **曲库索引只有进程内缓存**（`src/community/bestdori/songs.ts:56-64` 的 `catalogCache`）——
   13 #4 定案「打开后再拉 + 会话缓存」，会话 = 进程内存，**退出即丢**，重启重新拉。
3. **单曲资源（详情 JSON / 谱面代码原文 / 封面 / 音频）从来没有缓存**（`songs.ts:109-180`），每次实打。

因此用户 a/b/c 三条诉求目前一条都没满足：没有缓存清单、列表不跨启动、单曲资源无过期算法。
（唯一存在的「会话内不重拉」是 13 #4，只管切 tab。）

**为什么会这样**：07 Q4 的「启动清空」只覆盖了「半截下载」的过程态；13 #4 只解决「切 tab 重拉」。
「跨启动的可复用素材库」从来没被设计过 —— ADR-0011 §2 原话「音频/封面等大文件的磁盘缓存位置
**归实现票设计**」，一直没落到票。研究文档也早写了「客户端仍应低速率 + **本地缓存**」
（`docs/research/bestdori-api.md` §7）。

## 边界（既有定案，不重新拍）

- **版权**：缓存在用户本机、属「客户端运行时按需取用」档（ADR-0011 §4 + issue 05 风险梯度），
  风险低于捆绑分发；但缓存目录**不得进任何分发物**，也不得成为「再分发素材」的入口。
  issue 05 未结（开放运营 / 变现前复审），本票不改变该时点。
- **缓存不是工程素材**：工程内的音频 / 封面仍拷进 `<数据根>/projects/<id>/`（ADR-0015 §5 不动）；
  缓存只做「下载一次、多处复用」的源。

## 定案

### 2026-10-10 · 首轮 grill（用户答复）

- **Q1 缓存范围 = 全量分级**：曲库索引 + 单曲详情 / 谱面原文 + 封面原图与缩略图 + 音频全部进缓存，
  按「最久未用」回收。
- **Q2 回收参数 = 24h / 30天 / 1GB**：列表 24h 过期（先用旧索引、后台刷新）；单曲资源 30 天未用即清；
  总量上限 1GB，超了按最久未用清。

### 2026-10-10 · 次轮 grill（用户答复）

**Q3 = A · 缓存取代暂存（用户 2026-10-10 拍板）**

- `<数据根>/cache/community/` 成为唯一下载落点（按 URL 短哈希寻址 + `lastUsedAt` 索引）；
  导入 cache-first（命中直接用缓存文件拷进工程，未命中下载进缓存）。
- `downloads/` 退役、**启动不再清空**（清扫交给回收算法，含超龄 `.part-*` 半截文件）。
- 随之修订（不回改原票，结论在本票）：07 Q4「启动清空 `downloads/`」；`projectStore.copyStagedFile`
  的「暂存目录内」校验改指缓存目录；数据根搬家 / 认领时缓存随整包走。

**Q4 = A（带修正）· 设置页加缓存块（用户 2026-10-10 拍板）**

- 落在既有「存储与数据」分区（`settings.section.data`，与「谱面与资源 / 数据根」同区），
  **不新增侧栏条目**（用户修正）。
- 内容：占用展示（总量 + 文件数；分桶按缓存自己的 kind 粒度给「索引与文本 / 封面与音频」两类 ——
  缓存内部只有 json / text / binary 三档，拆不出「封面 vs 音频」，落地记录里写明）
  + 「清除缓存」（整目录清空，索引一并清，会话内曲库缓存也失效，下次重新拉）。

## 实现落点（拍板已齐）

- `electron/dataRoot.cjs`：新增 `cacheDir`（`cache/community/`，进 `ensureDataRootLayoutSync`；
  搬家随整包拷走）；`downloadsDir` / `resetCommunityStaging` 链路退役。
- 主进程：素材缓存模块（按 URL 短哈希寻址 + 元数据索引 `lastUsedAt`；**启动全扫一次**，
  **写入后**容量兜底 + 每小时节流的年龄扫描（含超龄 `.part-*`））；IPC 面新增「占用查询 / 清除」两条（设置页用）。
- `electron/main.cjs`：去掉 `resetCommunityStaging` 启动调用；网关 `stagingDir` 指向缓存目录。
- `electron/projectStore.cjs`：`copyStagedFile` 的路径校验改指 `cache/community/`。
- `src/community/bestdori/songs.ts`：索引 / 详情 / 谱面原文 / 封面 / 音频的取数接缓存（16 一并做）。
- `src/pages/settings/SettingsPage.tsx`：「存储与数据」分区加「社区素材缓存」块（占用 + 清除），i18n 新键。
- 曲库刷新：保留失败重试入口；TTL 过期后先用旧索引、后台刷新。

## 锁测

（2026-10-10 已落地，见 Comments 落地记录）

- 缓存命中不打网络（假出口计数）；冷启动命中持久索引不触发曲库请求。
- 清扫只清超龄项（最后使用 ≤ 30 天保留）；超龄 `.part-*` 一并清；总容量超 1GB 按最久未用回收。
- 数据根搬家 / 认领后缓存跟随。
- 07 修订项的锁测改动：`tests/platform/electron/CommunityNetWiring.test.ts` 的「启动即清空下载暂存」
  断言改为「启动不再清空」；`ProjectStoreFs` 一族里 `copyStagedFile` 越界的对照目录改指缓存。
- 设置页：占用数字来自主进程 IPC；「清除缓存」后占用归零、索引一并清。

**真机待验（单测覆盖不到）**

1. 冷启动两次：第一次打开「从官方谱面导入」拉曲库（约 400KB）；关掉应用再开，同一入口**秒开**
   （命中缓存；数据根下 `cache/community/` 能看到 `*-all.5.json` 与 `index.json`）。
2. 导入一次（含封面）→ 工程详情里音频 / 封面正常；**同一首歌再建一个新工程导入**：不产生网络流量，

5. 断网启动：缓存命中时列表仍秒开；未命中资源走既有错误横幅，不白屏、不循环报错。

### 2026-10-10 · 评审后修订（两轴走查的整改）

- **占用分桶真的画出来**（原实现算了 `byKind` 却丢掉，评审点出「票面写了可细分」）：设置页显示
  「索引与文本 / 封面与音频」两桶；缓存内部 kind 只有 json / text / binary，拆不出「封面 vs 音频」，
  票面措辞已按此收紧。
- **清扫时机对齐票面**：写入后除容量兜底外，加**每小时节流**的年龄扫描（长开着的会话也会清超龄项），
  并加锁测「写入后再扫一次」。
- **文本形态的回退页也按 1 小时负缓存**：`storeText` 现在记 `contentType`（原来恒写 null，谱面原文
  取到回退页时会被钉 24h）。
- **「清除缓存」连带失效会话内曲库缓存**（`clearSongCatalogCache()`）：否则同一会话里「清了重拉」看不出效果。

  「单曲资源 30 天」说的是**回收**（已实现）；鲜度按统一 24h + 先回旧的后台刷新落地，代码注释写明。
