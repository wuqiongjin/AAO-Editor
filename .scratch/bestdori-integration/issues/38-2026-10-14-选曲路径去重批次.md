### #1 `songs.ts` / `posts.ts` 三处同形逻辑各两份

- **症状**：`invalidResponse`（`songs.ts:40` / `posts.ts:41`）、`looksLikeMedia`（`songs.ts:180` / `posts.ts:240`）、`coverInflight` 并发去重（`songs.ts:257` / `posts.ts:340`）三对，形状相同。`posts.ts:339` 的注释已自陈「同 songs.ts 的 coverInflight 口径」。
- **根因**：官方（票 08）与社区（票 09）是**两条独立取数路径**，票 07/12 明确要求分开，竖切落地时各写了一份。
- **修法**：`invalidResponse` 上收到 `transport.ts`（贴着 `CommunityError`）。`coverInflight` 抽的是**去重内核**（get 命中即还 → `start()` 发起 → 塞表 → finally 按身份核对清坑）成 `src/community/inflight.ts` 的 `dedupInflight(map, key, start)` —— 两边「完全相同」的只是这个内核：key 类型不同（URL vs postId）、包装不同（社区侧有 non-custom / 无封面早退 + `.catch(() => null)`），差异留在调用方。**`looksLikeMedia` 不要硬合** —— 两边规则**故意不同**（2026-10-14 核对修正：**社区侧**把 `application/octet-stream` 对音频与图片一律放行，**官方侧**图片只认 `image/*`、只有音频放行 octet-stream —— 原稿「官方侧放行 vs 社区侧严判」方向写反了，以两文件注释自陈「官方那条路判定更严」为准），抽公共会抹掉这个差异；若要抽，须把「octet-stream 对图片放不放行」显式化为参数并保留两侧各自取值。同模式另有 `catalogInflight` / `pageInflight` / `idLookupInflight` 三处，用户拍板（2026-10-14）本次不抽。
- **Status**: resolved（2026-10-14，#1 范围 = invalidResponse + 两处 coverInflight）

### #2 等级窗口归一化 `lo/hi` 近乎逐字重复

- **症状**：`songs.ts:329-336` 与 `posts.ts:379-386` 的 `hasLo/hasHi → lo/hi` 归一化**近乎逐字相同**（含 `?? filter.levelMax as number` 的断言写法），仅后续取 `filter.difficulty` 还是 `filter.diff` 不同。
- **根因**：同上，两条路径各写一份。
- **修法**：**最值得先抽的一条** —— 纯函数、两边零差异、无外部依赖。抽成 `src/community/levelWindow.ts` 的 `normalizeLevelWindow(filter)` 返回 `{ lo, hi }`，两处调用。
- **Status**: resolved（2026-10-14）

### #3 两个选曲面板近乎同形

- **症状**：`OfficialSongPanel.tsx:265-576` 与 `CommunityPostPanel.tsx:414-644` 的筛选手风琴、`off-cover` 三态 + `retryCover` + `coverImgRef` 竞态护栏、列表行结构近乎同形；`chipLabel` 两份且**入参类型不一致**（`OfficialSongPanel.tsx:60` 收 `OfficialDifficulty`，`CommunityPostPanel.tsx:75` 收 `number`）。`CommunityPostPanel.tsx` 文件头注释自陈「骨架完全照 OfficialSongPanel」。**（2026-10-14 核对修正：`useSlowLoading` 不算重复 —— 它本就是 `src/ui/LoadingShimmer.tsx` 的共享 hook，150ms 常量只有一份，两个面板都是 import。）**
- **根因**：票 09 竖切时为赶进度显式复制票 08 的面板骨架，之后两边各自演化（难度类型一个用枚举、一个用数字）。
- **修法**：**风险最高、也最不该现在动的一条**。见「锁测」第 3 条 —— `tests/static/OfficialPickerPreviewBatch.test.ts` 等静态源码断言直接断言 `OfficialSongPanel` 里的字串，抽公共会让一批断言变红。要做就先统一难度类型、再抽面板骨架，并同步改锁测。
- **Status**: wontfix（2026-10-14 用户拍板**不做**：两边各自演化是常态、无第三个消费者，抽骨架的收益低于回归风险。重启条件——将来出现第三个选曲面板、或两边语义收敛且难度类型统一之后，再议）

3. **#3 先补锁再动刀**：现状先加 `tests/static/OfficialPickerPreviewBatch.test.ts` 风格的静态断言，锁住两个面板当前的 `retryCover` / `coverImgRef` 竞态护栏与 `useSlowLoading` 延迟 150ms 口径；抽骨架后这批断言须仍全绿。
4. **全量门禁**：`npm test`（基线 2026-10-14：**256 文件 / 3027 用例**）、`npx tsc -b`、`npm run build` 全绿。
