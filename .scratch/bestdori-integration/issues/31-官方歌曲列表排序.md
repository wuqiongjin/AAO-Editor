# 31 · 官方歌曲列表排序

Type: feature
Status: resolved (2026-10-13)

## 来源

用户 2026-10-13：「官方歌曲列表是否可以加个排序？（按发布时间/谱面ID/等等）」

## 现状与根因

- **没有排序功能**：`OfficialSongPanel.tsx` 只做过滤（`filterSongCandidates`），列表顺序由 `src/community/bestdori/mapping.ts:163-176` `toSongCandidates` 按 **song id 升序**写死。
- **发布时间数据在但不进候选**：曲库原始条目有 `publishedAt`（每服一个数组），当前只用于 `pickAssetServer` 选素材服，未映射进 `SongCandidate`（`mapping.ts:44-58` 只有 id/bandId/title/artist/jacketImage/server/difficulties）。
- 参考：工程列表已有排序先例（`src/project/projectSort.ts`，四键）。

## 修法

1. `SongCandidate` 增 `publishedAt`（映射层取主服或最早服时间，口径拍板后定）；
2. 面板加排序控件（与难度/等级筛选同一排）；排序键与默认排序待拍板。

## 定案（用户 2026-10-13）

- 排序键：**发布时间 / 谱面 ID / 曲名 / 乐队名** 四键；**默认 = 发布时间降序（最新在最上）**。
- 其他便捷键评估：难度/等级不进排序（语义已由筛选手风琴承担，两套难度语义并存收益低）；曲长等需额外拉详情，不做。
- publishedAt 各服口径：实现口径取**最早发布时间**（日服优先），待验收。

## 落地（2026-10-13）

- `mapping.ts`：`SongCandidate` 增 `publishedAt: number | null`；新 `earliestPublishedAt(raw)` 扫各服
  `publishedAt`（数字串 / 数字都收）取最小正值，空 / 0 / 负数 / 非数字一律跳过，一个有效值都没有才是 null。
  与 `pickAssetServer` 是两个问题（那个是「哪一服有素材」，这个是「什么时候上的」）。
- `songs.ts`：`SongSortKey` + `SONG_SORT_KEYS` + `DEFAULT_SONG_SORT_KEY` + `sortSongCandidates`
  （照 `projectSort.ts` 的写法：键白名单、id 兜底、不改原数组）。
  方向：发布时间降序、id 升序、曲名 / 乐队名按显示名 `localeCompare('zh-CN')` 升序；
  `publishedAt` 为 null 的排最后（对「最新在前」而言未知不该占首位）。
  （方向轴是后来那次验收回修补上的，见下。）
- `OfficialSongPanel.tsx`：**排序控件放在搜索框那一排**（搜索 / 刷新 / 筛选之后、计数之前），
  `<label class="off-sort"><span>排序</span><select>` —— 与启动台的 `.pb-sort` 同形。
  （控件形状与「会话内 state」两处都已被下面的验收回修推翻：换成 pill + 芯片，且落 settings。）
- 与票 33 的次序：`filter → sort → promoteIdMatches`。id 置顶是「搜索语境」的覆盖，必须排在用户选的排序键之后，
  否则换任意排序键就把置顶打散。
- 验收口径（待用户确认）：排序控件的位置（放搜索框那排，而非筛选手风琴里）；
  ~~排序不落 settings~~ → **已被验收回修 #2 推翻**（用户：肯定要保存），见下。

## 验收回修（2026-10-13，用户看截图后）

用户三点意见，前两点在本票、第三点落在票 32/33：

> 这个排序样式太丑了。并且它放这个位置合适吗？

1. **控件换成 app 自己的语言**：原生 `<select>` 的 OS 弹层（蓝底高亮）跟 bar 里那排 pill 不是一套语言，
   已换成「状态 pill + 一排芯片」——pill 上写当前状态（方向箭头 + 键名，如 `↓ 发布时间`），
   点开在 bar 下方出一排芯片（4 键 + 升序 / 降序），与左侧「筛选」同形、同位置。**位置判断：留在 bar 里**
   —— 它是「视图控制」，与筛选同级；丑的是弹层，不是那一格。两排芯片互斥（同时开会叠成两段）。
2. **加升序 / 降序**：`sortSongCandidates(songs, key, dir)` 多一个方向轴。
   - 每个键有**自然方向**（`SONG_SORT_NATURAL_DIR`：发布时间 `desc`，其余 `asc`）；点键 = 采用该键的自然方向
     （换到「曲名」就该 A→Z，而不是沿用上一把键的降序），之后再点升序 / 降序覆盖它；`dir` 省略 = 自然方向。
   - `publishedAt` 为 null 的**哪个方向都垫底**（未知不该占首位）。
   - 顺手删掉 `normalizeSongSortKey`（它的唯一消费者是那个 select）—— 不留没人用的白名单函数。
3. **重写锁测**：单测补方向（互反 / 升序时 null 仍垫底 / 自然方向表）；DOM 补「换键 → 换方向 → pill 文案跟着变」
   与「筛选 / 排序两排互斥」。
- 视觉核验：用 Playwright 起真机页面（注入假 communityNet 桥）截图核对 pill 与芯片排的观感，与筛选行同形；
  临时脚本与截图都在系统临时目录、未入库。

## 验收回修 #2（2026-10-13）：排序落 settings

> 排序的设置肯定要保存。

- `AppSettings.projects` 增 `songSort: { key, dir }`（additive，不 bump schemaVersion；默认
  `{ key: 'publishedAt', dir: 'desc' }`）—— 与 `sort`（启动台）/ `importWithChart`（票 28）同段、同范式。
- `songs.ts` 出 `SongSort` 类型 + `SONG_SORT_DEFAULT` + `normalizeSongSort`：**两个轴各自白名单**
  （settings 是不可信输入：手改过的 localStorage、旧版本写的值都可能不在白名单里），坏的那一轴回落默认、
  另一轴保留；整个值不是对象也一样。→ 上一轮删掉的 `normalizeSongSortKey` 以更强的形态回来了（现在有真消费者）。
- `ConfigProvider` 增 `setSongSort({ key, dir })`：字段级写回 + `saveSettings`（与 `setImportWithChart` 同范式）。
- `OfficialSongPanel.tsx` 不再自己存 state，直接读 `settings.projects.songSort`；改一次即落盘。
- 跨模块引用：`chart/config/AppSettings.ts` → `community/bestdori/songs.ts`（照 `projectSort.ts` 的先例，
  能力模块持有自己的枚举与归一化；songs.ts 不 import Electron，主进程无牵连）。
- 锁测：`tests/unit/chart/config/ProjectSortSettings.test.ts` 新增「票 31 · settings.projects.songSort」——
  出厂默认、additive 不 bump、save→load 往返、缺段 / 段非对象 / 半脏值（键坏保方向、方向坏保键）；
  DOM（`OfficialPickerThumbs.test.tsx`）补「改一次就写回 localStorage」+「开门就用上次存的键与方向
  （种一个与默认顺序不同的档：id 升序 → 5 在前）」。
