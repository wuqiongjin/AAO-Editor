# 33 · 官方谱面 ID：展示与搜索

Type: grilling
Status: open

## 来源

用户 2026-10-13：「官方谱面，可以增加官方谱面的ID吧？→ 并且要直接支持ID搜索、以及歌曲详情页是否要加上？」

## 现状与根因

**ID 已经存在，缺口同样在"不展示、搜不到"**：

- `SongCandidate.id` 即 Bestdori songId（`mapping.ts:45`）；工程侧已持久化 `source = { type: 'bandori', id: song.id }`（`officialImport.ts:126`），工程详情页有回显「bandori #id」（`ProjectDetail.tsx:88` → `sourceLabel()`，`projectFormat.ts:29-33`）。
- **展示缺口**：选曲面板的列表行与预览栏（`OfficialSongPanel.tsx`）都不显示 songId。
- **搜索缺口**：`filterSongCandidates`（`src/community/bestdori/songs.ts:313-338`）只匹配 title/artist，纯客户端、曲库全量在内存 —— **加 songId 匹配是零成本**（数字前缀/精确匹配即可）。
- **粒度问题**：官方"谱面" = songId + 难度，Bestdori 没有独立 chartId 字段（`/songs/info` 的谱面数据按难度键挂在 song 下）。用户说的"官方谱面ID"大概率指 songId；若要难度级引用，只能用 `songId-diff` 约定表达。

## 待拍板

1. ID 显示位置：列表行 / 预览栏 / 都放（工程详情页已有，是否统一文案）。
2. 搜索匹配规则：精确匹配 vs 数字前缀（输 `1` 命中 1/10/100…）。
3. 是否需要表达"谱面级"（songId+diff）引用，还是 songId 到顶。

## 定案（用户 2026-10-13）：ID 搜索行为

用户口径同票 32（纯数字 → id 匹配优先展示，其余结果照常）。

- **官方侧无"两个请求"**：曲库全量在内存，客户端过滤同时命中 songId 与 title/artist，**ID 命中行置顶、其余照常列出**，零网络成本。
- 匹配规则实现口径：输入串为纯数字时按 songId 匹配；前缀 vs 精确 —— 待验收（倾向前缀匹配 + 精确命中排最前）。

## 追加定案（用户 2026-10-13 二轮）

2. **songId 常驻展示**：列表行与预览栏都显示（理由同票 32：ID 搜索多结果时需辨别）。工程详情页已有回显，维持。

## 仍待拍板

1. 是否需要"谱面级"（songId+diff）引用表达（低优先，默认不做）。
2. 官方 songId 已落盘且有消费，**维持现状、不扩面**（2026-10-13 二轮与用户对齐来源数据类：二次发布时来源信息会变，新增落盘无消费场景，不做）。

## 实现落点（拍板后细化）

`songs.ts`（filter）+ `OfficialSongPanel.tsx`（展示）+ i18n。

## 锁测

- 单测：`tests/unit/community/bestdori/` filter 用例补「输入数字命中 songId」分支（含与 title 撞车的数字标题行为）。
- DOM：预览栏/列表行 ID 显示断言。
