# 44 · 官方/社区列表：超时看不见、刷新钮空转

Type: grilling
Status: resolved
Blocked by: —

## 来源

用户 2026-10-16 真机 #1：卡在「正在拉取官方曲库…」；此时点「刷新歌曲列表」钮无限转圈、无超时提示；很久之后第一次拉取成功列表出来了，刷新钮仍转。

## 症状

- 首屏可以一直停在「正在拉取官方曲库…」，不像会超时。
- 拉取中点刷新：钮 `is-busy` 转圈，没有失败文案。
- 列表终于出来后刷新钮仍转。

## 根因

**超时机制是有的，但挡不住这次复现，界面也几乎报不出来。**

1. **单次超时 30s，只在真正 `fetch` 开始后才计时**（`electron/communityNet.cjs` `send()` 的 `AbortController`）。API 档是 **1 并发 + ≥400ms 间隔**（票 17）。排队等待**不计入**超时。
2. **renderer 再套 3 次退避**（`BESTDORI_RETRY_POLICY`：含首次共 3 次，timeout 可重试）。一首 URL 最坏 ≈ 90s + backoff；曲库是 **索引 + 乐队两条串行**，最坏可到 **三分钟级**。超时文案只在三次都死光才冒出来；第一次挂死时 `onRetry` 还没触发，界面一直是「正在拉取…」而不是「正在重试…」。
3. **票 29 的 `freshFirst` 把「有磁盘缓存也秒开」改成了「先打穿网络，失败才回退缓存」**。本地明明有曲库副本，首屏仍被跨境慢链堵住。票 29 还写了「回退时给轻量提示」——**提示从未落地**。
4. **刷新与首拉不是同一趟请求**：`refreshSongCatalog` 先 `clearSongCatalogCache()`（只把 `catalogInflight` 指针清掉，**不 abort 正在飞的那趟**），再排队两发 `revalidate`。首拉成功 → `setCatalog` 列表出现；刷新那两发还在 API 档后面等，钮的 `refreshingCatalog` 要等它们 settle 才放下。跨境链路上这像「列表出来了钮还在转」。若前面那发 `net.fetch` 的 abort 没真正掐死，后面全部堵死，钮会转到永远。
5. 超时 abort **只包住 `fetchImpl` 到响应头**；`response.text()` 读 body 没有第二道时限。网关单测的 abort 用的是尊重 `signal` 的假 `fetchImpl`，**没锁 Electron `net.fetch` 真机会不会忽略 abort**。

社区列表同一套网关 / 同一颗刷新钮，同源。

## 定案（用户 2026-10-16）

本会话首次仍等这一枪网络；**不**缓存秒开、**不**后台偷换列表。列表一旦上屏，只有用户点刷新才整表替换。刷新若撞上还在飞的首拉 → 并进同一趟，不另排一队空转。超时/重试必须出字；三次都死且有磁盘缓存 → 这时才拿出缓存并标明「当前是本地缓存」（失败回退，不是后台偷换）。状态行观感跟票 46 原型走。

## 实现落点

`refreshSongCatalog` / `fetchPostPage`：同一趟还在飞则并进，不另排队。首屏仍 `freshFirst` 等这一枪。加载态跟票 46。

## 锁测

`tests/unit/community/bestdori/songs.test.ts`（并进 inflight；刷新失败留会话缓存）；`posts.test.ts` 同上；`CommunityNetGateway.test.ts`（freshFirst 回退带 fromCache）；`NewProjectSourceCopy.test.ts`（空台慢/失败文案）。

## Answer

首屏等这一枪网络，不缓存秒开。刷新并进在飞请求，成功前保留上一份列表。空台：拉取 → 8s 较慢 → 重试；无缓存居中失败；有缓存 Toast 使用上次结果。已有列表刷新失败只 Toast「刷新失败」。
