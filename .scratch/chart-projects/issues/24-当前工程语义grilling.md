# 24 · 「当前工程」的语义与切换（grilling）

Type: grilling
Status: open
Blocked by: —

**来源**：用户 2026-09-28 第三轮验收第 5 条——「切换当前工程，一定要"进入工作台"吗？（当前这个语义，用户真的能立刻弄明白吗？我感觉会很困扰吧？就是关于"当前"工程这个状态）」。用户当轮原文并明确"这与我之前提出的『当前工程到底怎么切换、怎么让用户明白当前工程这个概念和机制』有关"，且判定它**值得单独立场**（票 23 Q1=(a)）。

**症状**

- a) 「当前工程」这个状态在 UI 上**到处都是**，但**没有一个地方解释它是什么、为什么要它**：hub 卡片封面左上角的 `.pb-card__current`、详情左栏的 `.pp-current-tag`（两套视觉）、工作台的面包屑。用户看到徽标但不知道它的后果。
- b) **切换「当前工程」的唯一显式路径是"进入工作台"** —— 而"进工作台"是个页面跳转，「当前工程」是个状态。两个东西被绑在一个按钮上，于是用户以为"切当前工程 = 必须离开这个页面"。（票 23 已经把这层绑定拆开一半：创建/复制会静默改当前工程而不跳页 —— **那正是本票必须回答的问题**：静默改当前工程是否是用户能理解的？）
- c) 同一个动作有**四种文案**：`projects.enterWorkspace`「进入工作台」/ `projects.openInWorkspace`「在工作台打开」/ `projects.open`「打开」/ `projects.play`「直接进工作台」。用户要自己悟出它们是一回事。
- d) **缺一个"切当前工程"的正向语义**：想改当前工程但不想跳走时，用户没有任何入口（票 23 的创建/复制是副作用，不是入口）。

**待定问题（本票要拍板的）**

1. 「当前工程」到底**为什么要存在**？没有它，工作台"打开最近一个 / 新建"是不是就够？（ADR-0015 §3 的理由需要重述一遍：单例 Editor / 音频会话 / 持久化 / 快捷键分发都要求"同一时刻只有一个"，且进工作台要能直接回到上次的地方。）
2. **切换当前工程的入口应该是什么**？候选：
   - 保留"进入工作台"作为唯一入口（现状）；
   - 详情页给一个显式的「设为当前工程」动作（语义清楚，但多一层概念）；
   - **消除显式概念**：把"当前工程"降级为"工作台正在编辑的那个"，用户不再需要知道它 —— 只在工作台里能改，工程管理页只读展示"工作台在用：X"。
3. **「当前」徽标怎么表达**才不需要解释？是不是该从"状态徽标"改成"一句话"（例如"工作台正在编辑：Unmei no Hana"）？
4. **文案统一**：四种说法收敛成几种、分别用在哪（hub / 详情 / 面包屑）。
5. **「↑↓ 改当前工程」是否要做**（票 23 Q4 挂到本票的待定项）：在详情页按 ↑↓ 静默把工作台切到下一个工程，是"顺手"还是"危险"？它与第 2 问的答案强耦合 —— 如果第 2 问的结论是"用户不该感知当前工程"，那 ↑↓ 改它就无从谈起。
6. **ADR 落点**：本票很可能产出 ADR-0015 §3 的修订，或一个独立 ADR（若结论是"当前工程"概念本身要改形状）。

**为什么不能塞进票 23**

票 23 是"你报的 4 条 UI 缺陷"，验收标准是**看得见的页面行为**。本票要动的是**领域概念**（`当前工程` 与 `页面作用域` 的关系、ADR-0015 §3 的根基），会牵动 Editor / 音频会话 / 持久化 / 快捷键分发这一组单例。混在一起会让票 23 的验收被一个架构讨论堵住。

**与票 22 的关系**

票 22 刚把「页面作用域」与「当前工程」**分成两个词**（定了"不得用『当前』表示作用域"）。本票要问的是**另一个方向**：如果连「当前工程」本身都让用户困惑，是不是它的"存在感"（到处是徽标）需要收敛？票 22 定的是"作用域不是当前";本票要问"当前 到底是什么、要不要让用户看见"。
